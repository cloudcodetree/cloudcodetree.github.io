# Phase 2 — The Gate: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Real, server-enforced auth on `/projects/<slug>/demo/*` with Supabase identity (Google + magic link), an HttpOnly same-origin session cookie minted by `/api/session`, append-only `demo_events` analytics under RLS, a skippable profile step, and span-calculator vendored as the pilot demo — all verified on staging.

**Architecture:** Per the spec. The Worker verifies Supabase ES256 JWTs against cached JWKS (zero network per request after warm), mints/clears the `cct_session` cookie, gates demo paths, and logs `demo_open` via PostgREST **as the visitor** (their JWT; no service key exists in Worker env). Frontend adds a sign-in dialog, profile dialog, and launch button wired to the manifest.

**Tech Stack:** `jose` (JWT/JWKS in the Worker), supabase-js (browser), Supabase CLI SQL migrations, vitest (real ES256 keys in tests — no crypto mocks), existing staging deploy path.

**Spec:** `docs/superpowers/specs/2026-08-20-projects-gated-demos-design.md`

## Global Constraints

- cloudcodetree.com untouched. All verification on `cct-site-staging`.
- **No Supabase service-role key may ever reach Worker env or repo.** Events are written with the visitor's own verified JWT; RLS (`insert`-only, `user_id = auth.uid()`, no `select`) is the enforcement.
- Cookie: `cct_session`, `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600`, value = the Supabase access token verbatim.
- JWKS unreachable → **503, fail closed**. All auth failures on demo paths → 302 to `/projects/<slug>/?signin=1&next=<path>`. `next` guard: `^/projects/[a-z0-9-]+/demo/`.
- Log only navigation requests (`Sec-Fetch-Mode: navigate` or path ends `/demo/`), wrapped in `ctx.waitUntil`; logging failure never affects the response.
- `_headers` `connect-src` must gain the Supabase project origin + `https://accounts.google.com`; extend `scripts/validate-csp.mjs` REQUIRED accordingly (test first).
- Env names: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (build), `SUPABASE_URL` (Worker var). Worker gains no secrets.

## Task 2 — Worker auth core (no account needed; TDD with real ES256 keys)

`worker/auth.ts`: `verifyToken(token, env)` via `jose` `createRemoteJWKSet(new URL('/auth/v1/.well-known/jwks.json', env.SUPABASE_URL))` cached per isolate; checks `exp`, issuer `${SUPABASE_URL}/auth/v1`. `mintCookie(token, maxAge)` / `clearCookie()` string builders. `safeNext(raw)` guard. Tests: sign with a locally generated ES256 key served from a stubbed JWKS fetch — valid passes; expired/forged/wrong-issuer fail; JWKS fetch failure → distinct error for the 503 path; `safeNext` rejects absolute URLs, `//`, non-demo paths.

## Task 3 — `/api/session` (no account needed)

`worker/session.ts`: `POST` body `{access_token}` → verify → `Set-Cookie` mint + 204; invalid → 401. `DELETE` → clearCookie + 204. Any other method → 405. Wire into `worker/index.ts` router. Tests cover all branches.

## Task 4 — Gate + events (no account needed)

`worker/events.ts`: `logDemoOpen(env, ctx, {token, userId, slug, request})` → `fetch(${SUPABASE_URL}/rest/v1/demo_events, {headers: {apikey: env.SUPABASE_ANON_KEY, authorization: Bearer <visitor token>, prefer: 'return=minimal'}})` inside `ctx.waitUntil`, errors swallowed. `worker/index.ts`: demo path → cookie token → verify → serve via `env.ASSETS.fetch` + log on navigation; missing/invalid → 302 with `signin=1&next=`; JWKS outage → 503. Tests: 302 targets, exactly-one-log per navigation, zero logs for sub-assets, 503 fail-closed, `/api/*` unaffected.
