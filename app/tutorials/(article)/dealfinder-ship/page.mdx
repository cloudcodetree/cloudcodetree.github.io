## The hero cast: four items, one story

The same four noise-cancelling headphone listings recur throughout the course because they show every edge case a deal-finding system must handle. The anchor query median for "noise cancelling headphones" in the snapshot is **$162.97**.

| Item | Price | residual_frac | Verdict | Why it matters |
|---|---|---|---|---|
| Sony WH-1000XM5 | $162.97 | +0.428 | **FAIR** | Sits at the median. Also appears at $248 (Macy's) — the canonical dedup example. |
| Anker Soundcore Q20i | $44.99 | +0.585 | **DEAL** | 72% below median, and the model confirms it: predicted fair $108.33. Genuine value. |
| Bose QuietComfort 45 | $46.00 | +0.839 | **SUSPICIOUS** | Also 72% below median, but predicted fair $285.15. A $329-MSRP flagship at $46 with no condition token. The model catches what the median misses. |
| Sony WH-1000XM6 | $399.99 | −0.403 | **OVERPRICED** | Above fair price. Premium anchor, legitimately above median. |

The Bose and the Anker are at nearly the same price and both look like deals by median alone. Only the residual separates them: 0.585 for the Anker (honest budget headphones) vs 0.839 for the Bose (suspicious — model says that price is implausible for a tier-4 flagship). That gap is the entire motivation for the price model. You can see it live with:

```bash
pytest tests/test_dealscore.py -v
```

The sign convention is fixed course-wide: `residual = predicted_fair − actual`. Large positive residual means suspiciously cheap. The suspicious threshold is `median_signal ≥ 0.70 AND residual_frac > 0.70`. The Bose triggers both (median_signal 0.718, residual_frac 0.839). The Anker clears the median gate but not the model gate (residual_frac 0.585 < 0.70) — so it correctly lands as DEAL, not SUSPICIOUS.

## Write it up as a case study

A strong case study is four beats: **problem → approach → results → what you'd do next**. Here is the version for DealFinder, using only real numbers from the course.

**Problem.** Consumer electronics listings from Google Shopping are polluted: the `brand` field holds the retailer in 156 of 270 real snapshot rows, the same product appears at two prices across sources (Sony WH-1000XM5 at $162.97 and $248), and the naive deal signal — percentage below the query median — awards a 72% discount badge to a $329-MSRP flagship listed at $46 with no verifiable condition. A useful deal-finder must normalize the data, dedup across sources, and use a price model to guard against the false positive.

**Approach.** Built in seven phases across 33 parts:

1. A `DealSource` interface abstraction over five live sources (eBay, RapidAPI, Apify, Shopify, Firecrawl) with tiered early-stop and a 90-second circuit breaker. Sources that raise or timeout are benched for the cooldown period; a query with all sources down returns a well-formed empty envelope, never a 500.
2. A two-signal deal score: a cross-source live median (fast, model-free) combined with a gradient-boosted price model trained on the real 270-item snapshot (MAE $138.11, R² 0.727, −39.4% vs. the linear baseline). The model residual is the guard that catches the Bose QC45 false positive.
3. Hybrid retrieval: semantic search over 384-dim `BAAI/bge-small-en-v1.5` embeddings persisted in pgvector, BM25 keyword match, fused with RRF and reranked by deal score. Semantic cache at cosine threshold 0.90 gives a 0.500 cache hit rate over 14 test queries.
4. A ReAct agent exposed as an MCP server; the web frontend streams results via SSE with a GET fallback.
5. A full SaaS platform: Supabase JWT auth, Stripe plan gating (free 25 / pro 1,000 queries), sliding-window rate limiter, GDPR export and delete, abuse detection.
6. An MLOps loop pinned to real numbers: PSI 0.043 holds, 0.318 triggers retrain; the eval gate (precision@5 ≥ 0.80) promotes the two-signal ranker (1.00) and rejects the median-only ranker (0.40).
7. Deployed on Docker + Terraform + Kubernetes (HPA 2→10 pods at 70% CPU); 166 tests pass; 5 Playwright e2e scenarios pass; load measurements anchored locally at /healthz p50 2.4ms / 346 req/s, /search p50 10.1s (network-bound).

**Results (all real, all test-pinned).** Linear MAE $227.89 → GBDT MAE $138.11 (−39.4%). Precision@5 on the 20-item golden set: 1.00 (two-signal) vs 0.40 (median-only). Semantic cache hit rate 0.500 at threshold 0.90. PSI-triggered retrain promotes with probability 1.00 on the 20-item gate. 166 tests pass across the full stack.

**What comes next.** A learned reranker trained on user click signals would replace the heuristic RRF fusion. Real-time price-drop alerts from a Kafka stream would replace the batch MLOps loop. A production vector database (Pinecone or Qdrant) would replace the local pgvector instance for horizontal scale. The eval golden set should grow from 20 to 200+ items with user-labeled relevance, and the LLM judge (Part 19) should gate on that larger set.

## Mock system-design interview

The question: **"Design a system that finds good deals for a user given a product query."**

This is not a hypothetical. You built this system. The answers below map directly to decisions you made and code you ran.

<Callout tone="tip">
**Drill these out loud before an interview.** The goal is not to recite the architecture — it's to show you understand the tradeoffs and made deliberate choices. Each question below is a real probe a senior interviewer would use.
</Callout>

**Q: Walk me through the requirements and what makes this problem hard.**

Start with the data, not the model. The raw listings are polluted: brand fields hold retailers (156/270 rows in the real snapshot), the same product appears at multiple prices across sources, and a naive deal signal — percentage below the query median — awards a 72% discount badge to a mispriced flagship. You need normalization, deduplication, and a price model before you can trust the signal. The model itself is hard: electronics span 11 categories from $8 USB cables to $3,000 laptops; a single linear model fails (R² 0.268, MAE $227.89) because the relationship is non-linear and category-specific. Gradient boosting on category + brand tier + title embeddings brings MAE to $138.11.

**Q: How does the aggregator handle source failures?**

Each source implements a `DealSource` interface. The aggregator runs them in tiers with early-stop: if the first tier returns enough results, lower tiers are skipped. Sources that raise exceptions or time out are added to a cooldown list for 90 seconds (`COOLDOWN_SECONDS = 90.0`). The chaos tests confirm the invariants: one bad source doesn't break the search (healthy sources still serve), and all sources down returns a well-formed empty envelope (`results == []`, `count == 0`, `sources_live == []`) — never a 500. `tests/test_chaos.py` runs 5/5 offline.

**Q: Why hybrid search instead of just embeddings?**

Embeddings capture semantic similarity but miss exact model numbers — "WH-1000XM5" and "WH-1000XM6" are neighbors in embedding space but very different products and price points. BM25 catches exact-match queries but fails on synonyms ("noise cancelling" vs "ANC"). RRF fuses the two rankings without a tuned weight parameter: each retriever contributes its rank, and the combined score is robust to either retriever misfiring. The deal score reranks on top of that, so the final order reflects both relevance and value. All embeddings are `BAAI/bge-small-en-v1.5` (384-dim, fastembed) — one model, course-wide, cached in pgvector from Part 4.

**Q: How do you know the deal score is correct — and won't regress?**

Two answers. First, a 20-item golden set (all 15 headphone snapshot items + 5 cross-category), hand-labeled `DEAL|FAIR|SUSPICIOUS|OVERPRICED`. Precision@5 on the golden set is 1.00 for the two-signal ranker, 0.40 for median-only. Second, the eval gate in CI: every model candidate must clear precision@5 ≥ 0.80 before it can reach production. The MLflow registry holds the lineage; `tests/test_evals.py` pins the numbers. If the score regresses, CI fails and the deploy stops.

**Q: The system is too slow for real-time search. What do you do, in order?**

First, look at where time is actually spent. The load test shows /healthz at p50 2.4ms and /search at p50 10.1s — the latency is network-bound (live source queries), not compute-bound. The first lever is the semantic cache: 384-dim embeddings from the query are compared to cached query vectors at cosine threshold 0.90; 7 of 14 test queries hit the cache (0.500 hit rate). That costs one vector comparison instead of 5 live API calls. Second, the tiered aggregator with early-stop means if tier-1 sources (RapidAPI + eBay) return sufficient results, tiers 2 and 3 are skipped entirely. Third, if the extractor or ranker model is the bottleneck, quantization (Part 23) reduces memory and speeds inference without changing the interface. Last resort: smaller embedding model that still passes the eval gate.

**Q: A user reports a wrong deal badge. Walk me through debugging.**

Every search request produces a trace via Langfuse (Part 26): the query, which sources responded, the raw offer list, the model inference inputs and outputs, the final ranked list with scores and badges. Start there. Find the session with that offer. Check the residual: `residual = predicted_fair − actual`, `residual_frac = residual / predicted_fair`. If the badge is SUSPICIOUS but should be DEAL, either the model overestimates fair price (brand tier or category feature wrong) or the title condition parsing misfired. Reproduce the specific inference with the offer dict, fix the feature extraction, add the offer to the golden set, and run the eval gate. If it passes, promote.

**Q: How does the system stay correct after launch as data drifts?**

Population Stability Index (PSI) runs periodically against the training distribution. PSI 0.043 means the new data looks like training data — hold. PSI 0.318 exceeds the retrain threshold (0.2) — trigger retrain on the new data, run the eval gate (precision@5 ≥ 0.80 on the golden set), and promote if it passes. The MLOps cycle in Part 20 runs this end to end and the promotion reason string is real: "promoted: two_signal passed the gate (p@5=1.0 ≥ 0.8) and beat champion median_only (0.4)". The canary rollout shifts traffic gradually rather than a hard cutover.

**Q: What are the top three things you'd do differently in production?**

First, the golden set is only 20 items. For a production system you'd need 200+ with user-labeled relevance, refreshed as inventory shifts, with LLM-judge scoring on the long tail. Second, the live aggregator timeout is fixed at 90 seconds; a production system would use adaptive timeouts per source based on observed p99 latency and budget these against the overall SLO. Third, the price model uses a frozen snapshot for training — a production system would retrain on a sliding window of live offers with temporal splits to prevent leakage, and the brand-tier vocabulary would be updated automatically from offer data rather than a hand-curated list.
