## Write it up as a case study

A good case study is four beats: **problem → approach → results → what you'd do next.** For DealFinder:

- **Problem.** Find genuinely good deals from messy, multi-source product data — relevance *and* value, not just keyword matches.
- **Approach.** A typed ingestion layer behind one interface; a from-scratch price model for fair value; hybrid semantic+keyword search reranked by deal score; an agent orchestrating it; shipped behind an API/MCP with guardrails, evals, and observability.
- **Results (use real numbers).** Price model R² 0.886; semantic search surfaces relevant tents with zero keyword overlap; the agent answers a plain-English goal end to end; CF beats the popularity baseline; 53 tests + an eval gate in CI.
- **Next.** Real retailer data, a learned reranker, a production vector DB, online A/B testing.

## Résumé bullets that read as outcomes

Lead with the result, not the tool. Weak: *"Used Python and FastAPI."* Strong:

- *Built an end-to-end AI deal-finder: hybrid retrieval (embeddings + BM25 + RRF) reranked by a from-scratch price model (R² 0.886), served behind a FastAPI/MCP API.*
- *Shipped it production-grade: prompt-injection & PII guardrails, a golden-set eval gate in CI, Dockerized CD, and FinOps cost + PSI drift monitoring.*
- *Designed it as composable services with 53 tests and a step-by-step public repo.*

## The mock system-design interview

Practice on your own build — you already know every tradeoff. Walk through these the way an interviewer would probe:

<Callout tone="tip">
**Drill these out loud.**
1. *"Design a system that finds good deals for a user."* — start with requirements and the data, not the model.
2. *"Why hybrid search instead of just embeddings?"* — each retriever's blind spot; RRF needs no tuning.
3. *"How do you know it works — and won't regress?"* — golden set, metrics, the CI eval gate.
4. *"It's too slow / expensive. What do you do?"* — semantic cache, batching, quantization, smaller model that still passes eval.
5. *"A user reports a wrong deal. Walk me through debugging."* — the trace, the audit log, reproduce, add a golden case.
6. *"How does it stay correct after launch?"* — drift detection → orchestrated retrain → eval → canary.
</Callout>

Each question maps to a part you built — so your answer is a story with a repo behind it, not a textbook recital. That's the difference that gets the offer.
