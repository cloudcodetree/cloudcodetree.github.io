## Why MCP, not just an API

The agent in Part 11 called `score_deal` by importing it. That works inside one Python process. MCP turns the same functions outward — into a protocol-level contract that any tool-using model can speak, in any language, over any transport.

The practical consequence: you write the tools once. Claude Code, Claude Desktop, a custom OpenAI-compatible client, a CI evaluation harness — all call the same server without per-client glue. When the tools improve (Part 13 switches `search_deals` from the frozen snapshot to a live pgvector store), every client picks up the change automatically.

## The three MCP primitives

An MCP server exposes exactly three kinds of capability. Each is driven by a different party, and confusing them is the most common MCP design mistake.

<MCPPrimitives />

- **Tools** are model-controlled: the model decides when to call `score_deal` and what arguments to pass. They have side effects (in principle) and must have tight docstrings — that text is the schema the model reads.
- **Resources** are app-controlled: the server decides what is at `dealfinder://catalog/stats`. The model can request the resource but cannot mutate it. Use resources for static or slow-changing data — a catalog summary, a model card, a configuration dump.
- **Prompts** are user-controlled: the user (or calling app) invokes `find_a_deal` with their own arguments. Think of a prompt as a named, parameterized message template — a shortcut for a workflow a human author, not the model, defines.

None of the three is a catch-all. Putting everything in tools is the wrong answer.

## Install and initialize the server

`mcp_server.py` lives in the `dealfinder/` package. It is introduced in `step-12` and does not touch `dealscore.py`, `search.py`, `recommend.py`, or `snapshot.py`.

```bash
pip install "mcp[fastmcp]>=1.0,<2"
```

`FastMCP` initializes with a human-readable server name. `stdio` is the default transport — it works out of the box with Claude Code's subprocess model:

```python
# dealfinder/mcp_server.py
from mcp.server.fastmcp import FastMCP
from .dealscore import fair_price, median_signal, residual_fraction, verdict
from .dealmodel import LinearModel
from .features import feature_matrix, featurize
from .recommend import content_recommend, load_catalog_embeddings
from .search import cosine_rank
from .snapshot import load_snapshot
from .tools import load_catalog

# Build the catalog-backed state once, at import.
_catalog, _emb = load_catalog_embeddings(load_catalog())
_idx = {p.id: i for i, p in enumerate(_catalog)}
_medians = {r["id"]: r["median_price_at_capture"] for r in load_snapshot()}

_by_cat: dict[str, list] = {}
for _p in _catalog:
    _by_cat.setdefault(_p.category, []).append(_p)
_models = {
    c: LinearModel().fit(feature_matrix(ps), [p.price for p in ps])
    for c, ps in _by_cat.items() if len(ps) >= 3
}

def _fair_price(p) -> float:
    model = _models.get(p.category)
    return fair_price(model, featurize(p)) if model else p.price

mcp = FastMCP("dealfinder")
```

The catalog state — 270 products, their cached title embeddings, per-category linear models, and the query medians — is built once at import. All tool calls read from this in-memory snapshot. No live API call is made in this part.

## Register the tools

`@mcp.tool()` makes a decorated function visible to every MCP client. The name, docstring, and type hints become the schema; precision here determines how well the model fills arguments.

```python
@mcp.tool()
def score_deal(product_id: str) -> dict:
    """Price, fair price, median signal, and the two-signal deal verdict."""
    p = _catalog[_idx[product_id]]
    fp = _fair_price(p)
    v = verdict(p.price, _medians.get(product_id, p.price), fp)
    return {
        "id": product_id, "title": p.title, "price": p.price,
        "fair_price": round(fp, 2),
        "median_signal": round(median_signal(p.price, _medians.get(product_id, p.price)), 3),
        "residual_frac": round(residual_fraction(p.price, fp), 3),
        "verdict": v.label,
    }

@mcp.tool()
def recommend(product_id: str, k: int = 3) -> list[dict]:
    """k products similar to the given one (content-based on title embeddings)."""
    recs = content_recommend(_idx[product_id], _emb, k, standardize=False)
    return [{"id": _catalog[j].id, "title": _catalog[j].title,
             "price": _catalog[j].price} for j in recs]

@mcp.tool()
def search_deals(query: str, k: int = 5) -> list[dict]:
    """Semantic search the catalog; returns matches with their deal verdict."""
    from .embed import embed_texts
    qv = embed_texts([query])[0]
    out = []
    for i, _ in cosine_rank(qv, _emb, k):
        p = _catalog[i]
        fp = _fair_price(p)
        out.append({"id": p.id, "title": p.title, "price": p.price,
                    "verdict": verdict(p.price, _medians.get(p.id, p.price), fp).label})
    return out
```

Three tools; same Python functions that the agent in Part 11 called directly. The difference is the decorator — that one line makes them reachable over MCP.

<Callout tone="note">
**The docstring is load-bearing.** The model reads the docstring as the tool description. "Price, fair price, median signal, and the two-signal deal verdict" tells the model exactly what it gets back and why it might call this over `search_deals`. Write it like a contract.
</Callout>

## Prove the tools: score three headphones

Call `score_deal` with the three hero-cast items before wiring any client. Every catalog `id` is a long `rapidapi-catalogid:…` string, so instead of pasting raw ids, look each product up by a title substring — exactly the `_id` helper the real `tests/test_mcp.py` uses:

```python
# quick smoke test — the tool functions are plain callables
from dealfinder import mcp_server

def _id(needle):
    return next(p.id for p in mcp_server._catalog
                if needle.lower() in p.title.lower())

# The anchor: the reference Sony XM5, at the snapshot median
print(mcp_server.score_deal(_id("Sony WH-1000XM5 Wireless Headphones")))
```

```json
{
  "id": "rapidapi-catalogid:14556986932651510680,productid",
  "title": "Sony WH-1000XM5 Wireless Headphones",
  "price": 162.97,
  "fair_price": 285.15,
  "median_signal": 0.0,
  "residual_frac": 0.428,
  "verdict": "fair"
}
```

`median_signal` is exactly 0.0 because this XM5 listing sits at the snapshot median for "noise cancelling headphones" ($162.97). `residual_frac` of 0.428 says the price model's fair estimate ($285.15) is 43% above the list price — genuine value, not a red flag. Verdict: **fair**.

Now the Anker:

```python
print(mcp_server.score_deal(_id("Anker Soundcore Q20i")))
```

```json
{
  "id": "rapidapi-catalogid:4602286582194268609,productid:",
  "title": "Anker Soundcore Q20i Hybrid Active Noise Cancelling Headphones",
  "price": 44.99,
  "fair_price": 108.33,
  "median_signal": 0.724,
  "residual_frac": 0.585,
  "verdict": "deal"
}
```

`median_signal` of 0.724 — 72% below query median. `residual_frac` of 0.585 — the model's fair price for a mid-tier ANC headphone is $108.33, and $44.99 is genuinely cheap without crossing the suspicious line. Both signals agree. Verdict: **deal**.

Now the trap:

```python
print(mcp_server.score_deal(_id("Bose QuietComfort 45")))
```

```json
{
  "id": "rapidapi-catalogid:17549595923884402543,productid",
  "title": "Bose QuietComfort 45 Wireless Noise Cancelling Headphones",
  "price": 46.0,
  "fair_price": 285.15,
  "median_signal": 0.718,
  "residual_frac": 0.839,
  "verdict": "suspicious"
}
```

This is the teaching moment the whole two-signal architecture exists to surface. The Bose QC45 and the Anker Q20i are both listed around $45. Median signal alone would call both a deal. But the Bose is a flagship — the same fair-price tier as the reference Sony XM5 — so its model fair price is also $285.15. `residual_frac` of 0.839 crosses the threshold (≥ 0.70) while `median_signal` of 0.718 is also ≥ 0.70. Both conditions met: verdict **suspicious**.

The Bose QC45 title contains no condition token, so `condition = "new"` (default). The trap is caught by the model residual, not by a parsed refurb flag.

The MCP tool returns the full signal object — both numbers and the verdict — so the client can present all three and let the user decide. A scalar "72% off!" collapses that nuance.

## Add the catalog resource

Resources give clients a way to read static or slow-changing server data without calling a tool. The catalog summary — how many products, how many categories — is a natural resource: it changes only when the snapshot changes, and the model should be able to read it without executing search logic.

```python
@mcp.resource("dealfinder://catalog/stats")
def catalog_stats() -> str:
    """Quick catalog summary over the frozen snapshot."""
    n = len(_catalog)
    cats = len({p.category for p in _catalog})
    avg = sum(p.price for p in _catalog) / n
    return f"{n} electronics listings across {cats} categories; average price ${avg:.0f}"
```

A client reading `dealfinder://catalog/stats` gets:

```
270 electronics listings across 11 categories; average price $299
```

The server controls what is there. The model can request it; it cannot change it. This is the app-controlled boundary: the snapshot determines the numbers, not the calling model.

<Callout tone="note">
**Returning a dict from a resource.** The current `catalog_stats` returns a formatted string. In later versions you can return a structured dict by registering a `ResourceTemplate` — useful when the client needs to parse individual fields. For this part, the string is sufficient.
</Callout>

## Add the prompt template

Prompts are named, parameterized message templates. They let a human (or calling app) invoke a complex workflow through a short, memorable name. The model does not choose when to apply a prompt; the user or client does.

```python
@mcp.prompt()
def find_a_deal(category: str = "noise cancelling headphones") -> str:
    """A starter prompt for finding a good deal."""
    return f"Find the best-value {category} in the catalog and explain why it's a good deal."
```

Invoking `find_a_deal` with `category="noise cancelling headphones"` returns:

```
Find the best-value noise cancelling headphones in the catalog and explain why it's a good deal.
```

The prompt hands the model a workflow — find the best value and justify it — rather than a bare question. The model then reaches for `score_deal` and `search_deals` on its own. A non-technical user can invoke it by name without knowing which tools exist.

## Wire Claude Code with .mcp.json

Add the server to `.mcp.json` at the companion repo root. Claude Code reads this file and starts the server as a subprocess over stdio:

```json
{
  "mcpServers": {
    "dealfinder": {
      "command": "python",
      "args": ["-m", "dealfinder.mcp_server"],
      "cwd": "companions/dealfinder"
    }
  }
}
```

`cwd` must point to the companion root where `dealfinder/` is importable as a package. If Claude Code reports "server failed to start", verify the server starts manually first:

```bash
cd companions/dealfinder
python -m dealfinder.mcp_server
```

If that succeeds, the `.mcp.json` `cwd` is correct. If `import dealfinder` fails, check that `pyproject.toml` lists the package and that the venv is active.

Once wired, `score_deal`, `recommend`, and `search_deals` appear in Claude Code's tool list alongside any other registered MCP servers.

## Run an end-to-end session

After wiring `.mcp.json`, open Claude Code in the companion directory and run the prompt template:

```
User: find_a_deal("noise cancelling headphones")
```

The model self-selects `search_deals` to find candidates under $100, then calls `score_deal` on each. A representative session:

```
[tool: search_deals] query="noise cancelling headphones" k=5
→ returns 5 candidates: Bose QuietComfort ($359.99, overpriced),
  Sony WH-CH720N/P ($129.99, deal), SONY WH-1000XM5 Noise-Canceling
```

## Reproducibility checks

These tests cover the tool functions and the resource directly — no MCP client required. The `_id` helper resolves a title substring to the product's real `rapidapi-catalogid:…` id, so the tests read by name:

```python
# tests/test_mcp.py
from dealfinder import mcp_server


def _id(needle):
    return next(p.id for p in mcp_server._catalog if needle.lower() in p.title.lower())


def test_server_registers_expected_tools():
    names = {t.name for t in mcp_server.mcp._tool_manager.list_tools()}
    assert names == {"score_deal", "recommend", "search_deals"}


def test_score_deal_flags_the_anker_as_a_deal():
    out = mcp_server.score_deal(_id("Anker Soundcore Q20i"))
    assert out["price"] == 44.99
    assert out["verdict"] == "deal"          # the honest hero deal
    assert out["median_signal"] > 0.70


def test_score_deal_flags_the_bose_trap_as_suspicious():
    out = mcp_server.score_deal(_id("Bose QuietComfort 45"))
    assert out["verdict"] == "suspicious"    # median says steal; residual guards it
    assert out["residual_frac"] > 0.70


def test_recommend_returns_similar_real_audio_items():
    recs = mcp_server.recommend(_id("Sony WH-1000XM5 Wireless Headphones"), k=2)
    assert len(recs) == 2
    # the premium Sony sibling XM6 is in the neighbourhood
    assert any("WH-1000XM" in r["title"] for r in recs)


def test_catalog_stats_reflect_the_270_item_snapshot():
    stats = mcp_server.catalog_stats()
    assert "270" in stats and "11 categories" in stats
```

Run:

```bash
pytest tests/test_mcp.py -v
```

The first test pins the registered tool set to exactly `{score_deal, recommend, search_deals}`. The Anker and Bose tests re-assert the two-signal split: the Anker is a genuine `deal`, and the Bose QC45 is `suspicious` because its `residual_frac` crosses the 0.70 threshold — median discount alone would have called it a deal. That threshold is defined in `dealfinder/dealscore.py` and tested in `tests/test_dealscore.py`.
