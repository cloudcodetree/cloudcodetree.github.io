## The four levers, clearly labeled

Every inference-optimization claim you encounter carries an implicit disclaimer: *measured on what hardware, with what model, at what concurrency?* This part treats that disclaimer as a first-class constraint rather than an asterisk.

The four levers are:

| Lever | Requires | Numbers in this part |
|---|---|---|
| Semantic cache threshold | Offline — committed embeddings | **Measured** (real hit rates from `measure_cache_hit_rate`) |
| Model routing / cascade | Offline — injected transport | **Measured** logic (no network) |
| Batching throughput model | Offline — arithmetic | **Illustrative** (modeled overhead, not a device benchmark) |
| Quantization + vLLM | GPU | **Anchored** (concept + script pointers; figures labeled illustrative) |

The `measured` / `illustrative` / `anchored` flags appear on the dataclasses (`CacheReport.measured=True`, `BatchingModel.illustrative=True`, `AnchoredBenchmark.illustrative=True`). They are not decoration — they are the contract between the code and whatever prose or dashboard consumes it.

## Lever 1: Semantic cache — the threshold is the knob

The semantic cache from Part 26 stores embedding vectors and returns a cached answer when a new query is close enough. "Close enough" is entirely determined by the cosine threshold. Changing it by 0.05 changes the hit rate meaningfully.

`measure_cache_hit_rate` runs a deterministic 14-query batch through `SemanticCache`:

```python
# dealfinder/inference.py
from dealfinder.inference import measure_cache_hit_rate

report_095 = measure_cache_hit_rate(0.95)
report_090 = measure_cache_hit_rate(0.90)

print(report_095)
# threshold=0.95  n_queries=14  hits=6  hit_rate=0.429  near_dup_cosine=0.9498  measured=True

print(report_090)
# threshold=0.90  n_queries=14  hits=7  hit_rate=0.500  near_dup_cosine=0.9498  measured=True
```

The batch is constructed from the committed `electronics-2026-07.json` snapshot and its pre-computed 384-dim title embeddings (fastembed `BAAI/bge-small-en-v1.5`, introduced in Part 4). It contains six base queries (one per category, first item), each repeated once as an exact duplicate, plus the two Sony WH-1000XM5 listings as a near-duplicate pair. No model download; no network call.

At threshold 0.95: only the six exact repeats hit. The Sony near-duplicate pair misses. Hit rate: 6/14 = **0.429**.

At threshold 0.90: the same six exact repeats hit, plus the Sony pair crosses the gate. Hit rate: 7/14 = **0.500**.

<CacheThresholdKnob />

The lower threshold is not free: any pair with cosine ≥ 0.90 now returns the cached answer for the first query. If those two queries are genuinely different — same product, different question — the cache serves a wrong answer. The threshold is a precision/recall dial. Set it lower and you serve more queries from cache; set it wrong and you serve stale or mismatched results. There is no universal right answer, but now you have a measured baseline to tune from.

## The XM5 near-duplicate pair

The Sony WH-1000XM5 appears twice in the snapshot: listed at Costco ($162.97) and Macy's ($248). The aggregator collapses cross-source duplicates with a normalized brand+title dedup key. Here the same pair appears as a semantic cache case: their title embeddings sit at cosine **0.9498** — close but not identical, because the title text differs slightly between retailers.

```python
# The governing relationship (from the measured batch):
# 0.90 ≤ 0.9498 < 0.95
# → at threshold 0.95: MISS (0.9498 < 0.95)
# → at threshold 0.90: HIT  (0.9498 ≥ 0.90)
```

That single pair is what moves the hit rate from 6/14 to 7/14. It illustrates why threshold calibration matters more than you might expect: your traffic may carry many near-duplicate queries at exactly this cosine distance. The governing relationship `0.90 ≤ 0.9498 < 0.95` is what makes the pair miss at 0.95 and hit at 0.90.

## Lever 2: Model routing — serve cheapest, escalate on failure

Running every request through the most capable (and most expensive) model is the default only because it is the easiest to implement. `CascadeRouter` flips the priority: try the cheapest tier first, and escalate only when you have to.

```python
# dealfinder/inference.py
class CascadeRouter:
    """Cost/latency-aware cascade over the llm.py model tiers.

    Tries the cheapest tier first and escalates to the next only when the
    current tier fails (raises) or returns a low-confidence answer.
    The per-tier `call` is injected so tests exercise escalation with no
    network (mirrors how test_llm.py mocks the transport).
    """

    def __init__(
        self,
        call: Callable[[str, str], str],
        *,
        tiers: list[str] | None = None,
        confidence: Callable[[str], float] | None = None,
        min_confidence: float = 0.5,
    ) -> None:
        self.call = call
        self.tiers = tiers if tiers is not None else llm_models()
        self.confidence = confidence or (lambda _a: 1.0)
        self.min_confidence = min_confidence

    def route(self, prompt: str) -> RouteResult:
        attempts: list[str] = []
        last_err: str | None = None
        for model in self.tiers:
            attempts.append(model)
            try:
                answer = self.call(model, prompt)
            except Exception as e:            # tier unavailable/throttled → escalate
                last_err = f"{model}: {e}"
                continue
            if self.confidence(answer) >= self.min_confidence:
                return RouteResult(
                    answer=answer, model=model, attempts=attempts,
                    escalated=len(attempts) > 1,
                )
            last_err = f"{model}: low confidence"
        raise RuntimeError(f"all tiers exhausted ({last_err})")
```

The real tier order comes from `llm.models()`:

```python
# default tiers = llm.models():
# ['deepseek/deepseek-chat', 'meta-llama/llama-3.3-70b-instruct:free']
```

Cheap paid model first, free fallback second. The four routing scenarios, tested with an injected transport (no live API key required):

```python
# cheapest tier answers:
#   model=cheap  attempts=['cheap']          escalated=False

# cheap fails (429) →:
#   model=free   attempts=['cheap','free']   escalated=True

# low confidence on cheap →:
#   model=free   attempts=['cheap','free']   escalated=True

# all tiers raise →:
#   RuntimeError: all tiers exhausted (free: down)
```

The `escalated` field is `len(attempts) > 1`. Both the exception path and the low-confidence path produce the same escalation signal — they just arrive there differently.

<CascadeEscalation />

<Callout tone="note">
**Injected transport, not a mock.** `CascadeRouter` accepts a `call: Callable[[str, str], str]` rather than owning the HTTP layer. This mirrors `test_llm.py`'s pattern: you inject a function that raises `Exception("429")` or returns a low-confidence string. No patching, no `unittest.mock`. The routing logic is fully exercised without a live key.
</Callout>

The confidence function is also injected (`confidence: Callable[[str], float] | None`). The default returns 1.0 (always confident), which exercises only the exception escalation path. For the DealFinder extractor you would inject a function that scores the structured output — returning < 0.5 when the JSON is malformed or missing required fields.

## Lever 3: Batching — amortizing call overhead

Every call to an embedding API or a model endpoint carries a fixed per-call overhead — network round-trip, request parsing, batch setup. That overhead is the same whether you send one item or sixty. Batching amortizes it.

`model_batching_throughput` makes this concrete with a simple, honest model:

```python
# dealfinder/inference.py
def model_batching_throughput(
    n_items: int = 64,
    *,
    call_overhead_s: float = 0.02,
    per_item_compute_s: float = 0.001,
) -> BatchingModel:
    """A MODELED per-item-vs-batched comparison — illustrative, not a benchmark.

    Per-item total  = n * (overhead + compute)
    Batched total   = overhead + n * compute   (one call, same compute)
    """
    per_item = n_items * (call_overhead_s + per_item_compute_s)
    batched  = call_overhead_s + n_items * per_item_compute_s
    return BatchingModel(
        n_items=n_items,
        per_item_seconds=round(per_item, 4),
        batched_seconds=round(batched, 4),
        speedup=round(per_item / batched, 2),
        illustrative=True,
    )
```

With the default parameters (n=64, overhead=0.02s, compute=0.001s):

```
n_items=64  per_item_s=1.344  batched_s=0.084  speedup=16.0  illustrative=True
```

`illustrative=True` is not a caveat — it is the type signature. The constants (0.02s overhead, 0.001s per-item compute) are assumed, not measured on a specific device. The lesson is the shape: batching is beneficial whenever `call_overhead_s` dominates `per_item_compute_s`, which it does for most API-backed embedding and LLM calls. The exact speedup depends on your hardware, your endpoint, and your batch size ceiling.

<Callout tone="warn">
**Do not quote the 16x speedup as a benchmark.** It is a model output from fixed assumed constants. On a slow network the real overhead might be 200ms (making batching even more valuable); on a local model server it might be 2ms (reducing the gain). Run `model_batching_throughput` with your actual measured constants to get a number that reflects your setup.
</Callout>

The implication for DealFinder is immediate: when the recommendation endpoint scores a page of 20 results, batch all 20 embedding lookups into one call instead of 20. The semantic cache (Part 26) also benefits — a batch lookup against the cache vector store is one FAISS scan, not 20.

## Lever 4: Quantization and vLLM — anchored, requires a GPU

Quantization (INT8/INT4) and vLLM's continuous batching are real, significant techniques. They also require a GPU to benchmark honestly. `quantization_reference` and `vllm_reference` return structured references — concept, illustrative expectation figures, and a pointer to a runnable script — rather than pretending to have measured what they have not.

First, *what quantization does to the weights* — because the VRAM numbers below only make sense once you see the mechanism:

<Quantization />

```python
from dealfinder.inference import quantization_reference, vllm_reference

q = quantization_reference()
print(q.name)           # "quantization (INT8 / INT4)"
print(q.illustrative)   # True
print(q.illustrative_numbers)
# {
#   'fp16_vram_gb': 16.0,
#   'int8_vram_gb': 8.0,
#   'int4_vram_gb': 4.0,
#   'note': 'figures illustrate the ~4x VRAM reduction shape, not a benchmark'
# }
print(q.runnable_script)  # 'scripts/bench_quantization.py'

v = vllm_reference()
print(v.name)             # "vLLM (continuous batching + PagedAttention)"
print(v.illustrative_numbers)
# {
#   'baseline_tokens_per_s': 900,
#   'vllm_tokens_per_s': 3200,
#   'note': 'shape only (concurrency win); measure on your own GPU'
# }
print(v.runnable_script)  # 'scripts/bench_vllm.py'
```

**What the illustrative figures mean.** The 16/8/4 GB figures show the shape of INT8/INT4 quantization: each step roughly halves VRAM footprint. 4-bit weights run in roughly a quarter of the FP16 VRAM. The quality impact — perplexity increase, task-specific accuracy drop — is model-specific and must be measured, not assumed. For DealFinder's extractor (which produces structured JSON from product titles) INT8 typically preserves output quality; INT4 can introduce formatting errors that the output validation in Part 25 will catch.

Before the vLLM figures, one more mechanism — because "PagedAttention manages the KV cache" is meaningless until you know *what the KV cache is and why it eats GPU memory*:

<KVCache />

**What vLLM actually does.** Continuous batching packs requests together dynamically instead of waiting for one to finish before starting the next. PagedAttention manages the KV cache as virtual memory pages, avoiding fragmentation. Together they raise throughput under concurrency — the 900→3200 tokens/s illustrative figures show the shape of that gain. The actual ratio depends on your GPU, your model, your batch size, and your concurrency level. `scripts/bench_vllm.py` runs the comparison on your hardware.

<Callout tone="note">
**`scripts/bench_quantization.py` and `scripts/bench_vllm.py` refuse to print numbers on CPU.** They are designed to fail fast and informatively rather than produce CPU-timed results that would be misread as GPU benchmarks. If you run them on a machine without a CUDA device, they exit with an explicit message. This is the right behavior.
</Callout>

## Two levers the field added while this course was being written

The four levers above are the durable ones. Two more have gone from research to one-flag defaults recently — both worth knowing by name, both in the same "pay less for the same tokens" family:

**Prompt caching.** Every DealFinder LLM call — extraction, the agent loop, the RAG answerer — resends the same system prompt and tool schemas. Anthropic's `cache_control` marks that stable prefix once and bills cache reads at a fraction of input price (up to ~90% off the repeated prefix); the semantic cache from Lever 1 sits *above* this (skip the call entirely), prompt caching sits *below* it (make the unavoidable calls cheaper). vLLM ships the self-hosted twin: **automatic prefix caching** (`--enable-prefix-caching`) reuses the KV cache (Part 27's own diagram!) across requests that share a prefix — reported ~2.5× throughput on repetitive traffic with zero code changes.

**Speculative decoding.** A small draft model proposes several tokens; the big model verifies them in one forward pass — accepted tokens cost one pass instead of several. Same output distribution, up to ~2.8× faster generation. It's a serving-config flag in vLLM/SGLang, not an application change, which is exactly why it belongs in your mental model of "things the serving layer can do for free."

Neither changes DealFinder's code — they change what you tick when you deploy Parts 26–29. The lesson is the pattern: inference cost falls fastest at the layers *below* your application.

## The full inference report

`run_inference_report` assembles everything into one call:

```python
from dealfinder.inference import run_inference_report

report = run_inference_report()

print(report.cache_at_095)
# threshold=0.95  n_queries=14  hits=6  hit_rate=0.429  near_dup_cosine=0.9498  measured=True

print(report.cache_at_090)
# threshold=0.90  n_queries=14  hits=7  hit_rate=0.500  near_dup_cosine=0.9498  measured=True

print(report.batching)
# n_items=64  per_item_s=1.344  batched_s=0.084  speedup=16.0  illustrative=True

for ref in report.anchored:
    print(ref.name, '→ illustrative:', ref.illustrative, '· script:', ref.runnable_script)
# quantization (INT8 / INT4)                   → illustrative: True · script: scripts/bench_quantization.py
# vLLM (continuous batching + PagedAttention)  → illustrative: True · script: scripts/bench_vllm.py
```

The `measured=True` fields (`cache_at_095`, `cache_at_090`) are real outputs computed from the committed snapshot. The `illustrative=True` fields (`batching`, `anchored`) carry assumed constants or require hardware you may not have. Nothing in `run_inference_report` requires a network call, a GPU, or any environment variable.
