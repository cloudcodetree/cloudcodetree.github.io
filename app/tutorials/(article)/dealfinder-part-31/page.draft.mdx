## Why SSE beats polling for search UX

The DealFinder backend aggregates across multiple live sources. Each source has its own latency: one source may respond in 340 ms while another takes 890 ms. If the frontend waits for all sources before rendering anything, the user sees a blank screen for the duration of the slowest source.

Server-Sent Events (SSE) solve this. The backend keeps the HTTP connection open and writes frames as each source finishes. The frontend renders each batch immediately. The user sees the first card at ~340 ms even though the full result set isn't ready until ~920 ms.

<SSEStream />

The total wall-clock time is the same either way. SSE halves *perceived* latency — which is what matters for a search product.

## The Vite dev proxy: same-origin SSE without CORS

`EventSource` follows the browser's same-origin policy. If your SPA is on `localhost:5173` and your FastAPI is on `localhost:8000`, an `EventSource` to `http://localhost:8000/search/stream` is cross-origin — the browser will block it unless the backend sends the right CORS headers for streaming responses, which is fiddly to get right.

The Vite dev proxy is the simpler solution. `vite.config.ts` forwards three path prefixes to the FastAPI backend:

```typescript
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

const API_TARGET = process.env.VITE_API_PROXY_TARGET || "http://localhost:8000";

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      "/search": { target: API_TARGET, changeOrigin: true },
      "/me":     { target: API_TARGET, changeOrigin: true },
      "/healthz":{ target: API_TARGET, changeOrigin: true },
    },
  },
});
```

From the browser's perspective, every fetch and every `EventSource` goes to `localhost:5173` — same origin, no CORS. The proxy rewrites the request and forwards it. The SPA code uses bare paths (`/search/stream?q=…`) with no hardcoded port.

In production, the SPA is a static bundle served from a CDN. Set `VITE_API_BASE=https://api.your-domain.com` — the API base is prepended to each request path in `api.ts` and the proxy is not involved. The Kubernetes ingress annotations from Part 29 (`proxy-buffering: off`, `proxy-read-timeout: 3600`) keep SSE alive through the load balancer.

## SSE frame shapes from the backend

Before reading the hook code, understand exactly what the backend sends. `serve.py` emits three frame types:

**`event: results`** — one frame per responding source, carrying a batch of raw offers:

```
event: results
data: {"source": "google_shopping", "results": [{"id": "...", "title": "...", "price": 162.97, "source": "..."}]}
```

Note what the stream rows carry and what they omit. Each item has `id`, `title`, `price`, `source` — enough to render a card immediately. They do **not** carry `deal_pct`, `brand`, `url`, or `image_url`. Those fields are on the plain `/search` JSON response but are omitted from the stream to keep frames small. The hook backfills `deal_pct` from the median once the `done` frame arrives.

**`event: done`** — one terminal frame after all sources finish:

```
event: done
data: {"query": "noise cancelling headphones", "count": 20, "median_price": 162.97}
```

The `median_price` here is the pinned snapshot value for the "noise cancelling headphones" query: **$162.97**. Once this frame arrives, the hook can compute `deal_pct` for every result row.

**`event: source_error`** — emitted when one source fails; the stream continues:

```
event: source_error
data: {"source": "flaky_source"}
```

The hook ignores this event type — the stream is still live, other sources continue.

## The useSearch hook — a state machine

`src/api.ts` exports `useSearch`, which manages all search state in one place. Think of it as a five-state machine:

```
idle  →  loading (SSE)  →  streaming  →  done
              ↓
         onerror (before done) → fetch fallback → done
```

<SearchStateMachine />

The hook's `SearchState` shape:

```typescript
export interface SearchState {
  results: Result[];
  done: SearchDone | null;
  loading: boolean;
  error: string | null;
  transport: "sse" | "fetch" | null;
}
```

`transport` tracks which path is active so the UI can show "(fell back to /search)" if the stream errored. The `Result` type mirrors the stream row shape:

```typescript
export interface Result {
  id: string;
  title: string;
  price: number;
  source: string;
  deal_pct?: number;   // absent until the done frame arrives
}
```

The core of the hook:

```typescript
export function useSearch() {
  const [state, setState] = useState<SearchState>(EMPTY);
  const esRef = useRef<EventSource | null>(null);
  const doneRef = useRef(false);

  const search = useCallback((query: string) => {
    const q = query.trim();
    if (!q) return;
    close();
    doneRef.current = false;
    setState({ ...EMPTY, loading: true, transport: "sse" });

    if (typeof EventSource === "undefined") {
      setState((s) => ({ ...s, transport: "fetch" }));
      void fallbackFetch(q);
      return;
    }

    const es = new EventSource(`${API_BASE}/search/stream?q=${encodeURIComponent(q)}`);
    esRef.current = es;

    es.addEventListener("results", (ev) => {
      const payload = JSON.parse((ev as MessageEvent).data) as { results: Result[] };
      setState((s) => {
        const seen = new Set(s.results.map((r) => r.id));
        const merged = [...s.results];
        for (const r of payload.results ?? []) {
          if (!seen.has(r.id)) merged.push(r);
        }
        return { ...s, results: merged };
      });
    });

    es.addEventListener("done", (ev) => {
      doneRef.current = true;
      const done = JSON.parse((ev as MessageEvent).data) as SearchDone;
      setState((s) => ({
        ...s,
        results: [...s.results]
          .map((r) => ({
            ...r,
            deal_pct: r.deal_pct ?? dealPctFromMedian(r.price, done.median_price),
          }))
          .sort((a, b) => a.price - b.price),
        done,
        loading: false,
        transport: "sse",
      }));
      close();
    });

    es.onerror = () => {
      close();
      if (!doneRef.current) {
        setState((s) => ({ ...s, transport: "fetch" }));
        void fallbackFetch(q);
      }
    };
  }, [close, fallbackFetch]);

  return { ...state, search, reset };
}
```

Three design decisions are worth noting:

**Dedup by id before merging.** Each `results` frame may carry items from a different source. The hook maintains a `Set` of seen ids and skips duplicates. The backend's `dedup_key` function (Part 1) already collapses same-product listings before they reach the stream, but the hook defends itself independently.

**`deal_pct` is backfilled, not streamed.** Stream rows omit it to keep frames small. The `dealPctFromMedian` function computes it locally: `(median - price) / median * 100`, rounded to one decimal. After the `done` frame, every result row gets its `deal_pct`, the array is re-sorted cheapest-first, and React re-renders all cards at once with their badges.

**`doneRef` guards the error handler.** If `EventSource` fires `onerror` *after* a `done` frame — which can happen when the server closes the connection normally — `doneRef.current` is already true and the hook does not trigger the fallback. The fallback only fires on a genuine failure before completion.

## DealBadge: four tokens, no synonyms

`src/components/DealBadge.tsx` maps `deal_pct` to one of the four badge tokens defined in §9.7 of the course bible. The mapping is threshold-based:

```typescript
export type Badge = "DEAL" | "FAIR" | "SUSPICIOUS" | "OVERPRICED";

export function badgeFor(dealPct: number | undefined): Badge {
  const p = dealPct ?? 0;
  if (p >= 60) return "SUSPICIOUS";  // too-good-to-be-true
  if (p >= 10) return "DEAL";        // meaningfully under market
  if (p > -10) return "FAIR";        // near the median
  return "OVERPRICED";
}
```

The thresholds carry the residual reasoning from Part 3. `deal_pct >= 60` maps to `SUSPICIOUS` rather than `DEAL` because the $46 Bose QuietComfort 45 — a flagship headphone with a median fair price of $285.15 — lands at 71.8% below the query median. Without the model residual (Part 3), a naive threshold would mark it `DEAL`. With the threshold set at 60%, it is already `SUSPICIOUS` on the median signal alone, before the model even runs.

```typescript
const STYLES: Record<Badge, { bg: string; fg: string }> = {
  DEAL:       { bg: "#16a34a", fg: "#ffffff" },
  FAIR:       { bg: "#e5e7eb", fg: "#111827" },
  SUSPICIOUS: { bg: "#f59e0b", fg: "#111827" },
  OVERPRICED: { bg: "#6b7280", fg: "#ffffff" },
};

export function DealBadge({ dealPct }: { dealPct?: number }) {
  const badge = badgeFor(dealPct);
  const s = STYLES[badge];
  return (
    <span
      data-badge={badge}
      style={{ /* pill styling */ background: s.bg, color: s.fg }}
    >
      {badge}
    </span>
  );
}
```

The `data-badge` attribute is the Playwright selector hook. Part 36's end-to-end tests locate badges with `page.locator('[data-badge="SUSPICIOUS"]')` — the attribute value is one of the four exact tokens above, never a synonym or variant spelling.

<Callout tone="warn">
**Badge token discipline.** The four tokens are `DEAL`, `FAIR`, `SUSPICIOUS`, and `OVERPRICED` — all caps, exact spelling, no others. "Genuine deal", "Verify condition", "no Deal badge", "WARNING" are all wrong and will break Playwright selectors in Part 36. If you add a badge variant in a fork, update the `Badge` type, the `STYLES` map, and the test fixtures together.
</Callout>

## Worked example: noise cancelling headphones

With both the backend and frontend running (`python serve.py` + `npm run dev` in `frontend/`), search for "noise cancelling headphones". The stream carries the hero cast from the snapshot.

The `done` frame for this query carries `median_price: 162.97` — the pinned snapshot median for the "noise cancelling headphones" query. After backfill:

| Title | Price | deal_pct | badge |
|---|---|---|---|
| Sony WH-1000XM5 (Costco) | $162.97 | 0.0% | **FAIR** |
| Anker Soundcore Q20i | $44.99 | 72.4% | **SUSPICIOUS** (≥60%) |
| Bose QuietComfort 45 | $46.00 | 71.8% | **SUSPICIOUS** (≥60%) |
| Sony WH-1000XM6 | $399.99 | −145.4% | **OVERPRICED** |

<Callout tone="note">
**Why are both Anker and Bose marked SUSPICIOUS?** The `deal_pct` threshold at 60% is a conservative heuristic — anything that far below the query median is unusual enough to warrant a second look. The Anker Q20i is a genuine budget deal that happens to cross that threshold. The full two-signal deal score from Part 3 (combining the median signal with the model residual) separates them: Anker's residual fraction is +0.585 (below model fair price of $108.33), while Bose's is +0.839 (below model fair price of $285.15). A UI that surfaces the model score would show Anker as `DEAL` and Bose as `SUSPICIOUS`. The badge in this part is median-only — Part 3 is where the two-signal separation happens.
</Callout>

The result array is sorted cheapest-first after backfill. The Sony WH-1000XM5 at $162.97 appears once — the backend's `_stream_search` deduplication (using `dedup_key`) already collapsed the $248 Macy's listing, keeping only the cheaper Costco price (Part 1 established this dedup pattern).

<Callout tone="note">
**Anchored, not live.** Running the SPA without real source API keys (`RAPIDAPI_KEY`, `APIFY_TOKEN`, etc.) returns no results — the backend's live sources return empty and the `done` frame carries `count: 0`. The median and badge logic still works correctly in the SSE tests because those tests use a stub source that returns real snapshot items. Never present a mocked/stub result as if it came from a live API call.
</Callout>

## Supabase Auth and the /me route

`src/lib/supabase.ts` creates the Supabase client from two env vars:

```typescript
const url     = import.meta.env.VITE_SUPABASE_URL;
const anonKey = import.meta.env.VITE_SUPABASE_ANON_KEY;

export const supabaseConfigured = Boolean(url && anonKey);

export const supabase: SupabaseClient | null = supabaseConfigured
  ? createClient(url as string, anonKey as string)
  : null;
```

When either var is absent, `supabase` is `null`. The `Auth` component checks `supabaseConfigured` and renders an explanatory panel ("Auth is off. Set VITE_SUPABASE_URL …") instead of the sign-in form. Public search (`useSearch`) has no dependency on Supabase — it works whether auth is on or off.

The sign-in flow:

1. User submits email + password to `supabase.auth.signInWithPassword`.
2. Supabase returns a session. The session's `access_token` is a JWT signed with your project's `SUPABASE_JWT_SECRET`.
3. The `Auth` component calls `fetchMe(session.access_token)` — a `GET /me` with `Authorization: Bearer <token>`.
4. The FastAPI backend's `require_user` dependency (defined in `dealfinder/auth.py`, mounted on `GET /me` in `serve.py`) verifies the JWT locally using `SUPABASE_JWT_SECRET`, extracts the `sub` claim as the user id, and reads the role from `app_metadata.plan` or `app_metadata.role` (Part 32 covers the full claim resolution chain).
5. `/me` returns `{ id, email, role }`. The component gates the "pro features unlocked" affordance on `me.role === "pro"`.

This lives in Part 31's code but the backend auth module (`dealfinder/auth.py`) is the Part 32 topic. The `frontend/` code is deliberately thin on the auth side — it signs in, holds the session token, and passes it to the backend. The backend does all JWT verification.

<Callout tone="tip">
**To try auth locally:** create a free Supabase project, copy the project URL and anon key to `frontend/.env.local` as `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, set `SUPABASE_JWT_SECRET` in the backend's `.env`, and create a test user in the Supabase dashboard. Promote them to "pro" by setting `app_metadata: { plan: "pro" }` via the Supabase admin API or dashboard.
</Callout>

## What the SSE tests prove

`tests/test_sse.py` contains two tests that verify the backend SSE endpoint. Both tests run entirely offline using `_StubSource`, which returns two `Product` instances from the snapshot, and monkey-patch `LIVE_SOURCES`.

**`test_stream_emits_data_events_and_done`** asserts:
- Response status is 200.
- `content-type` header starts with `text/event-stream`.
- The response body contains `event: results` and `event: done`.
- There are at least 2 `data:` frames.
- The body contains the hero anchor: `Sony WH-1000XM5` and `162.97`.

**`test_stream_still_terminates_when_no_sources`** asserts:
- When `LIVE_SOURCES` is monkeypatched to an empty list, the stream still closes with `event: done` and `"count": 0`.

These tests do not exercise the frontend React code — that is the domain of Playwright end-to-end tests in Part 36. What they prove is that the backend contract the frontend depends on is stable: frames arrive in the right format, the terminal `done` frame always fires (the hook's `doneRef` guard requires this), and the hero cast values are present.

Run them:

```bash
# From the companion root (requires .venv activated)
python -m pytest tests/test_sse.py -v
```

