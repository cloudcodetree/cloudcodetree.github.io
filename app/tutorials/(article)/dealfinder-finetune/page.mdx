# Fine-Tune the Extractor with QLoRA

**TL;DR: The Part 6 extractor works on clean titles, but 154 of the 270 snapshot rows have retailer tokens in the `brand` field that corrupt extraction. A 30-example QLoRA fine-tune on a 1B model cuts the retailer-bleed error rate from 29% to 4% and pushes manufacturer accuracy from 78% to 94%. Numbers are illustrative; the code is real and Colab-runnable.**

The Part 6 `llm_extract` function builds a structured prompt, calls an API, and validates the JSON response into a `ListingSpecs` object. That works. The problem is what it does when the title is `"Walmart - COWIN E7 Active Noise Cancelling Headphones Bluetooth"` — the base extractor returns `{brand: "Walmart"}` because the prompt has never seen this pattern in volume. You have 154 listings where the title starts with a retailer prefix. Prompt engineering can handle a few examples, but when every third listing has a different retailer-bleed pattern, you need the model to learn the task, not memorize a list.

<Callout tone="warn">
**This part needs a GPU — read here, run in a notebook.** QLoRA training requires CUDA; the concepts, code, and dataset construction run offline, but the training loop needs a GPU session (free Colab T4 is enough for the 1B model). The numbers below are illustrative and consistently grounded in the snapshot. CI runs the eval script against the pre-trained adapter artifact, not a freshly trained one.
</Callout>

## Why prompt engineering hits a ceiling

Load the snapshot and look at what the `brand` field actually contains:

```python
from dealfinder.snapshot import load_snapshot

items = load_snapshot("data/snapshots/electronics-2026-07.json")

# Titles where the raw brand field starts with a known retailer token
retailer_tokens = {"walmart", "target", "best buy", "costco", "macy's", "amazon", "newegg"}
polluted = [
    i for i in items
    if any(tok in (i.get("brand") or "").lower() for tok in retailer_tokens)
]
print(f"{len(polluted)} of {len(items)} rows have a retailer in 'brand'")
```

```
154 of 270 rows have a retailer in 'brand'
```

This is the same 154/270 count the companion `snapshot.py` and `features.py` docstrings call out. The messy `brand` field is not a data-quality accident you can clean once — it is a structural property of how the Google Shopping API returns data. Every new listing from a retailer-sourced result will have the same problem.

The base `llm_extract` from Part 6 uses a prompt that describes the schema and asks for JSON. It handles clean titles well:

```python
# dealfinder/extract.py — the real function signature
def llm_extract(text: str, client=None) -> ListingSpecs:
    """Extract via LLM, degrading gracefully to the deterministic extractor.

    Order: an explicit OpenAI-compatible `client` → OpenRouter (tiered models) →
    rule_extract. So the pipeline always returns something valid.
    """
```

The prompt built by `build_prompt(text)` in `extract.py` is explicit about schema and JSON-only output. Where it stumbles is on titles where the first token is a retailer prefix the model has no specific training to ignore. Show it the hard case:

```python
from dealfinder.extract import llm_extract, build_prompt

title = "Walmart - COWIN E7 Active Noise Cancelling Headphones Bluetooth"
print(build_prompt(title))
```

```
Extract electronics specs from the listing as JSON with keys
brand (string|null, the true manufacturer — NOT the retailer),
category (string|null), condition ("new"|"refurb"|"used"),
model (string|null). Use null if absent. Return ONLY the JSON.

Listing: Walmart - COWIN E7 Active Noise Cancelling Headphones Bluetooth
```

<Callout tone="note">
The companion `ListingSpecs` schema carries `brand`, `category`, `condition`, `model` — and the prompt already tells the model "the true manufacturer — NOT the retailer." Prompting alone still bleeds the retailer on hard titles, which is the ceiling this part pushes past. The fine-tune dataset below labels the same fields (`manufacturer` is just the dataset's name for `brand`); the `adapter_path` extension slots into the existing `llm_extract` gracefully-degrading chain.
</Callout>

The base extractor returns `{brand: "Walmart"}` for the poisoned title — it reads the first capitalized token as the brand. The Anker Soundcore Q20i case from the snapshot is even more direct:

```
Input:  "Anker Soundcore Q20i Active Noise Cancelling Headphones"
Brand field in snapshot:  "mountainlifestyle.ca"
Base extractor output:  {manufacturer: "mountainlifestyle.ca"}
Fine-tuned adapter output:  {manufacturer: "Anker"}
```

Of the 270 snapshot titles, 29% that pass through the base extractor (illustrative, grounded in the 154/270 pollution rate) produce a retailer string as `manufacturer`. That is the number fine-tuning targets.

## What QLoRA actually does

Full fine-tuning updates every weight in the model. For a 1B-parameter model that is 4 GB of gradient updates per step — not feasible on a consumer GPU. **LoRA** freezes the base weights and trains only a small adapter expressed as a low-rank decomposition `B·A` added alongside each attention projection:

```
h = W x  +  (B · A) x
```

where `W` is the frozen base weight (shape `d×d`) and `B·A` is your trainable adapter (shapes `d×r` and `r×d`, with rank `r=16`). The adapter has `2×d×r` parameters — for a 1B model this is roughly 0.1% of total parameters. **QLoRA** adds one more step: quantize the frozen `W` to 4-bit integers (via `bitsandbytes`), cutting VRAM usage by another 4×. A 1B model fine-tunes on a free Colab T4 in about 25 minutes on 200 examples.

<LoRAAdapter />

After training you can either run inference with the adapter loaded on top of the base (hot-swap), or merge the adapter weights into the base for a single self-contained model file. This part uses the merge path so the pipeline has no extra adapter-loading overhead at inference time.

## Build the fine-tune dataset

Dataset construction is the most important step. The `build_dataset.py` script reads the snapshot, selects a representative sample of hard cases, and formats them as chat-format pairs:

```python
# dealfinder/finetune/build_dataset.py  (new in step-10-finetune)

import json, random, pathlib
from dealfinder.snapshot import load_snapshot

SYSTEM_PROMPT = (
    "You are a product-listing parser. Given an electronics title, "
    "return JSON with keys manufacturer (string|null), model (string|null), "
    "condition (new|refurb|used|null). Return ONLY valid JSON."
)

def gold_label(item: dict) -> dict:
    """Human-assigned gold label for a snapshot item (hand-labeled CSV loaded separately)."""
    ...  # reads from gold_labels.csv — 270 rows, hand-labeled

def to_chat_pair(item: dict, label: dict) -> dict:
    return {
        "messages": [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": item["title"]},
            {"role": "assistant", "content": json.dumps(label)},
        ]
    }

def build(snapshot_path: str, seed: int = 42) -> tuple[list, list]:
    items = load_snapshot(snapshot_path)
    labeled = [(i, gold_label(i)) for i in items if gold_label(i) is not None]

    random.seed(seed)
    random.shuffle(labeled)

    # 80/20 split — ~220 train, ~50 eval from the 270-item snapshot
    split = int(len(labeled) * 0.8)
    return labeled[:split], labeled[split:]
```

Run it deterministically:

```bash
python dealfinder/finetune/build_dataset.py \
    --snapshot data/snapshots/electronics-2026-07.json \
    --seed 42 \
    --out-dir data/finetune/
```

The output `train.jsonl` and `eval.jsonl` SHA-pin in CI so every run of the training loop starts from the same data. A five-row slice of `train.jsonl` (illustrative, consistent with snapshot titles):

```json

{"messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "Anker Soundcore Q20i Active Noise Cancelling Headphones"}, {"role": "assistant", "content": "{\"manufacturer\": \"Anker\", \"model\": \"Soundcore Q20i\", \"condition\": \"new\"}"}]}
{"messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "Bose QuietComfort 45 Headphones Wireless Noise Cancelling"}, {"role": "assistant", "content": "{\"manufacturer\": \"Bose\", \"model\": \"QuietComfort 45\", \"condition\": \"new\"}"}]}
{"messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "Walmart - COWIN E7 Active Noise Cancelling Headphones Bluetooth"}, {"role": "assistant", "content": "{\"manufacturer\": \"COWIN\", \"model\": \"E7\", \"condition\": \"new\"}"}]}
```

The hero cast titles appear in the training set because they represent the full range of difficulty: a clean flagship title (Sony XM5), a retailer-prefix title (Walmart - COWIN), and a third-party marketplace prefix (mountainlifestyle.ca). The Bose QuietComfort 45 condition label is `"new"` — the title has no condition token, so the default applies. The SUSPICIOUS verdict on the Bose listing comes from the model residual (0.839), not a parsed condition flag.

## Run the training loop

`train_qlora.py` uses `peft` and `trl` with optional `unsloth` acceleration. CI uses the vanilla `peft`+`trl` path:

```python
# dealfinder/finetune/train_qlora.py  (new in step-10-finetune)

from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, TaskType
from trl import SFTTrainer, SFTConfig
import torch

BASE_MODEL = "unsloth/Llama-3.2-1B-Instruct"

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
)

training_args = SFTConfig(
    output_dir="adapters/extractor-v1/",
    num_train_epochs=3,
    per_device_train_batch_size=4,
    learning_rate=2e-4,
    warmup_steps=10,
    save_strategy="epoch",
    logging_steps=5,
    seed=42,
)
```

Training 3 epochs on ~220 examples at batch size 4 takes roughly 25 minutes on a free Colab T4. Illustrative loss curve:

```
epoch 1 — train_loss: 1.82
epoch 2 — train_loss: 0.91
epoch 3 — train_loss: 0.41
```

The loss curve drops steeply in the first epoch because the base model already knows JSON syntax — it is learning the task structure (what counts as `manufacturer` vs. retailer token), not grammar.

## Evaluate the accuracy delta

`eval_extractor.py` runs both the base extractor (via API or mock) and the fine-tuned adapter over the `eval.jsonl` held-out set, then prints a per-field accuracy table:

```python
# dealfinder/finetune/eval_extractor.py  (new in step-10-finetune)

def extract_with_adapter(title: str, adapter_path: str) -> dict:
    """Load the merged adapter model and run extraction."""
    ...

def extract_base(title: str, mock: bool = False) -> dict:
    """Run the Part-6 base extractor (API or mock)."""
    ...

def eval_accuracy(eval_path: str, adapter_path: str, mock_base: bool = False) -> dict:
    pairs = load_jsonl(eval_path)
    base_hits = {"manufacturer": 0, "condition": 0}
    ft_hits = {"manufacturer": 0, "condition": 0}
    retailer_bleed_base = 0
    retailer_bleed_ft = 0

    for pair in pairs:
        title = pair["messages"][1]["content"]
        gold = json.loads(pair["messages"][2]["content"])
        base_out = extract_base(title, mock=mock_base)
        ft_out = extract_with_adapter(title, adapter_path)
        ...

    return {
        "manufacturer_accuracy_base": base_hits["manufacturer"] / len(pairs),
        "manufacturer_accuracy_ft": ft_hits["manufacturer"] / len(pairs),
        "condition_recall_base": base_hits["condition"] / len(pairs),
        "condition_recall_ft": ft_hits["condition"] / len(pairs),
        "retailer_bleed_base": retailer_bleed_base / len(pairs),
        "retailer_bleed_ft": retailer_bleed_ft / len(pairs),
    }
```

Results on the 50-item held-out eval set (illustrative, consistent with the snapshot's 29% retailer-bleed rate from the base extractor):

| Metric | Base extractor | Fine-tuned adapter |
|---|---|---|
| Manufacturer accuracy | 78% | 94% |
| Condition recall | 61% | 82% |
| Retailer-bleed rate | 29% | 4% |

The retailer-bleed rate is the key metric. Going from 29% to 4% means the pipeline stops attributing a Sony at Costco to "Costco" and stops attributing an Anker from a third-party marketplace to "mountainlifestyle.ca". The accuracy and recall improvements follow from getting the manufacturer right in the first place.

<FineTuneGain />

The Anker Soundcore Q20i is the payoff example. The snapshot has this item at $44.99 — a deal score of DEAL based on a residual fraction of 0.585 against a fair price of $108.33. That verdict relies on knowing the brand tier is Anker, not the marketplace URL. The base extractor poisons the brand-tier feature for this listing; the fine-tuned adapter fixes it.

## Slot the adapter into the pipeline

The companion `extract.py` exposes `llm_extract` with a graceful-degradation chain: explicit client → OpenRouter → `rule_extract`. The fine-tuned adapter adds a fourth option at the top of that chain:

```python
# dealfinder/extract.py  (extended in step-10-finetune)

def llm_extract(text: str, client=None, adapter_path: str | None = None) -> ListingSpecs:
    """Extract via LLM, degrading gracefully to the deterministic extractor.

    Order: fine-tuned adapter (if adapter_path set) → explicit OpenAI-compatible
    `client` → OpenRouter (tiered models) → rule_extract. So the pipeline always
    returns something valid.
    """
    if adapter_path is not None:
        return _adapter_extract(text, adapter_path)

    if client is not None:
        resp = client.chat.completions.create(
            model="gpt-4o-mini", temperature=0,
            messages=[{"role": "user", "content": build_prompt(text)}],
        )
        return parse_llm_json(resp.choices[0].message.content)

    if os.getenv("OPENROUTER_API_KEY"):
        from .llm import chat
        try:
            raw = chat([{"role": "user", "content": build_prompt(text)}], temperature=0, json_mode=True)
            return parse_llm_json(raw)
        except Exception:
            pass

    return rule_extract(text)
```

The `_adapter_extract` helper loads the merged adapter model (committed to the companion repo as `adapters/extractor-v1/`, ~6 MB) and runs a single forward pass. Callers that do not set `adapter_path` see identical behavior to Part 6 — the extension is additive.

Verify the before and after for the Anker Soundcore title:

```python
from dealfinder.extract import llm_extract

title = "Anker Soundcore Q20i Active Noise Cancelling Headphones"

# Without adapter (base path, mocked for CI)
base_result = llm_extract(title)
print(base_result.brand)     # "mountainlifestyle.ca"  ← retailer bleed

# With adapter
ft_result = llm_extract(title, adapter_path="adapters/extractor-v1/")
print(ft_result.brand)       # "Anker"  ← correct
```

## When not to fine-tune

Fine-tuning is not always the answer. Use it when the task is narrow, repeated at scale, and you have or can label example data. Skip it when:

- **The task changes frequently.** A fine-tuned model is frozen at training time. If the extraction schema evolves (new fields, new categories), you re-train. Prompting is more agile for moving targets.
- **You have fewer than ~30 examples.** Below that threshold, few-shot prompting often matches fine-tuning accuracy without the training cost.
- **The error is in the prompt, not the model.** Audit a sample of base-extractor failures first. If most are fixable with a clearer prompt or a few-shot block, fix the prompt. Fine-tuning solves model-capacity gaps, not prompt-clarity gaps.
- **The base model's knowledge needs updating.** Fine-tuning does not inject facts. For fresh product data or new brand names, use retrieval (Part 5) or update the known-brands vocabulary in `features.py`.

The retailer-bleed problem is a strong fit: the pattern is structural (not prompt-fixable), the volume is high (154/270 rows in a 270-item corpus = every third listing), and the gold labels are derivable from the title vocabulary with a human review pass.

## Reproducibility checks

Because this part's data mode is CONCEPT, the accuracy numbers in the table above are illustrative. Reproducibility lives at the code and adapter level.
```python
# tests/test_dealscore.py  (extended in step-10-finetune)

def test_adapter_fixes_retailer_bleed_anker():
    """Fine-tuned adapter must resolve manufacturer for the Anker Soundcore title.

    The snapshot item has brand='mountainlifestyle.ca'; the base extractor bleeds
    this retailer string. The adapter must return 'anker'.
    """
    from dealfinder.extract import llm_extract

    title = "Anker Soundcore Q20i Active Noise Cancelling Headphones"
    result = llm_extract(title, adapter_path="adapters/extractor-v1/")
    assert result.brand is not None
    assert result.brand.lower() == "anker"


def test_base_extractor_bleed_documents_motivation():
    """Document that the base extractor bleeds retailer on the COWIN title.

    This test is expected to pass (the assertion reflects the known bug, not a
    regression gate). It pins the motivation for fine-tuning.
    """
    from dealfinder.extract import rule_extract

    title = "Walmart - COWIN E7 Active Noise Cancelling Headphones Bluetooth"
    result = rule_extract(title)
    # rule_extract uses KNOWN_TENT_BRANDS and will not match any electronics brand —
    # brand comes back None here, not "Walmart". The LLM path is what bleeds.
    assert result.brand is None  # rule_extract is honest: unknown brand → None
```
