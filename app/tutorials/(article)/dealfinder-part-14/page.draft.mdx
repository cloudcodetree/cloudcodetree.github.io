# RAG: Grounded Answers Over Your Deals

**TL;DR: Part 13 gave you a durable semantic retriever. But a ranked list of rows is not an answer to "which noise-cancelling headphones under $150 should I buy?" This part adds the last two stages of RAG — build a numbered context from the retrieved deals, then generate an answer that may only cite listings it was handed. A mechanical faithfulness guard (`is_grounded`) rejects any answer that invents a price or a product. The result is a `/ask` endpoint that recommends the real Anker Q20i at $44.99, warns about the $46 Bose trap, and — provably — cannot hallucinate.**

You have built retrieval three times now: the in-memory hybrid index (Part 5), the durable pgvector store (Part 13), and the value rerank that floats honest deals above traps. Retrieval answers *"which listings are relevant?"* RAG — Retrieval-Augmented Generation — answers the question the user actually asked, in prose, **grounded in those listings so the model can't make things up.** The generation step is where LLMs are dangerous: ask a raw model for "cheap noise-cancelling headphones" and it will confidently quote a price it invented. RAG's discipline is that the model sees only the retrieved evidence, and a guard checks that every claim traces back to it.

## Why a ranked list is not an answer

Part 13's `semantic_search` returns rows: title, price, similarity. That is perfect for a search UI, but a user who types *"noise cancelling headphones under $150"* wants a recommendation, not a table. They want: **buy this, consider that, avoid the other one — and why.**

The naive move is to hand the raw question to an LLM. Do that and you inherit the model's training-data guesses: it will "recall" that some headphone costs $79, quote a discount that never existed, or invent a model number. None of it is tied to *your* live inventory. For a deal-finder, a confidently wrong price is worse than no answer — it is a liability.

RAG fixes this by inverting the flow. Instead of asking the model what it knows, you **retrieve the real listings first**, then ask the model to answer *using only those*. The model's job shrinks from "know everything about headphones" to "read these five rows and recommend." That is a job it can do reliably — and one you can verify.

## The RAG pipeline: retrieve → context → generate

`dealfinder/rag.py` is 414 lines built around three public functions that mirror the three RAG stages exactly:

```python
# dealfinder/rag.py — the three stages
def retrieve(query: str, k: int = 5, ...) -> list[RetrievedItem]: ...
def build_context(items: list[RetrievedItem]) -> str: ...
def answer(query: str, k: int = 5, *, llm=None) -> RagAnswer: ...
```

The unit that flows between them is `RetrievedItem` — a retrieved listing *plus its deal signal*, so the generator has everything it needs to both recommend and warn:

```python
@dataclass
class RetrievedItem:
    """One retrieved listing plus its deal signal — the unit an answer grounds on."""
    id: str
    title: str
    price: float
    source: str
    category: str
    similarity: float          # value-rerank score from search_catalog (higher = better pick)
    verdict: str               # deal | fair | suspicious | overpriced
    median_signal: float       # fraction under the same-query median
    fair_price: float          # model's predicted fair price
    residual_frac: float       # (fair - actual) / fair
    reason: str                # the verdict's human explanation
```

The final output is a `RagAnswer` — the prose plus its provenance and, critically, a faithfulness flag:

```python
@dataclass
class RagAnswer:
    """The generated answer plus its provenance and a faithfulness flag."""
    answer: str
    sources: list[str] = field(default_factory=list)  # item ids the answer actually uses
    grounded: bool = False
    used_llm: bool = False
```

`grounded` is not decoration. It is the output of a check that runs on every answer, and it is what makes this pipeline safe to expose.

## retrieve(): the value-reranked evidence

`retrieve()` is not a bare cosine query. It reuses the full Part 5 retriever — hybrid semantic + BM25, fused with RRF, then **value-reranked** over the cached title embeddings — and attaches each item's deal verdict from the Part 3 model. It's deterministic by design: it ranks over the committed cached vectors, so the output below reproduces on any machine, `DATABASE_URL` or not. The pgvector store (Part 13) holds the same vectors and powers the raw-cosine `/semantic` browser; you can opt `retrieve` into it with `use_db=True`, but that returns raw semantic candidates *without* the value rerank — a different tool for a different job.

```python
def retrieve(query: str, k: int = 5, products=None, embeddings=None) -> list[RetrievedItem]:
    """Retrieve the top-k real listings for `query` with their deal signal.

    Embeds the query (fastembed bge-small, via search_catalog), ranks against
    the cached title embeddings — or pgvector semantic_search when DATABASE_URL
    is set — hybridizes with BM25, and value-reranks so honest deals float above
    too-good-to-be-true traps. Each result carries its similarity, price, and the
    two-signal verdict, so an answer can ground on it.
    """
    if products is None:
        products, embeddings = load_catalog_embeddings()
    ...
    if os.getenv("DATABASE_URL"):
        ranked = _retrieve_pgvector(query, products, k)
    else:
        hits = search_catalog(query, products, embeddings, medians, k=k)
        ranked = [(p, float(score)) for _idx, p, score in hits]

    items = []
    for p, score in ranked:
        v = _verdict_for(p, medians.get(p.id, 0.0), models)
        items.append(RetrievedItem(id=p.id, title=p.title, price=float(p.price),
            source=p.source, category=p.category, similarity=round(score, 4),
            verdict=v.label, median_signal=round(v.median_signal, 4),
            fair_price=round(v.fair_price, 2), residual_frac=round(v.residual_frac, 4),
            reason=v.reason))
    return items
```

<Callout tone="note">
**This is not raw cosine order.** In Part 13, a pure `<=>` cosine query surfaced the pricier, most canonically-described listings first — the $359.99 Bose QuietComfort at similarity 0.8652 — with the budget Anker Q20i nowhere near the top. Here the **Anker Q20i is rank 1** — the value rerank blends relevance with the deal score, so a genuine bargain outranks a merely-relevant listing. The `similarity` field is the *post-rerank* score, which is why the OVERPRICED Bose sits at −1.21: relevant, but pushed down for being a bad buy. Same corpus, a ranking objective tuned for a deal-finder. This value-reranked path is what `retrieve` always runs — the pgvector store (Part 13) is a separate raw-cosine retriever behind `/semantic`, opt-in here via `use_db=True` — so `tests/test_rag.py` reproduces this exact ordering on any machine.
</Callout>

Notice the two Bose rows. The QuietComfort 45 at **$46.00** is flagged SUSPICIOUS, not DEAL — its `median_signal` (0.7177, i.e. 72% under median) looks like the Anker's, but its `residual_frac` is 0.839: the price sits 84% below the model's $285.15 fair price, the signature of a refurb or a mislisting. Retrieval surfaces it; the verdict warns about it. Both facts travel with the item into the answer.

<Callout tone="note">
**Two reranks, don't confuse them — and a third you'll want on documents.** DealFinder's `value_rerank` is a *business* rerank: it reorders by deal quality, not relevance. The other kind — a **relevance cross-encoder reranker** — takes the query and each candidate *together* through a small model that scores true relevance far better than cosine (which encodes query and document separately). The standard move on a document corpus is retrieve-100 → cross-encoder-rerank → keep-10, with measured latency/quality tiers: `cross-encoder/ms-marco-MiniLM-L-6-v2` ≈ 30 ms/100 pairs, `bge-reranker-v2-m3` ≈ 80 ms (best local), hosted Cohere/Voyage rerank ≈ 120–150 ms — and skip it entirely under ~500 docs or on latency-critical paths. DealFinder's listings are single short titles, so cosine + value-rerank suffices; the cross-encoder earns its latency when candidates are long, similar documents.
</Callout>

<Callout tone="note">
**When your corpus is documents, not listings — two techniques this pipeline doesn't need but you will.** DealFinder retrieves whole listings (one short title each), so there's no chunking and no per-chunk context loss. The moment you RAG over *documents* (manuals, contracts, your own blog), two upgrades matter: **(1) chunking defaults** — 256–512 tokens for factoid queries, 1024–2048 for analytical, with 10–20% overlap and structure-aware splits so a chunk never starts mid-code-block; wrong chunking silently drops recall 20–30%. **(2) Contextual Retrieval** — before embedding, prepend a 50–100-token LLM-generated summary situating each chunk in its document ("this excerpt is from the Q3 refund policy…"); Anthropic measured a **49% reduction in retrieval failures** (67% with a reranker added), and `cache_control` on the document prefix keeps the per-chunk generation cost ~90% lower. Neither applies to a title; both are essential once a "listing" becomes a page.
</Callout>

## build_context(): the numbered evidence block

The augmentation stage turns the retrieved objects into a compact, numbered text block. This block is the **entire** evidence set the generator may use — nothing else about headphones is in scope:

```python
def build_context(items: list[RetrievedItem]) -> str:
    """Format retrieved listings into a compact, numbered, groundable context block.

    One line per item: index, title, price, source, and the deal verdict badge.
    This is the *only* evidence the answer is allowed to use.
    """
    lines = []
    for i, it in enumerate(items, 1):
        lines.append(
            f"[{i}] {it.title} — ${it.price:.2f} ({it.source}) "
            f"[{it.verdict.upper()}] — {it.reason}"
        )
    return "\n".join(lines)
```

For the hero query it produces exactly this — real output:

```text
[1] Anker Soundcore Q20i Hybrid Active Noise Cancelling Headphones — $44.99 (RapidAPI:Kohl's) [DEAL] — 72% under the $162.97 median and consistent with the model's $108 fair price — a genuine value pick.
[2] Soundcore Space 2 Active Noise Cancelling Headphones — $129.99 (RapidAPI:Target) [DEAL] — 20% under the $162.97 median and consistent with the model's $108 fair price — a genuine value pick.
[3] JBL Tune 770NC Wireless Noise Cancelling Over-Ear Headphones — $89.95 (RapidAPI:Walmart - OEM ACCESSORIES) [DEAL] — 45% under the $162.97 median and consistent with the model's $197 fair price — a genuine value pick.
[4] Bose QuietComfort Noise Cancelling Wireless Headphones — $359.99 (RapidAPI:Target) [OVERPRICED] — 121% above the market median.
[5] Bose QuietComfort 45 Wireless Noise Cancelling Headphones — $46.00 (RapidAPI:mountainlifestyle.ca) [SUSPICIOUS] — 72% under median but 84% under model fair price $285 — too far below to be real (likely refurb/mislisted).
```

Every line carries the verdict and its reason. That is deliberate: the generator doesn't have to *compute* whether the $46 Bose is a trap — the retrieval stage already decided, and the answer just has to relay it. The numbering (`[1]`, `[2]`, …) gives the model a stable handle to cite and gives the guard a set to check against.

## answer(): generate, grounded — LLM or deterministic

`answer()` wires the three stages together. It retrieves, and if an LLM client is configured it generates under a strict grounded prompt; otherwise it falls back to a deterministic extractive synthesis. **Either path is checked for faithfulness before it is returned:**

```python
def answer(query: str, k: int = 5, *, llm=None) -> RagAnswer:
    """Retrieve → build context → GENERATE a grounded answer."""
    items = retrieve(query, k=k)
    client = llm if llm is not None else _llm_module
    if getattr(client, "available", lambda: False)():
        try:
            return _llm_answer(query, items, client)
        except Exception:
            return _deterministic_answer(query, items)  # any LLM failure degrades safely
    return _deterministic_answer(query, items)
```

**The LLM path** injects the numbered context into a prompt whose system message forbids invention. This is the prompt that does the real work of grounding:

```python
_SYSTEM = (
    "You are DealFinder's shopping assistant. Answer ONLY using the numbered "
    "listings provided. Cite every item you mention by its exact title and price. "
    "If none of the listings qualify, say so plainly. Do NOT invent products, "
    "prices, brands, or specs that are not in the listings."
)

def _llm_answer(query, items, llm) -> RagAnswer:
    context = build_context(items)
    user = (f"Question: {query}\n\nListings (the ONLY evidence you may use):\n{context}\n\n"
            "Recommend the best pick, a runner-up, and warn about any SUSPICIOUS trap. "
            "Cite each by title and price.")
    text = llm.chat([{"role": "system", "content": _SYSTEM},
                     {"role": "user", "content": user}], temperature=0)
    used = [it.id for it in items if _title_cited(it, text)] or [it.id for it in items]
    return RagAnswer(answer=text.strip(), sources=used,
                     grounded=is_grounded(text, items), used_llm=True)
```

`temperature=0` is the same lesson from Part 2: extraction and grounded recommendation want determinism, not creativity.

**The deterministic path** needs no API key and is *always* grounded by construction — it only ever emits titles and prices that are in the retrieved set. It names the best DEAL, a runner-up, and the SUSPICIOUS trap with its reason:

```python
def _deterministic_answer(query, items) -> RagAnswer:
    """Build a grounded answer straight from the retrieved rows — no model."""
    deals = [it for it in items if it.verdict == "deal"]
    suspicious = [it for it in items if it.verdict == "suspicious"]
    hero = deals[0] if deals else items[0]
    runners = [it for it in items if it.id != hero.id and it.verdict != "suspicious"]

    used = [hero.id]
    parts = [f"Best value: {hero.title} at ${hero.price:.2f} "
             f"({hero.median_signal * 100:.0f}% under the same-query median)."]
    if runners:
        r = runners[0]; used.append(r.id)
        parts.append(f"Also consider: {r.title} at ${r.price:.2f}.")
    if suspicious:
        s = suspicious[0]; used.append(s.id)
        parts.append(f"Avoid: {s.title} at ${s.price:.2f} — flagged SUSPICIOUS: it "
            f"reads {s.median_signal * 100:.0f}% under median but sits far below its "
            "modeled fair price, the signature of a refurb/mislisting rather than a real bargain.")
    answer = " ".join(parts)
    return RagAnswer(answer=answer, sources=used, grounded=is_grounded(answer, items), used_llm=False)
```

## The faithfulness guard: is_grounded

Whichever path generated the answer, `is_grounded()` is the gate. It is not an LLM "judge" and it is not fuzzy — it is a mechanical check: **every price the answer cites must appear in the context block, and every distinctive product token must appear in a retrieved title.**

<GroundingGuard />

```python
def is_grounded(answer_text: str, retrieved: list[RetrievedItem]) -> bool:
    """True iff every product AND price the answer cites is in the context."""
    if not retrieved:
        return False

    # The allowed evidence is the WHOLE context block the model saw — which
    # includes each listing's price AND the derived values in its reason line
    # (the model's fair price, the query median). Whitelisting only listing
    # prices would falsely flag an answer for citing the fair price the context
    # itself supplied ("84% under model fair price $285").
    allowed_prices = _prices_in(build_context(retrieved))
    for price in _prices_in(answer_text):
        if price not in allowed_prices:
            return False   # a price the context never contained is a hallucination

    haystack = " " + _norm(" ".join(it.title for it in retrieved)) + " "
    ans = _norm(answer_text)
    # Model-code tokens (q20i, wh, 1000xm5, qc45) are the strongest product
    # fingerprints — each one cited must occur in some retrieved title.
    for tok in set(re.findall(r"[a-z]+\d[a-z0-9]*|\d+[a-z]+[a-z0-9]*", ans)):
        if len(tok) < 3:
            continue
        if f" {tok} " not in haystack:
            return False
    return True
```

Two independent traps close here. First, **prices**: pull every `$X` out of the answer; if one isn't in the context, fail. Second, **product fingerprints**: model codes like `q20i` or `wh-1000xm5` are near-unique, so if the answer names one that appears in no retrieved title, fail. An LLM that "helpfully" adds a headphone it remembers from training — at a price it invented — trips both.

<Callout tone="warn">
**A subtle bug worth internalizing: validate against the evidence you *gave*, not a subset of it.** An earlier version of this guard whitelisted only the *listing* prices (`{it.price}`). But `build_context` deliberately feeds the model more than that — each item's line ends with the deal reason, which cites the model's fair price and the query median (*"84% under model fair price $285"*). So a perfectly faithful answer that said *"…below its $285 fair price"* was flagged as ungrounded, because `$285` isn't a *listing* price. The guard was stricter than the context it handed the model — and in the running app that meant the faithfulness badge read **FLAGGED on every good answer**. The fix is one line: build the allowed-price set from `build_context(retrieved)` — the exact text the model saw. The lesson: a grounding check must be scoped to *precisely* the evidence provided, no wider and no narrower.
</Callout>

That is exactly what the tests assert. Two shapes of hallucination are caught — an unknown product *and* a real product at an invented price — while a faithful citation passes:

```python
QUERY = "noise cancelling headphones under $150"

def test_is_grounded_rejects_hallucinated_product():
    items = rag.retrieve(QUERY, k=5)
    # A product (and price) that is NOT in the retrieved set.
    halluc = "Buy the Sennheiser Momentum 4 at $199.00 — it's the best pick."
    assert rag.is_grounded(halluc, items) is False
    # A real product with a fabricated price is also a hallucination.
    bad_price = "The Anker Soundcore Q20i at $9.99 is the steal of the year."
    assert rag.is_grounded(bad_price, items) is False
    # A faithful answer citing a real retrieved product + price is grounded.
    good = "The Anker Soundcore Q20i at $44.99 is the best value."
    assert rag.is_grounded(good, items) is True
```

<Callout tone="tip">
**This is why RAG is safe to ship and a raw LLM is not.** The generator can still make a mistake — but a mistake that invents a price or a product cannot pass the guard, so it never reaches the user as `grounded: True`. You get to decide what to do with a `grounded: False` answer: suppress it, retry, or fall back to the deterministic path.
</Callout>

## The /ask endpoint

Expose the pipeline as one route on the FastAPI app from Part 12. It works fully offline — with no `OPENROUTER_API_KEY`, the deterministic path answers:

```python
# dealfinder/serve.py
@app.get("/ask")
def ask(q: str, k: int = 5):
    """RAG: retrieve real listings for the query, then GENERATE a grounded answer.

    Returns the RagAnswer — the synthesized answer, the retrieved item ids it
    used as `sources`, whether it passed the faithfulness check (`grounded`), and
    whether an LLM produced it (`used_llm`). With no OPENROUTER_API_KEY the
    deterministic extractive path answers, so this route works fully offline."""
    from .rag import answer as rag_answer
    a = rag_answer(q, k=k)
    return {"query": q, "answer": a.answer, "sources": a.sources,
            "grounded": a.grounded, "used_llm": a.used_llm}
```

## Reproducibility checks

The eight assertions in `tests/test_rag.py` pin the whole pipeline. They run offline against the frozen snapshot — no key, no network:


<Callout tone="note">
**Determinism, on purpose.** With no LLM key the pipeline is fully deterministic against the frozen snapshot — same corpus, same cached embeddings, same value rerank ⇒ the same top-5 and the same answer every run. That is what makes these assertions stable. When you inject a real LLM (`temperature=0`) the prose varies slightly, but the *guard* is the invariant the tests protect: grounded answers pass, hallucinations fail.
