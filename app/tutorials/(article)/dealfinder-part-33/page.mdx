## What the suggestions worker does

Price-tracker apps — Honey, Camelizer, Google Shopping alerts — share one abstraction: a background job that knows what you saved, knows what it already told you, and notifies you only about the rest. The interesting part is not the scheduler (a cron job, a Prefect flow, a Supabase Edge Function) nor the delivery channel (email, push, webhook). The interesting part is the **diff**: how do you make the core logic correct, testable, and re-runnable without surprise?

The answer in `dealfinder/worker.py` is two small dataclasses and one pure function:

```
SavedSearch(user_id, query, k=5)      — what to watch and for whom
SuggestionState(seen: dict → set[id]) — memory of what was already notified
run_suggestions(saved, state) → (notifications, new_state)
```

The function takes state in, returns new state out. Nothing is mutated globally. The same inputs always produce the same outputs. Feed the returned state back in and the next run is idempotent. That property is the whole lesson.

## SavedSearch and SuggestionState

The two dataclasses are deliberately minimal.

```python
# dealfinder/worker.py
from dataclasses import dataclass, field

@dataclass(frozen=True)
class SavedSearch:
    user_id: str
    query: str
    k: int = 5
```

`SavedSearch` is frozen (hashable, no accidental mutation). `k` is how many top results the search pipeline surfaces per run; you rarely need more than five.

```python
@dataclass
class SuggestionState:
    seen: dict[tuple[str, str], set[str]] = field(default_factory=dict)

    def key(self, s: SavedSearch) -> tuple[str, str]:
        return (s.user_id, s.query)

    def already_seen(self, s: SavedSearch) -> set[str]:
        return self.seen.get(self.key(s), set())

    def mark_seen(self, s: SavedSearch, ids: set[str]) -> None:
        self.seen.setdefault(self.key(s), set()).update(ids)

    def copy(self) -> "SuggestionState":
        return SuggestionState(seen={k: set(v) for k, v in self.seen.items()})
```

The key is `(user_id, query)` — one slot per user per saved query. `already_seen` returns the set of item ids the user was previously notified about. `mark_seen` adds newly notified ids. `copy` returns a deep clone so the caller's original state is never touched.

In production you persist `SuggestionState` to a key-value store (Redis, Supabase) between cron runs. In the test suite you pass a fresh `SuggestionState()` and inspect the returned copy.

## The Notifier protocol seam

Delivery is behind a `Protocol`:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Notifier(Protocol):
    def notify(self, notification: Notification) -> None: ...
```

The `runtime_checkable` decorator lets you assert `isinstance(obj, Notifier)` in tests — useful for verifying that a custom notifier satisfies the contract before wiring it in.

The default implementation is `ConsoleNotifier`, which prints and records:

```python
class ConsoleNotifier:
    def __init__(self) -> None:
        self.sent: list[dict] = []

    def notify(self, notification: Notification) -> None:
        payload = notification.as_dict()
        self.sent.append(payload)
        print(
            f"[deal] {payload['user_id']} · {payload['query']!r} → "
            f"{payload['title'][:48]} ${payload['price']} "
            f"(score {payload['deal_score']})"
        )
```

`ConsoleNotifier.sent` accumulates the dict payloads so tests can assert on the exact notification without capturing stdout. The payload dict is what a real email or push notifier would serialize to JSON.

<NotifierProtocol />

The `Notification` dataclass itself:

```python
@dataclass
class Notification:
    user_id: str
    query: str
    item_id: str
    title: str
    price: float
    deal_score: float

    def as_dict(self) -> dict:
        return {
            "user_id": self.user_id,
            "query": self.query,
            "item_id": self.item_id,
            "title": self.title,
            "price": self.price,
            "deal_score": round(self.deal_score, 4),
        }
```

`deal_score` is rounded to four decimal places in the dict payload. That rounding is the number you quote when citing the Anker result (+0.7239), not a truncation that loses precision in the diff logic.

## The Catalog and find_deals

`run_suggestions` needs something to search. Rather than embed snapshot I/O inside the diff logic, the module exposes a `Catalog` dataclass that bundles what the worker needs:

```python
@dataclass
class Catalog:
    products: list[Product]
    embeddings: object        # np.ndarray aligned to products
    medians: dict[str, float]
```

`load_catalog()` builds one from the committed snapshot (offline):

```python
def load_catalog(path: str | None = None) -> Catalog:
    items = load_snapshot(path)
    products, emb = load_catalog_embeddings(load_products(path))
    medians = {r["id"]: float(r["median_price_at_capture"]) for r in items}
    return Catalog(products=products, embeddings=emb, medians=medians)
```

Tests hand in a real `Catalog` (from the committed snapshot) or a slimmed one. No mocking of the catalog itself — the snapshot is the fixture.

`find_deals` runs the full search pipeline from Part 5 and Part 3, then applies the threshold:

```python
DEAL_SCORE_THRESHOLD = 0.30

def find_deals(catalog: Catalog, query: str, k: int) -> list[tuple[Product, float]]:
    from .search import search_catalog

    results = search_catalog(
        query, catalog.products, catalog.embeddings, catalog.medians, k=k
    )
    return [(p, score) for _, p, score in results if score >= DEAL_SCORE_THRESHOLD]
```

`search_catalog` returns `(rank, product, score)` tuples; `find_deals` strips the rank and filters to the deals that clear the threshold. The threshold 0.30 is module-level so tests can import and verify it.

<Callout tone="note">
`search_catalog` is the same pipeline you built in Part 5 (semantic + BM25, RRF fusion) with the two-signal value rerank from Part 3 applied last. The worker does not re-implement any of that — it calls it. This is the payoff of building those parts as composable functions rather than scripts.
</Callout>

## run_suggestions: the diff loop

```python
def run_suggestions(
    saved: list[SavedSearch],
    state: SuggestionState,
    *,
    catalog: Catalog | None = None,
    notifier: Notifier | None = None,
) -> tuple[list[Notification], SuggestionState]:
    catalog = catalog if catalog is not None else load_catalog()
    notifier = notifier if notifier is not None else ConsoleNotifier()
    new_state = state.copy()

    notifications: list[Notification] = []
    for s in saved:
        seen = new_state.already_seen(s)
        deals = find_deals(catalog, s.query, s.k)
        fresh_ids: set[str] = set()
        for product, score in deals:
            if product.id in seen:
                continue
            note = Notification(
                user_id=s.user_id,
                query=s.query,
                item_id=product.id,
                title=product.title,
                price=product.price,
                deal_score=score,
            )
            notifier.notify(note)
            notifications.append(note)
            fresh_ids.add(product.id)
        if fresh_ids:
            new_state.mark_seen(s, fresh_ids)

    return notifications, new_state
```

Walk through the control flow:

1. **Copy state first.** `new_state = state.copy()` means the caller's original `SuggestionState` is never mutated. The returned `new_state` is a separate object.
2. **Per saved search, check already_seen.** Any `product.id` already in the set is skipped silently. No re-notification, no matter how many times the same deal appears in search results.
3. **Notify and record fresh ids.** `fresh_ids` accumulates only ids not previously seen. After the inner loop, `mark_seen` updates `new_state` for this saved search.
4. **Return both.** The caller feeds `new_state` back into the next invocation.

The catalog and notifier are keyword-only with `None` defaults so they can be omitted in production (defaults load from disk / print to console) or injected in tests. The function signature is the interface; the defaults are the convenience.

## Worked example: hero cast, first and second run

The hero cast anchor query is **"noise cancelling headphones"**, snapshot median **$162.97**.

```python
from dealfinder.worker import (
    SavedSearch, SuggestionState, ConsoleNotifier, load_catalog, run_suggestions
)

catalog = load_catalog()
notifier = ConsoleNotifier()

saved = [SavedSearch(user_id="u1", query="noise cancelling headphones", k=5)]
state = SuggestionState()

notifications, new_state = run_suggestions(saved, state, catalog=catalog, notifier=notifier)
```

**First run output:**

```
[deal] u1 · 'noise cancelling headphones' → Anker Soundcore Q20i Hybrid Active Noise Cancell $44.99 (score 0.7239)
```

```python
print(len(notifications))          # 1
print(notifier.sent[0])
```

```

  "query": "noise cancelling headphones",
  "item_id": "rapidapi-catalogid:4602286582194268609,productid:",
  "title": "Anker Soundcore Q20i Hybrid Active Noise Cancelling Headphones",
  "price": 44.99,
  "deal_score": 0.7239
```

The Anker Soundcore Q20i surfaces as the one notification. Its deal score +0.7239 clears the 0.30 threshold by a wide margin — it is 72% under the $162.97 query median and the model fair price ($108.33) also validates the discount as genuine rather than suspicious.

<Callout tone="note">
`title_brand()` on "Anker Soundcore Q20i Hybrid Active Noise Cancelling Headphones" resolves to **"Soundcore"** — the sub-brand Anker markets ANC headphones under. This is the same behavior pinned in `test_normalize_attaches_title_extracted_brand` from Part 20 (`true_brand == "Soundcore"`). The notification title includes the full listing title, not the extracted brand.
</Callout>

The Bose QuietComfort 45 at $46.00 has a median_signal of +0.718, which puts it above the threshold on that signal alone. But the two-signal score factors in the model residual: the price model's fair price for this flagship is $285.15 (the same as the XM5, since both are tier-4 flagships). The residual_frac +0.839 flags it as SUSPICIOUS, which the value rerank penalizes. It does not appear in the top-k deals that clear 0.30 on the blended score.

The Sony WH-1000XM5 at $162.97 sits at the median: median_signal +0.000. Below threshold. No notification.

**Second run — feed back the returned state:**

```python
notifications2, _ = run_suggestions(saved, new_state, catalog=catalog, notifier=notifier)
print(len(notifications2))         # 0
```

Zero notifications. The Anker Q20i's item id is now in `new_state.already_seen(saved[0])`. The diff loop skips it. The function is idempotent with respect to the state it returns.

## Idempotency proof

The idempotency guarantee is worth being explicit about. The function:

1. Does not load state from any external store inside the call — state is an argument.
2. Does not modify the input state — it copies it.
3. Returns the updated copy — the caller controls persistence.

This means you can call `run_suggestions` as many times as you want with the same `state` object and get the same `notifications` list back every time. Only by feeding back the returned `new_state` does the output change. The job scheduler's job is to persist and supply that state; the function's job is the diff and the notification. They are separated by the return type.

In production the state is persisted to a key-value store between cron runs:

```python
# Illustrative production wrapper (not in worker.py — this lives in the scheduler)
state = load_state_from_kv(user_id)           # fetch persisted state
notifications, new_state = run_suggestions(saved, state, catalog=catalog)
save_state_to_kv(user_id, new_state)          # persist new state
dispatch_notifications(notifications)          # deliver
```

The core module stays pure. The infrastructure wrapper handles I/O.

## A newly covered saved search

The third test in `tests/test_worker.py` covers a different scenario: a saved search for a query that was not previously run at all.

```python
from dealfinder.worker import SavedSearch, SuggestionState, ConsoleNotifier, load_catalog, run_suggestions

catalog = load_catalog()
saved = [SavedSearch(user_id="u2", query="bluetooth speaker", k=1)]
state = SuggestionState()    # fresh — no prior "bluetooth speaker" run

notifier = ConsoleNotifier()
notifications, _ = run_suggestions(saved, state, catalog=catalog, notifier=notifier)

assert len(notifications) == 1   # exactly one notification, k=1 so only one considered
```

With `k=1`, only the top-ranked deal is considered for notification. Because the state has no prior entry for this `(user_id, query)` key, whatever deal clears the threshold on the first result fires exactly one notification. This pins the boundary: `SuggestionState.already_seen()` returns an empty set for an unknown key (not a `KeyError`), so a brand-new saved search always gets its first notification.
