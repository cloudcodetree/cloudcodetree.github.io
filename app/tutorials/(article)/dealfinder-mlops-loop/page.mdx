# Closing the MLOps Loop

**TL;DR: The individual pieces — drift detection, model retraining, an evaluation gate — exist. This part wires them into one auditable cycle. When the live feature mix shifts past PSI 0.2, the system retrains, runs the challenger through the precision@5 gate (≥0.80 required), and promotes it only if it beats the incumbent champion. You run one function and get back a structured trace that records every decision.**

This is **Part 24 of DealFinder**, sitting at the end of Phase 4 (ML rigor & MLOps). Parts 21, 22, and 23 built the price model, wired up experiment tracking, and established evaluation as a discipline. This part asks the harder question: once you have all that, how do you keep the model honest over time? The answer is a loop — one that fires on evidence, retrain deterministically, gates on a pinned metric, and promotes only when the evidence is unambiguous.

- Compute PSI between two category distributions and interpret the result — PSI 0.043 means hold, PSI 0.318 means retrain.

## Why the loop, not the model, is the product

A price model trained in July against the noise-cancelling-headphones-heavy snapshot will go stale. Not because it was wrong, but because the live traffic mix shifts — gaming laptops surge, ultrawide monitors spike, the audio bucket shrinks. The model's priors were built on a different distribution. Its predictions silently degrade. Deal scores rot.

The point of Part 21 was to build a model. The point of Part 24 is to make sure the model you shipped in July is still the right model in October. That requires a loop: measure drift, decide whether retraining is warranted, evaluate the retrained candidate, and promote only when the evidence clears an explicit bar.

What makes this different from ad-hoc maintenance is that every step produces a record. The `CycleDecision` returned by `run_mlops_cycle()` is not a side effect or a log line — it is the artifact. You can serialize it, store it, replay it, and audit it. "We promoted two_signal on date X because PSI was 0.318, GBDT MAE dropped to $138.11, and precision@5 hit 1.00" is a statement you can verify from the trace, not a shrug.

## The four stations

`dealfinder/mlops.py` structures the loop as four discrete stations. Each produces a typed dataclass; the next station receives the previous one's output. Nothing is global state; nothing is implicit.

```
drift → retrain → eval gate → promote
```

The full module:

```python
# dealfinder/mlops.py (abbreviated)
from .evals import GATE_K, GATE_PRECISION, evaluate, median_only_ranker, two_signal_ranker
from .features import category_code
from .models import gbdt_vs_linear
from .ops import has_drifted, population_stability_index
from .snapshot import load_products

DRIFT_THRESHOLD = 0.2

RANKERS = {
    "two_signal": two_signal_ranker,
    "median_only": median_only_ranker,
}
```

`DRIFT_THRESHOLD = 0.2` is the PSI boundary. Below it the loop holds. At or above it the loop retrains. The threshold comes from the standard PSI rule of thumb: &lt;0.1 no shift, 0.1–0.2 moderate, ≥0.2 significant.

## Station 1: drift detection with PSI

Population Stability Index measures how much a distribution has moved. `check_drift(frac)` builds the reference distribution from the snapshot's actual category mix, shifts it by `frac` toward the high-code categories (computers, displays, misc — simulating a live traffic surge), and computes PSI:

```python
@dataclass
class DriftReport:
    psi: float
    threshold: float
    drifted: bool
    frac: float

    @property
    def action(self) -> str:
        return "retrain" if self.drifted else "hold"


def check_drift(frac: float, *, products=None) -> DriftReport:
    ref = reference_category_histogram(products)
    cur = shift_distribution(ref, frac)
    psi = round(population_stability_index(ref, cur), 4)
    return DriftReport(
        psi=psi,
        threshold=DRIFT_THRESHOLD,
        drifted=has_drifted(ref, cur, DRIFT_THRESHOLD),
        frac=frac,
    )
```

The shift is deterministic in `(ref, frac)`: `shift_distribution` moves `frac` of the mass toward the last three bins. Same inputs → same PSI, every time.

Run it:

```python
from dealfinder.mlops import check_drift

mild   = check_drift(0.1)
strong = check_drift(0.3)

print(f"mild:   PSI={mild.psi}  drifted={mild.drifted}  action={mild.action}")
print(f"strong: PSI={strong.psi}  drifted={strong.drifted}  action={strong.action}")
```

```
mild:   PSI=0.0426  drifted=False  action=hold
strong: PSI=0.3182  drifted=True   action=retrain
```

A 10% shift barely moves the distribution. A 30% shift exceeds PSI 0.2 by more than 50%. The `.action` property converts the boolean into the next step.

<PSIGauge />

<Callout tone="note">
**Why category mix and not raw features?** Category code is the coarsest, most stable feature: it captures the economic structure of what people are searching for, without depending on price or embeddings that change for every listing. A PSI spike here means the model's foundational assumptions about what category of product it will score have shifted — that is the signal worth acting on.
</Callout>

## Station 2: deterministic retraining

When drift fires, the loop retrains. Retraining here means replaying `models.gbdt_vs_linear()` against the frozen snapshot — the same data, the same train/test split, the same result every time:

```python
@dataclass
class RetrainReport:
    linear_mae: float
    gbdt_mae: float
    improvement_pct: float
    n_train: int
    n_test: int


def retrain() -> RetrainReport:
    c = gbdt_vs_linear()
    return RetrainReport(
        linear_mae=c.linear_mae,
        gbdt_mae=c.gbdt_mae,
        improvement_pct=c.improvement_pct,
        n_train=c.n_train,
        n_test=c.n_test,
    )
```

Run it:

```python
from dealfinder.mlops import retrain

rr = retrain()
print(f"GBDT MAE ${rr.gbdt_mae}  linear MAE ${rr.linear_mae}")
print(f"improvement {rr.improvement_pct}%  train/test {rr.n_train}/{rr.n_test}")
```

```
GBDT MAE $138.11  linear MAE $227.89
improvement 39.4%  train/test 202/68
```

The numbers reproduce because the snapshot is frozen and the split is deterministic. GBDT MAE $138.11 vs. linear $227.89 is the permanent, pinned baseline for this course — established in Part 21, confirmed in Part 22's experiment tracking, and reproduced here. If a future retrain on live data yields different numbers, those will be different numbers from a different corpus — and the course will say so explicitly.

<Callout tone="note">
**GBDT here is sklearn GradientBoostingRegressor**, not XGBoost. The model uses hand features (category, brand_tier, condition) plus 16-dimensional title embeddings from the BAAI/bge-small-en-v1.5 model. The same feature contract that won in Part 21's comparison table (`fair-price` contract, `selectable=True`) is what retrains here.
</Callout>

## Station 3: the eval gate

Retraining improves the price model. But the deal-finder's job is ranking — specifically, putting the genuine deals at the top of the list. A better R² on pricing does not automatically mean better deal ranking. You need to ask the ranking question directly.

The gate from Part 23 is the answer: **precision@5 ≥ 0.80** on the 20-item golden set (15 noise-cancelling headphones plus 5 cross-category items: Kindle, Galaxy Tab, Armitron watch, Arlo, PNY RTX). Of the five listings the ranker surfaces first, at least four must be ground-truth deals.

```python
@dataclass
class GateReport:
    challenger: str
    precision_at_5: float
    gate: float
    passes_gate: bool


def eval_gate(challenger: str) -> GateReport:
    ranker = RANKERS[challenger]
    res = evaluate(ranker)
    return GateReport(
        challenger=challenger,
        precision_at_5=res["precision_at_5"],
        gate=GATE_PRECISION,
        passes_gate=res["passes_gate"],
    )
```

Run it for both rankers:

```python
from dealfinder.mlops import eval_gate

two   = eval_gate("two_signal")
median = eval_gate("median_only")

print(f"two_signal:   p@5={two.precision_at_5}  passes={two.passes_gate}")
print(f"median_only:  p@5={median.precision_at_5}  passes={median.passes_gate}")
```

```
two_signal:   p@5=1.0   passes=True
median_only:  p@5=0.4   passes=False
```

`two_signal` scores 1.00 — all five of its top-five picks are genuine deals. `median_only` scores 0.40 — it puts the Bose QuietComfort 45 at $46 at the top (median says 72% off the $162.97 anchor, which reads as a screaming deal). The model knows it is not. The median does not. Two correct picks out of five fails the gate.

This is the same result established in Part 23 and pinned in `tests/test_mlops.py`. The gate number does not change between parts. That is the point of pinning it.

## Station 4: champion/challenger promotion

Passing the gate is necessary but not sufficient for promotion. The challenger must also beat the incumbent champion's precision@5. A challenger that passes the gate but merely ties the champion is not promoted — the tie-breaks toward keeping the known quantity.

```python
def _champion_precision(champion: str | None) -> float:
    if champion is None:
        return 0.0
    return evaluate(RANKERS[champion])["precision_at_5"]
```

Promotion requires both:

1. `gate.passes_gate` — challenger clears precision@5 ≥ 0.80
2. `gate.precision_at_5 > champ_p` — challenger strictly beats the champion

```python
beats_champion = gate.precision_at_5 > champ_p
promote = gate.passes_gate and beats_champion
```

Three scenarios and their outcomes:

| Scenario | Gate | Beats champion | Promote | Reason |
|---|---|---|---|---|
| two_signal challenger, median_only champion (0.40) | p@5=1.00 ≥ 0.80 PASS | 1.00 > 0.40 yes | **yes** | passed gate and beat champion |
| median_only challenger, two_signal champion (1.00) | p@5=0.40 < 0.80 FAIL | 0.40 < 1.00 no | **no** | rejected by gate |
| challenger ties champion | p@5=X ≥ 0.80 PASS | X > X is false | **no** | tied, not promoted |

The third scenario is tested explicitly in `test_passing_challenger_that_does_not_beat_champion_is_not_promoted`. A tie is not a win.

## Running the full cycle

`run_mlops_cycle()` runs all four stations in sequence and returns a `CycleDecision` with the full trace. The headline scenario — drift detected, retrain, two_signal promoted over median_only — is the default:

```python
from dealfinder.mlops import run_mlops_cycle

decision = run_mlops_cycle(
    frac=0.3,
    challenger="two_signal",
    champion="median_only",
)

print(f"drifted={decision.drift.drifted}  psi={decision.drift.psi}")
print(f"retrained={decision.retrained}  gbdt_mae={decision.retrain_report.gbdt_mae}")
print(f"gate: {decision.gate.challenger}  p@5={decision.gate.precision_at_5}  passes={decision.gate.passes_gate}")
print(f"champion={decision.champion}  champion_p@5={decision.champion_precision_at_5}")
print(f"promote={decision.promote}")
print(f"reason={decision.reason}")
print("trace:")
for line in decision.trace:
    print(f"  - {line}")
```

```
drifted=True  psi=0.3182
retrained=True  gbdt_mae=138.11  linear_mae=227.89  improvement_pct=39.4  n_train=202  n_test=68
gate: two_signal  precision@5=1.0  passes=True
champion=median_only  champion_p@5=0.4
promote=True
reason=promoted: two_signal passed the gate (p@5=1.0 ≥ 0.8) and beat champion median_only (0.4)
trace:
  - drift: PSI=0.3182 vs threshold 0.2 → DRIFT, retrain
  - retrain: GBDT MAE $138.11 vs linear $227.89 (39.4% better) on 202/68 split
  - gate: two_signal precision@5=1.0 vs 0.8 → PASS
  - promoted: two_signal passed the gate (p@5=1.0 ≥ 0.8) and beat champion median_only (0.4)
```

The rejected scenario — `median_only` as challenger against a `two_signal` champion — fails at station 3 and short-circuits:

```python
decision2 = run_mlops_cycle(
    frac=0.3,
    challenger="median_only",
    champion="two_signal",
)
print(f"promote={decision2.promote}")
print(f"reason={decision2.reason}")
```

```
promote=False
reason=rejected: median_only failed the eval gate (p@5=0.4 < 0.8)
```

The no-drift branch (frac=0.1, PSI 0.043) also short-circuits — no retrain, no gate, champion retained. Tested in `test_no_drift_holds_without_retrain_or_promotion`.

## What the tests pin

`tests/test_mlops.py` has seven tests. Each one pins a specific behavior so that none of these results can silently change:

- `test_mild_shift_does_not_trip_drift` — frac=0.1 → PSI 0.0426, drifted=False
- `test_strong_shift_trips_drift` — frac=0.3 → PSI 0.3182, drifted=True
- `test_two_signal_challenger_passes_gate_and_is_promoted` — the headline scenario end-to-end
- `test_weak_challenger_is_rejected_by_the_gate` — median_only fails at p@5=0.40
- `test_passing_challenger_that_does_not_beat_champion_is_not_promoted` — the tie/draw case
- `test_no_drift_holds_without_retrain_or_promotion` — mild shift → champion retained
- `test_eval_gate_standalone_matches_the_pinned_ab` — `eval_gate()` in isolation reproduces Part 23's A/B numbers

Run them:

```bash
pytest tests/test_mlops.py -v
```

All seven pass. Run them alongside Part 21's tracking suite:

```bash
pytest tests/test_tracking.py tests/test_mlops.py
```

```
11 passed
```

The PSI values, MAE numbers, precision@5 scores, and promotion decisions are fixed by the committed snapshot. If they change, a test breaks — and a breaking test is the correct signal that something in the underlying data or model contract has changed.

<Callout tone="warn">
**The retrain here is offline and deterministic.** In production you would wire `retrain()` to your actual feature store and a fresh data pull, and the MAE would vary. What the tests guarantee is the *structure* of the decision — that the gate fires correctly, that the promotion rule is applied, that the trace records the reasoning. The snapshot numbers are the ground truth for this course; your production numbers will differ, and that is expected.
</Callout>
