## Why "looks better" is not engineering

After Part 3, you had a strong intuition that the two-signal deal scorer was better than the naive median. The Bose QuietComfort 45 at $46 was no longer surfaced as a star deal; the Anker Q20i at $44.99 was. But "intuition" is not something you can track over 33 parts and thousands of commits.

The discipline of evaluation is simple: pick representative inputs, label the correct answer once, and you can score any version of the system automatically. The score is tracked on every commit. When a score drops, the build fails. When you ship a new model or a new ranking function, you can cite the delta — "+0.60 precision@5" — not a gut feeling.

That discipline is what this part builds.

## The golden set: 20 labeled real listings

The golden set is defined in `GOLDEN_LABELS` inside `dealfinder/evals.py`. It contains exactly 20 items: all 15 "noise cancelling headphones" rows from the snapshot (the full anchor subset, covering the whole price range) plus 5 cross-category items chosen specifically to stress the two-signal score.

The cross-category items are the important teaching cases. Each was chosen because the median-only signal has a strong opinion about it — and that opinion is wrong:

| Item | Price | Median signal says | Truth |
|---|---|---|---|
| Kindle Paperwhite (accessory/mislisting) | $10.75 | strong deal | suspicious |
| Samsung Galaxy Tab A11+ | $15.00 | strong deal | suspicious |
| Armitron Link Smart Watch | $39.88 | good deal | deal |
| Arlo Ultra 3 | $372.90 | slightly high | overpriced |
| PNY NVIDIA RTX PRO 6000 | $13,599 | far above median | overpriced |

The full label distribution across all 20 items: `deal: 6, overpriced: 9, suspicious: 4, fair: 1`. There are more overpriced and suspicious items than deals in this set — that asymmetry is realistic (the snapshot is broad consumer electronics, and most items are not actually deals).

`load_golden` materializes the golden set from the committed snapshot:

```python
# dealfinder/evals.py
def load_golden(path: str | None = None) -> list[dict]:
    """Materialize the golden set as rows: {id, title, category, price, median, label}."""
    items = load_snapshot(path)
    golden: list[dict] = []
    for needle, label in GOLDEN_LABELS:
        r = _resolve(items, needle)
        golden.append(
            {
                "id": r["id"], "title": r["title"], "category": r["category"],
                "price": float(r["price"]),
                "median": float(r["median_price_at_capture"]),
                "label": label,
            }
        )
    return golden
```

Labels are matched by title substring so they survive any change to the opaque snapshot IDs. The needle strings are chosen to be unambiguous: "Anker Soundcore Q20i" matches exactly one row; "Bose QuietComfort 45" matches exactly one row. The snapshot is committed and frozen, so `load_golden()` is deterministic.

## Precision@5: the one eval-gate metric

The deal ranker surfaces the five listings it thinks are the best deals. A user sees those five first. The metric that captures this is **precision@5**: of the top-5 ranked items, how many are truly labeled `deal`?

```python
# dealfinder/evals.py
GATE_K = 5
GATE_PRECISION = 0.80

def precision_at_k(ranked: list[dict], k: int = GATE_K) -> float:
    """Fraction of the top-k ranked items that are truly labeled 'deal'."""
    top = ranked[:k]
    return sum(1 for g in top if g["label"] == "deal") / max(1, len(top))
```

A perfect score is 1.00 (all 5 of the top 5 are genuine deals). The gate threshold is 0.80 — at least 4 of the 5 must be real deals for the system to pass. That gate is used identically in Parts 20, 24, and 32.

Why precision, not recall? Because the user sees exactly 5 listings. Surfacing 6 true deals when only 5 are shown is invisible. What hurts the user is showing a trap — a $46 Bose QC45 that looks like a deal but isn't — in position 1 or 2.

## The two rankers side by side

The harness tests two rankers. Both take the golden set and return it sorted from "best deal" to "worst."

**`median_only_ranker`** — the naive Part 3 baseline:

```python
def median_only_ranker(golden: list[dict]) -> list[dict]:
    return sorted(golden, key=lambda g: -median_signal(g["price"], g["median"]))
```

It ranks by how far below the query median each item sits. Fast, model-free, and fooled by anything that is cheap for the wrong reason.

**`two_signal_ranker`** — the two-signal blend from the spec:

```python
def two_signal_ranker(golden: list[dict], products: list[Product] | None = None) -> list[dict]:
    # ...fits a per-category LinearModel on the snapshot, then:
    def score(g: dict) -> float:
        m = median_signal(g["price"], g["median"])
        model = models.get(g["category"])
        p = by_id.get(g["id"])
        if model is None or p is None:
            return m
        rf = residual_fraction(p.price, fair_price(model, featurize(p)))
        if m >= 0.15 and rf > SUSPICIOUS_RESIDUAL_FRAC:  # a trap — demote below real deals
            return m - 1.0
        return m
    return sorted(golden, key=lambda g: -score(g))
```

`SUSPICIOUS_RESIDUAL_FRAC = 0.70`. An item that is both far below the median (`median_signal >= 0.15`) and implausibly far below its model-predicted fair price (`residual_frac > 0.70`) gets its score penalized by 1.0 — pushed below every honest deal. This is the residual sign convention from the spec: `residual = predicted_fair - actual`; a large positive residual means the item is suspiciously cheap relative to what the model expects for its features.

The hero cast makes the arithmetic concrete:

| Item | actual | fair price | residual_frac | median_signal | verdict |
|---|---|---|---|---|---|
| Sony WH-1000XM5 | $162.97 | $285.15 | +0.428 | +0.000 | fair |
| Anker Q20i | $44.99 | $108.33 | +0.585 | +0.724 | deal |
| Bose QC45 | $46.00 | $285.15 | +0.839 | +0.718 | suspicious |
| Sony WH-1000XM6 | $399.99 | $285.15 | -0.403 | -1.454 | overpriced |

Anker Q20i: `residual_frac = 0.585 < 0.70` — not a trap, score stays at `+0.724`. The Bose QC45: `residual_frac = 0.839 > 0.70` and `median_signal = 0.718 >= 0.15` — both conditions met, score penalized to `0.718 - 1.0 = -0.282`. The Bose drops below every genuine deal in the ranking. The Anker stays near the top.

<Callout tone="note">
Anker and Bose are both approximately 72% below the query median at roughly $45. **Only the residual fraction (0.585 vs 0.839) separates them.** That separation is the entire point of the two-signal architecture.
</Callout>

```bash
python -m dealfinder.run_evals
```

```
golden set: 20 labeled snapshot items

  two_signal   precision@5 = 1.00   gate PASS ✓
  median_only  precision@5 = 0.40   gate FAIL ✗

A/B: winner = two_signal (+0.60 precision@5)
CI gate (precision@5 >= 0.80): PASS ✓

two_signal top-5:
  [deal      ] Armitron Link Smart Watch
  [deal      ] Anker Soundcore Q20i Hybrid Active Noise Cancelling Headphones
  [deal      ] JBL Tune 770NC Wireless Noise Cancelling Over-Ear Headphones
  [deal      ] Sony WH-CH720N Noise Canceling Wireless Headphones
  [deal      ] Sony WH-CH720N/P Wireless Noise Canceling Headphones
```

Five items, all labeled deal: precision@5 = 5/5 = **1.00**. Gate: 1.00 >= 0.80. Pass.

`evaluate` produces that result:

```python
# dealfinder/evals.py
def evaluate(ranker, golden=None) -> dict:
    golden = golden if golden is not None else load_golden()
    ranked = ranker(golden)
    p_at_5 = precision_at_k(ranked, GATE_K)
    return {
        "n": len(golden),
        "precision_at_5": p_at_5,
        "gate": GATE_PRECISION,
        "passes_gate": p_at_5 >= GATE_PRECISION,
        "top5": [{"title": g["title"], "label": g["label"]} for g in ranked[:GATE_K]],
    }
```

## Why the median-only ranker fails

The median-only top 5 for the same 20 items:

```
  [suspicious] Kindle Paperwhite (mislisting/accessory)
  [suspicious] Samsung Galaxy Tab A11+
  [deal      ] Armitron Link Smart Watch
  [suspicious] Cowin SE7
  [deal      ] Anker Soundcore Q20i
```

Two of five are genuine deals: precision@5 = 2/5 = **0.40**. Gate: 0.40 < 0.80. Fail.

The $10.75 Kindle Paperwhite and the $15 Samsung Galaxy Tab A11+ are at the top because they are far below their query medians. The median has no way to know they are accessories or mislistings. It sees a large positive `median_signal` and rewards them. That is the false positive problem Parts 3 and 17 were built to solve — and this part is what proves the solution works.

<Callout tone="warning">
The Bose QC45 does not appear in the median-only top 5 here because the Kindle and Galaxy Tab displace it — their prices are even more extreme. But in production, query composition varies: with a narrower query that excludes accessories, the Bose would be at position 1 in the median-only ranking. The cross-category golden set exposes this fragility; a headphones-only golden set would not.
</Callout>

## A/B: measuring the delta

`ab_compare` takes two scores and returns the winner with the delta:

```python
# dealfinder/evals.py
def ab_compare(name_a: str, score_a: float, name_b: str, score_b: float) -> dict:
    """Pick the higher-scoring system and report the delta (ties → A)."""
    winner = name_a if score_a >= score_b else name_b
    return {"winner": winner, "delta": round(abs(score_a - score_b), 3)}
```

```python
ab_compare("two_signal", 1.0, "median_only", 0.4)
# → {'winner': 'two_signal', 'delta': 0.6}
```

That `+0.60 precision@5` is a number you can put in a pull request description. It is not "feels better." It is measured on the same 20-item golden set, from the same frozen snapshot, reproducible by anyone who runs `pytest -q`.

## Wiring the gate into CI

`run_evals.main()` exits non-zero when the gate fails. In `.github/workflows/ci.yml`:

```yaml
- name: Run eval gate
  run: python -m dealfinder.run_evals
```

This step runs after `pytest -q`. If `two_signal` precision@5 drops below 0.80 — because someone changed the deal scorer, the feature matrix, or the model — the CI job fails and the pull request cannot merge. Same discipline as a unit test, applied to system-level quality.

<Callout tone="tip">
The gate checks the **two_signal** ranker, not the median_only baseline. The baseline failing is expected and documented. Only the production ranker needs to clear the bar.
</Callout>

The gate is the same threshold you will see in Part 20 (the MLOps drift-retrain loop gates on the same metric before promoting a retrained model to canary) and Part 24 (the deploy CI gate runs `run_evals` before building the Docker image).

## The tests

The eval harness is itself tested in `tests/test_evals.py`:

- **`test_golden_set_is_20_labeled_snapshot_items`** — asserts `n == 20` and `labels["deal"] == 6`. If the golden set grows or shrinks, the test catches it.
- **`test_two_signal_ranker_passes_the_eval_gate`** — calls `evaluate(two_signal_ranker)` and asserts `passes_gate == True` and `precision_at_5 >= 0.80`.
- **`test_median_only_ranker_is_fooled_and_misses_the_gate`** — calls `evaluate(median_only_ranker)` and asserts `precision_at_5 < 0.80`.
- **`test_ab_compare_prefers_the_two_signal_ranker`** — calls `ab_compare("two_signal", 1.0, "median_only", 0.4)` and asserts `winner == "two_signal"` and `delta == 0.6`.

```bash
pytest tests/test_evals.py -v
```

All four pass against the committed snapshot. They are part of the same `pytest -q` run that produces `17 passed` across the wave-3 parts.
