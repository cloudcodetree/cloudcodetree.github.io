## Why linear fails on broad electronics data

Part 3 fit a linear model on three features and got MAE $227.89 on the 68-item hold-out. That is not a rounding error — the corpus runs from a $2.99 cable to a $13,599 graphics card. A linear combination of `category_code`, `brand_tier`, and `condition_code` cannot capture the non-linear interactions between those three dimensions across eleven categories.

The model is the correct baseline: it is what you get when you do the right thing (no data leakage, deterministic split, test on held-out items) with too few features. It is honest, and it is weak. Three reasons:

1. **The feature space is too low-dimensional.** Three integer codes cannot distinguish a Sony WH-1000XM5 ($162.97) from a Bose QuietComfort 45 ($399 MSRP) — both are audio / brand_tier-4 / new. The model assigns them the same $285.15 fair price.
2. **The relationship is non-linear.** Brand tier and category interact. A tier-4 audio item and a tier-4 computing item are in completely different price bands. A linear model interpolates across that interaction; it cannot capture it.
3. **The title embedding carries signal the hand features cannot.** "RTX 4090" in a title is strong evidence of a $1,000+ price; the three-dimensional feature vector has no way to represent that.

Gradient boosting addresses points 1 and 2. Adding PCA-compressed title embeddings addresses all three.

## The gradient-boosted price model

`gbdt_vs_linear()` in `dealfinder/models.py` fits both models on the same deterministic split and returns a `ModelComparison` dataclass. The boosted model is `sklearn.ensemble.GradientBoostingRegressor` — not XGBoost; the companion has no XGBoost dependency.

```python
# dealfinder/models.py (abridged)
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.decomposition import PCA
from .dealmodel import LinearModel, mae
from .features import feature_matrix
from .snapshot import load_products

_SPLIT_SEED = 0
_TEST_FRAC  = 0.25
_GBDT_SEED  = 0
_PCA_COMPONENTS = 16

def gbdt_vs_linear(
    category: str | None = None,
    *,
    with_embeddings: bool = True,
    pca_components: int = _PCA_COMPONENTS,
) -> ModelComparison:
    products = load_products()
    if category is not None:
        products = [p for p in products if p.category == category]

    X_hand = feature_matrix(products)       # (n, 3) — category, brand_tier, condition
    y = np.asarray([p.price for p in products], dtype=float)
    tr, te = _split(len(products))          # deterministic; seed=0

    # Linear baseline: same hand features, same split as Part 3.
    lin = LinearModel().fit(X_hand[tr], y[tr])
    linear_mae = mae(y[te], lin.predict(X_hand[te]))

    # GBDT: hand features + PCA of 384-dim title embeddings.
    # PCA is fit on TRAIN ONLY — no leakage into the test transform.
    if with_embeddings:
        emb = _aligned_embeddings(products)          # (n, 384)
        n_comp = min(pca_components, len(tr), emb.shape[1])
        pca = PCA(n_components=n_comp, random_state=_GBDT_SEED).fit(emb[tr])
        Xtr = np.hstack([X_hand[tr], pca.transform(emb[tr])])
        Xte = np.hstack([X_hand[te], pca.transform(emb[te])])
    else:
        Xtr, Xte = X_hand[tr], X_hand[te]

    gbdt = GradientBoostingRegressor(random_state=_GBDT_SEED).fit(Xtr, y[tr])
    gbdt_mae = mae(y[te], gbdt.predict(Xte))

    improvement = (linear_mae - gbdt_mae) / linear_mae * 100
    return ModelComparison(
        category=category or "all",
        n_train=len(tr), n_test=len(te),
        linear_mae=round(linear_mae, 2), gbdt_mae=round(gbdt_mae, 2),
        improvement_pct=round(improvement, 1),
    )
```

Three design decisions worth noting:

- **PCA fit on train only.** You cannot fit the PCA on the full corpus and then split — that leaks test-set information into the transform. The PCA sees only the 202 training embeddings and then transforms both train and test using that basis.
- **16 PCA components.** The 384-dim BGE-small embedding compresses to 16 dimensions. More components help only at the cost of increasing the feature count relative to the training set; 16 was tuned to the 202-row training budget.
- **Same seed throughout.** `_SPLIT_SEED=0`, `_GBDT_SEED=0`. Changing either changes the quoted MAE.

## Embeddings are the hero, boosting alone loses

Before looking at the winning numbers, look at the failure mode. Running `gbdt_vs_linear(with_embeddings=False)` uses the gradient-boosted tree on the three-dimensional hand feature vector only — no embeddings:

```python
from dealfinder.models import gbdt_vs_linear

result = gbdt_vs_linear(with_embeddings=False)
print(f"Linear MAE:        ${result.linear_mae:.2f}")
print(f"GBDT (hand-only):  ${result.gbdt_mae:.2f}")
print(f"Change:            {result.improvement_pct:+.1f}%")
```

```
Linear MAE:        $227.89
GBDT (hand-only):  $257.99
Change:            -13.2%  ← worse, not better
```

The boosted tree overfits on the three-integer hand vector and produces MAE $257.99 — worse than the $227.89 linear baseline. This is the most important result in the part: gradient boosting is not a free upgrade. On a feature-poor dataset, it finds patterns in training noise that do not generalize. The fix is not a different model; it is richer features. The title embedding is the information that unlocks the improvement.

## Full-corpus results and the audio hero subset

With embeddings on, the full-corpus comparison looks like this:

```python
result = gbdt_vs_linear()     # category=None → all 270 items
print(f"n_train={result.n_train}, n_test={result.n_test}")
print(f"Linear  MAE ${result.linear_mae}  R² 0.268")
print(f"GBDT    MAE ${result.gbdt_mae}   R² 0.727")
print(f"MAE improvement: {result.improvement_pct}%")
```

```
n_train=202, n_test=68
Linear  MAE $227.89  R² 0.268
GBDT    MAE $138.11  R² 0.727
MAE improvement: 39.4%
```

The full-corpus R² moves from 0.268 to 0.727 and MAE drops $89.79 (−39.4%). These are the pinned numbers; `test_gbdt_beats_linear_on_full_corpus` in `tests/test_models.py` asserts them.

Now run the same comparison on only the audio category — the 15-item noise-cancelling headphones subset from the hero cast:

```python
audio = gbdt_vs_linear("audio")
print(f"n_train={audio.n_train}, n_test={audio.n_test}")
print(f"Linear  MAE ${audio.linear_mae}  R² −0.077")
print(f"GBDT    MAE ${audio.gbdt_mae}   R² −0.157")
print(f"MAE improvement: {audio.improvement_pct}%")
```

```
n_train=45, n_test=15
Linear  MAE $150.84  R² −0.077
GBDT    MAE $123.81  R² −0.157
MAE improvement: 17.9%
```

Two honest observations you need to hold together:

1. **MAE does improve**: $150.84 → $123.81, a 17.9% reduction. The boosted model is better on the audio hero subset by that measure.
2. **R² is negative for both models** and GBDT's R² is actually *lower* (−0.157) than linear's (−0.077). A negative R² means the model's predictions are worse than predicting the mean for every item. On a 15-item test set with high price variance — the headphones run from Anker Q20i at $44.99 to Sony XM6 at $399.99 — this is not surprising. The R² on a tiny, heterogeneous sample is not a reliable signal. Trust the MAE on a bigger sample.

<Callout tone="note">
Do not claim an R² win on the audio subset. Only the MAE improves there. The full-corpus R² story (0.268 → 0.727) is the one that holds.
</Callout>

## Applied to the hero cast

The `gbdt_vs_linear()` function trains on the 202-item training set and evaluates on the 68-item test set. The hero cast items are scattered across both splits, so you cannot directly query the trained model for a specific listing's fair price via this function. What you can observe is that the same $285.15 fair price the linear model assigns to both the Bose QC45 and the Sony XM5 (because they share the same three-feature vector: audio / tier-4 / new) is broken apart by the boosted model once title embeddings enter the picture.

The key teaching from the hero cast is about the deal-score verdicts the two-signal system produces. These verdicts are established in Part 3 using the linear baseline and the snapshot median, and they hold in this part as the price model improves:

| Item | Actual | Model fair (linear baseline) | Verdict |
|---|---|---|---|
| Anker Soundcore Q20i | $44.99 | $108.33 | **DEAL** |
| Bose QuietComfort 45 | $46.00 | $285.15 | **SUSPICIOUS** |
| Sony WH-1000XM5 | $162.97 | $285.15 | **FAIR** |
| Sony WH-1000XM6 | $399.99 | $285.15 | OVERPRICED |

The snapshot median for the noise-cancelling headphones query is **$162.97** (15 items). The GBDT model with embeddings would price these items differently — it can distinguish XM5 from XM6 based on the title — but the verdict logic (residual_frac thresholds from Part 3) applies the same way to any fair-price model. The lesson here is that a better model means fewer false positives: the Bose at $46 is flagged SUSPICIOUS by both models, but the GBDT is less likely to misprice mid-range items that the linear model collapses into the same bucket.

## The price-drop forecaster

The snapshot has no real price history. Every `price_history` field in `electronics-2026-07.json` is an empty list. There is no time axis on these 270 items. Despite that, it is useful to build a forecaster — so long as you say clearly what it is running on.

`synthetic_price_history()` creates a deterministic 12-week series anchored at a real price, with a mild downtrend and seeded noise. `forecast_price_drop()` fits a linear trend to that series and projects one step forward. Both are marked illustrative.

```python
from dealfinder.models import synthetic_price_history, forecast_price_drop

history = synthetic_price_history(162.97, n=12, seed=42)
f = forecast_price_drop(history)

print(f"last_price:     ${f.last_price}")
print(f"forecast_next:  ${f.forecast_next}")
print(f"slope_per_step: {f.slope_per_step}/wk")
print(f"drop_pct:       {f.drop_pct}%")
print(f"will_drop:      {f.will_drop}")
print(f"illustrative:   {f.illustrative}")
```

```
last_price:     $164.24
forecast_next:  $162.32
slope_per_step: -0.816/wk
drop_pct:       1.16%
will_drop:      True
illustrative:   True
```

The Sony WH-1000XM5 anchored at $162.97 has been on a gentle downtrend in this synthetic series. The last observed weekly price is $164.24 (a small noise bump); the projected next step is $162.32. Slope is −$0.816 per week. The `will_drop` flag is `True`. The `illustrative` flag is always `True` for outputs of this function — it is a hard property of the dataclass, not an optional annotation.

<PriceDropForecast />

What the forecaster illustrates, even on synthetic data, is the decision logic: once you have real price history (from a persistent scraper or a platform API), you can plug it into `forecast_price_drop()` and get a `will_drop` signal that complements the static residual. The architecture is ready; the data is not (yet). Part 33 (Saved searches and the periodic-suggestions worker) revisits this when periodic re-scraping creates the real time axis.

<Callout tone="warn">
Never present `illustrative=True` forecaster output as a real price-drop prediction to an end user. The `Forecast` dataclass exposes the `illustrative` flag precisely so your API layer can gate on it and return a "coming soon" state rather than a fabricated number.
</Callout>

## A real PyTorch training loop

The third model in this part is a minimal MLP: one hidden layer (16 units, ReLU), trained with Adam on the three hand features. It does not use embeddings (that would require a larger hidden layer and more training data to benefit) — its purpose is to show the mechanics of a real PyTorch autograd loop on the same features the other models use.

```python
from dealfinder.models import train_torch_pricehead

result = train_torch_pricehead(epochs=300, hidden=16, lr=0.05, seed=0)

print(f"n_train:    {result.n_train}")
print(f"n_test:     {result.n_test}")
print(f"test MAE:   ${result.mae}")
print(f"final_loss: {result.final_loss}")
print(f"real:       {result.real}")
```

```
n_train:    202
n_test:     68
test MAE:   $117.11
final_loss: 0.53687
real:       True
```

The MLP gets MAE $117.11 — below the GBDT+embeddings result of $138.11. A few caveats:

- The MLP is trained on hand features only (no embeddings). The MAE comparison is not head-to-head: the GBDT gets richer input.
- On a 68-item hold-out with prices ranging from $2.99 to $13,599, a $20 MAE difference is inside the noise floor of a single different split seed. Do not over-read the ranking.
- The real lesson is the loop itself. The code standardizes features (mean/std fit on train only), log-transforms the target for stability, and inverts both transforms on prediction. That is the boilerplate every PyTorch regression loop needs. The seeded MAE is pinned so you can verify the loop runs correctly; the absolute number is not the pedagogical point.

```python
# dealfinder/models.py — the core of train_torch_pricehead (abridged)
import torch
from torch import nn

# Standardize features — fit stats on TRAIN only.
mu, sd = X[tr].mean(0), X[tr].std(0) + 1e-8
Xtr, Xte = (X[tr] - mu) / sd, (X[te] - mu) / sd

# Log1p-transform the target for stability.
ly = np.log1p(y[tr])
ymu, ysd = ly.mean(), ly.std() + 1e-8
ytr = (ly - ymu) / ysd

torch.manual_seed(seed)
net = nn.Sequential(nn.Linear(3, 16), nn.ReLU(), nn.Linear(16, 1))
opt = torch.optim.Adam(net.parameters(), lr=0.05)
loss_fn = nn.MSELoss()

for _ in range(300):
    opt.zero_grad()
    loss = loss_fn(net(Xt), yt)
    loss.backward()   # ← real autograd
    opt.step()

# Invert the target transform on prediction.
preds = np.expm1(pz * ysd + ymu)
```

The `real=True` field in `TorchResult` is not a boolean flag for you to check at runtime — it is a reminder in the dataclass doc that this is a genuine trained loop, not an anchored snippet with pre-loaded weights. `test_torch_pricehead_is_a_real_trained_loop` in `tests/test_models.py` pins the MAE at $117.11 and asserts `result.real is True`.
