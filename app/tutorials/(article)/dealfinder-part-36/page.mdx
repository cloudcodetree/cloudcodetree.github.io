## Why e2e, load, and chaos are three different things

Unit and integration tests — you have 166 of them — check that individual components behave correctly in isolation or in controlled combinations. They do not prove that the browser can actually render a deal card, that the system holds up under concurrent load, or that the circuit breaker fires correctly when a source goes dark at runtime.

Each layer tests something the others cannot:

| Layer | What it tests | Runs offline? | Gate in CI? |
|---|---|---|---|
| Unit / integration (pytest) | Component contracts, hero-cast invariants | Yes | Yes — blocks merge |
| Playwright e2e (hermetic) | Browser → UI contract; badge taxonomy | Yes (stubbed) | Yes — blocks merge |
| Playwright e2e (live) | Full stack: browser → API → live sources | No (`E2E_LIVE=1`) | No — human decision |
| Load test (loadtest.py) | Throughput, latency distribution | No (needs uvicorn) | No — run before release |
| Chaos (pytest, offline) | Circuit breaker invariants, empty envelope | Yes | Yes — blocks merge |

The offline layers belong in CI. The live layers are human checkpoints: you run them before a release cut, not on every commit.

## Playwright: guarding the badge contract

The most important thing the frontend must not break is the §9.7 badge contract: exactly four tokens, no synonyms, each mapping deterministically to its colour in `DealBadge.ts`. Playwright tests this contract at the browser level, where a typo in a CSS class or a renamed constant would otherwise only surface in production.

`frontend/e2e/search.spec.ts` covers five cases:

```typescript
// frontend/e2e/search.spec.ts (abridged)
import { test, expect } from '@playwright/test';
import { stubSearch, BADGE_TOKENS, SEARCH_RESPONSE, EMPTY_RESPONSE } from './fixtures';

test.describe('search results', () => {
  test('renders result cards, each carrying a §9 badge', async ({ page }) => {
    await stubSearch(page, SEARCH_RESPONSE);
    await page.getByRole('textbox', { name: /search for a product/i }).fill('headphones');
    await page.getByRole('button',  { name: /search/i }).click();

    const cards = page.getByTestId('result-card');
    await expect(cards).toHaveCount(SEARCH_RESPONSE.results.length);

    for (const card of await cards.all()) {
      const badge = await card.getAttribute('data-badge');
      expect(BADGE_TOKENS).toContain(badge);
    }
  });

  test('badge taxonomy is EXACTLY the four §9 tokens — no synonyms', async ({ page }) => {
    await stubSearch(page, SEARCH_RESPONSE);
    // … fills + clicks …
    const badges = await page.locator('[data-badge]').allInnerTexts();
    for (const b of badges) {
      expect(['DEAL', 'FAIR', 'SUSPICIOUS', 'OVERPRICED']).toContain(b.trim());
    }
  });
  // … 3 more cases …
});
```

<E2ETestLattice />

The test that catches the most regressions in practice is the "badge taxonomy" case — it is a closed-set assertion. If a future commit renames `SUSPICIOUS` to `WARNING` (a common temptation when softening copy), this test fails before the PR merges.

## Fixtures: hermetic e2e without a live backend

Running e2e tests against a live backend makes them slow, flaky, and dependent on API quotas. `frontend/e2e/fixtures.ts` solves this by giving each test a controlled, hermetic environment.

```typescript
// frontend/e2e/fixtures.ts (key excerpts)
export const BADGE_TOKENS = ['DEAL', 'FAIR', 'SUSPICIOUS', 'OVERPRICED'] as const;

export const SEARCH_RESPONSE = {
  count: 4,
  results: [
    { id: 'a', title: 'Sony WH-1000XM5',       price: 162.97, deal_pct:   0, verdict: 'FAIR'       },
    { id: 'b', title: 'Anker Soundcore Q20i',   price:  44.99, deal_pct:  72, verdict: 'DEAL'       },
    { id: 'c', title: 'Bose QuietComfort 45',   price:  46.00, deal_pct:  72, verdict: 'SUSPICIOUS' },
    { id: 'd', title: 'Sony WH-1000XM6',        price: 399.99, deal_pct: -30, verdict: 'OVERPRICED' },
  ],
  median_price: 162.97,
};

export const EMPTY_RESPONSE = { count: 0, results: [], median_price: 0 };

/**
 * Aborts the SSE stream (**/search/stream*) so the frontend falls back to
 * GET /search, then fulfills that request with the supplied fixture.
 * Net effect: hermetic test, no backend, exercises the SSE-abort fallback path.
 */
export async function stubSearch(page: Page, body: object) {
  await page.route('**/search/stream*', (route) => route.abort());
  await page.route('**/search*',        (route) =>
    route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify(body) }),
  );
}
```

The `stubSearch` helper does two things at once: it proves the SSE abort fallback works (because the SSE route is explicitly aborted, the frontend *must* fall through to the plain fetch), and it keeps the test fast and repeatable.

<Callout tone="note">
The fixture includes one offer from each of the four badge tiers — one representative per tier is enough to test the closed set. The fixture deliberately matches the hero cast: Sony XM5 at $162.97, Anker Q20i at $44.99, Bose QC45 at $46, Sony XM6 at $399.99.
</Callout>

## The live spec: opt-in backend smoke test

`frontend/e2e/live.spec.ts` has a single test gated on the `E2E_LIVE` environment variable. It does what the hermetic suite cannot: confirms that a real query through the full stack produces real cards with valid §9 badges.

```typescript
// frontend/e2e/live.spec.ts
import { test, expect } from '@playwright/test';
import { BADGE_TOKENS } from './fixtures';

test.describe('live backend', () => {
  test.skip(!process.env.E2E_LIVE, 'set E2E_LIVE=1 to run against the live backend');

  test('real search renders cards with valid §9 badges', async ({ page }) => {
    await page.goto('/');
    await page.getByRole('textbox', { name: /search for a product/i }).fill('noise cancelling headphones');
    await page.getByRole('button',  { name: /search/i }).click();

    await page.waitForSelector('[data-testid="result-card"]', { timeout: 30_000 });

    for (const card of await page.getByTestId('result-card').all()) {
      const badge = await card.getAttribute('data-badge');
      expect(BADGE_TOKENS).toContain(badge);
    }
  });
});
```

Run it before a release:

```bash
# Start the backend first
uvicorn dealfinder.api:app --port 8000

# In a second terminal, run the full suite including live
E2E_LIVE=1 npm run test:e2e:live
```

The live test is not gated in CI because it would require live API keys and a running server in every build. It is a human checkpoint. Run it on a staging environment before cutting a release tag.

## Load testing: what the numbers actually mean

`scripts/loadtest.py` measures raw throughput and latency against a locally-running server. It is a measurement tool, not a pass/fail gate. The numbers below are **measured locally against `uvicorn` with live sources active, concurrency 6, 60 requests** — they are anchored figures, not production SLAs. Re-measure in your own environment.

```bash
# Start the backend
uvicorn dealfinder.api:app --host 127.0.0.1 --port 8000

# Run the load test (defaults: 60 req, concurrency 8, query "noise cancelling headphones")
python scripts/loadtest.py --requests 60 --concurrency 6
```

Anchored results from a local run (measured-locally, live sources active). Read the percentile columns as "N% of requests finished at or under this time": p50 is the median (typical) request, p95 is what 1-in-20 users experience, p99 the 1-in-100 worst case. Latency work always reports percentiles instead of averages because the average hides the tail — one 25-second straggler barely moves the mean but is a real user staring at a spinner:

| Endpoint | p50 | p95 | p99 | Throughput |
|---|---|---|---|---|
| `GET /healthz` | 2.4 ms | 136.6 ms | 137.3 ms | 346 req/s |
| `GET /search`  | 10.1 s | 21.9 s | 25.2 s | 0.2 req/s |

The `/search` latency is dominated by the live retailer fan-out — the system is waiting for real HTTP responses from the upstream sources. 17 of 60 requests timed out under concurrency 6. That is not a bug: the circuit breaker correctly identifies and benches slow sources after COOLDOWN_SECONDS = 90, and the timeout policy is intentionally tight to bound tail latency. The `/healthz` numbers are what a health probe should see: sub-millisecond in steady state, with a long tail only when the process is under concurrent search load.

<Callout tone="warn">
Do not treat these numbers as a production SLA. They are a single local measurement against a laptop uvicorn instance with live APIs. A production deployment (Kubernetes, connection pooling, a CDN in front of static assets) will read differently. Use the load test to catch regressions in your own environment before a release — not to make capacity commitments.
</Callout>

## Chaos testing: the circuit breaker under fire

The load test shows what the system does under normal-ish concurrency. The chaos tests show what it does when sources fail. First, the pattern being tested — the state machine from Part 9, because the chaos invariants below are assertions about its transitions:

<CircuitStates />

`tests/test_chaos.py` runs entirely offline using mocked sources and exercises the circuit breaker's invariants directly:

```python
# tests/test_chaos.py (representative excerpts)
import pytest
from unittest.mock import MagicMock
from dealfinder.aggregate import Aggregator

COOLDOWN_SECONDS = 90.0  # pinned constant from aggregate.py

def test_one_source_raising_does_not_break_search():
    """A source that raises should not propagate; healthy sources still serve."""
    bad_source   = MagicMock(spec=DealSource, available=lambda: True)
    bad_source.products.side_effect = RuntimeError("connection refused")
    good_source  = MagicMock(spec=DealSource, available=lambda: True,
                             products=lambda: [make_product(price=44.99)])

    agg    = Aggregator(sources=[bad_source, good_source])
    result = agg.search("noise cancelling headphones")

    assert result["count"] == 1
    assert result["results"][0]["price"] == 44.99
    assert bad_source.id in result["throttled"]

def test_all_sources_down_returns_well_formed_empty_envelope():
    """All sources failing → empty envelope, never a 500."""
    sources = [MagicMock(spec=DealSource, available=lambda: True,
                         products=MagicMock(side_effect=RuntimeError("timeout")))
               for _ in range(3)]

    agg    = Aggregator(sources=sources)
    result = agg.search("headphones")

    assert result["count"]        == 0
    assert result["results"]      == []
    assert result["median_price"] == 0.0
    assert set(result["throttled"]) == {s.id for s in sources}
    # No exception raised — this is the key invariant.
```

All five tests pass offline in 0.08 seconds:

<ChaosBreaker />

The pinned invariants the chaos tests exercise:

- **COOLDOWN_SECONDS = 90.0** — a raising or timing-out source is added to `agg._cooldown` and excluded from the next search within that window. The constant is pinned in `aggregate.py` and asserted by the test that reads it directly from the module.
- **One bad source → healthy sources serve** — `count` and `results` contain the healthy-source data; the failing source appears in `throttled[]`.
- **Lower-tier source absorbs a failed same-tier source** — when a tier-1 source fails, a tier-2 source picks up the slot; cheapest-first ordering is preserved.
- **All sources down → well-formed empty envelope** — `{count: 0, results: [], median_price: 0.0, sources_live: [], throttled: [...all...]}`. No exception, no 500.

<Callout tone="note">
The "unavailable-only" case (`available() == False` without an error) returns the same empty envelope but with `throttled == []` — the source was never attempted, so it is not logged as throttled. This distinction matters for alerting: throttled sources indicate a runtime failure that triggered the breaker, not a pre-flight check that excluded the source.
</Callout>

## The runbook

`RUNBOOK.md` is the document on-call consults when an alert fires. A runbook that lives only in someone's head is not a runbook. The key sections:

### Health endpoints

Check these first on any incident:

```bash
curl http://your-host/healthz          # { "status": "ok" }
curl http://your-host/sources          # per-source live/throttled state
curl 'http://your-host/search?q=headphones&limit=3'  # end-to-end smoke test
curl 'http://your-host/deal?id=<id>'   # deal-score calculation
curl http://your-host/me               # auth context (requires token)
```

A degraded `/healthz` with `sources` showing one source throttled is normal — the circuit breaker is working. Multiple sources throttled simultaneously, or `/search` returning only empty envelopes, is the escalation signal.

### Alerts and thresholds

| Alert | Condition | First action |
|---|---|---|
| High error rate | `error_rate > 1%` over 5 min | Check `/sources` for throttled count; tail app logs for the root exception |
| `/search` p95 high | p95 > 30 s | Check retailer API status pages; inspect `throttled[]` in `/sources` |
| Breaker trips | `agg._cooldown` size spikes | Expected under source outage; escalate if all sources throttled simultaneously |
| Budget alert | `ops.CostTracker / budget_status` approaching limit | Review `GET /me` call volume; apply rate limit adjustments from Part 35 |
| PSI drift | `PSI ≥ 0.2` (from Part 24) | Trigger retrain pipeline; eval gate (precision@5 ≥ 0.80) must pass before promotion |
| Billing quota | `billing.QuotaExceeded` in logs | Pause new Stripe subscriptions; check metering lag from Part 34 |

### Rollback

Three rollback paths depending on where the failure is:

```bash
# Kubernetes: roll back to the previous deployment
kubectl rollout undo deployment/dealfinder-api

# Terraform: revert infrastructure changes
terraform plan -target=<resource>   # confirm scope
terraform apply -target=<resource>  # with previous .tfvars

# Render (if using render.yaml): re-deploy the last known-good commit
git revert HEAD && git push         # triggers auto-deploy
```

### Incident template

Each incident gets a brief written record: timestamp, symptom, root cause, mitigation, and a "what to pin in CI" item. The last field is the one most teams skip — and the one that prevents recurrence. If the chaos test suite would have caught this failure, write the test. If the load test would have flagged the regression, add a latency assertion to the pre-release checklist.
