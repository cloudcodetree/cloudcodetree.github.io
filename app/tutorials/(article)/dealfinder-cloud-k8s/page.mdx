# Cloud & Kubernetes

**TL;DR: Take the Docker image from Part 28 and run it on a real cluster. Eight Kubernetes manifests give you a hardened, autoscaling deployment with TLS at the ingress, SSE buffering disabled so the Part 31 stream endpoint stays live, and secrets that never touch a committed file.**

Part 28 proved that the DealFinder container is portable — same bits across dev, staging, and prod. This part proves it is *operable*: health-checked, horizontally autoscaled, TLS-terminated, and connected to a managed external Postgres rather than an in-cluster database that would become a single point of failure. The cluster stays stateless; the database stays managed. That design decision is visible in every manifest.

## The eight manifests at a glance

The `infra/k8s/` directory contains exactly eight YAML files:

| File | Kind | Purpose |
|---|---|---|
| `namespace.yaml` | `Namespace` | Isolate every resource under `dealfinder` |
| `configmap.yaml` | `ConfigMap` | Non-secret runtime config (Apify actor, port, log level) |
| `secret.example.yaml` | `Secret` | Placeholder template — filled copy is gitignored |
| `deployment.yaml` | `Deployment` | The app: 2 replicas, healthz probes, envFrom, hardened securityContext |
| `service.yaml` | `Service` | ClusterIP, port 80 → container 8000 |
| `ingress.yaml` | `Ingress` | TLS, nginx annotations for SSE, host `api.dealfinder.example.com` |
| `hpa.yaml` | `HorizontalPodAutoscaler` | CPU-driven autoscale 2 → 10 replicas |
| `kustomization.yaml` | `Kustomization` | Wires all the above; explicitly excludes the secret template |

All eight files parse cleanly — validated with `yaml.safe_load_all` against every manifest in the repo. The `secret.yaml` you create from the template is not in the list because it is gitignored and applied separately.

<Callout tone="note">
**Verification used here is YAML well-formedness only** — `yaml.safe_load_all` on each file. No live cluster was used. To test against a real cluster, run `kubectl apply --dry-run=server -k infra/k8s/` after filling in your `secret.yaml` and pointing at a cluster.
</Callout>

## Namespace and ConfigMap — separating config from secrets

Every manifest carries `namespace: dealfinder`. The `Namespace` resource creates that isolation:

```yaml
# infra/k8s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dealfinder
```

The `ConfigMap` holds everything that is not a secret:

```yaml
# infra/k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: dealfinder-config
  namespace: dealfinder
data:
  SHOPIFY_STORES: ""
  APIFY_ACTOR: "automation-lab~google-shopping-scraper"
  PORT: "8000"
  LOG_LEVEL: "info"
```

`SHOPIFY_STORES` is blank — the app uses its built-in list. `APIFY_ACTOR` names the Apify actor for the Google Shopping source (same value used in the Part 9 scraping connector). `PORT` and `LOG_LEVEL` are Uvicorn/app tuning knobs you can change per environment without rebuilding the image.

The `Deployment` mounts both this ConfigMap and the Secret via `envFrom`, so the app sees all of them as ordinary environment variables:

```yaml
envFrom:
  - configMapRef:
      name: dealfinder-config
  - secretRef:
      name: dealfinder-secrets
```

Non-secret config in the ConfigMap, secrets in the Secret — nothing sensitive in a ConfigMap.

## Secrets — the template pattern

<SecretFlow />

The committed file is a template:

```yaml
# infra/k8s/secret.example.yaml  — PLACEHOLDERS ONLY, safe to commit
apiVersion: v1
kind: Secret
metadata:
  name: dealfinder-secrets
  namespace: dealfinder
type: Opaque
stringData:
  DATABASE_URL: "postgresql://USER:PASSWORD@your-managed-pg-host:5432/dealfinder"
  SUPABASE_JWT_SECRET: "REPLACE_WITH_SUPABASE_JWT_SECRET"
  STRIPE_SECRET_KEY: "sk_test_REPLACE_ME"
  STRIPE_PRICE_PRO: "price_REPLACE_ME"
  STRIPE_WEBHOOK_SECRET: "whsec_REPLACE_ME"
  RAPIDAPI_KEY: ""
  APIFY_TOKEN: ""
  FIRECRAWL_API_KEY: ""
  OPENROUTER_API_KEY: ""
  BESTBUY_API_KEY: ""
  EBAY_APP_ID: ""
  EBAY_CERT_ID: ""
  EBAY_CAMPAIGN_ID: ""
```

The template uses `stringData` (plain text; Kubernetes base64-encodes on apply) so you can read and edit it without base64 gymnastics. Blank keys for live sources (`RAPIDAPI_KEY: ""`) simply disable that source — the aggregator degrades gracefully.

The workflow for applying it:

```bash
# 1. Copy the template
cp infra/k8s/secret.example.yaml infra/k8s/secret.yaml

# 2. Edit with your real values — never commit this file
#    infra/k8s/.gitignore already lists secret.yaml

# 3. Apply it out-of-band — separately from the kustomize stack
kubectl apply -f infra/k8s/secret.yaml

# 4. Apply the rest of the stack (kustomization.yaml excludes secret.example.yaml)
kubectl apply -k infra/k8s/

# 5. Delete the local filled copy (or rotate it to a secrets manager)
rm infra/k8s/secret.yaml
```

`DATABASE_URL` is the most important secret. It points at your managed external Postgres — Supabase connection pooler, Amazon RDS, Neon, or any pgvector-capable host. The cluster does not run a database; `DATABASE_URL` is the only connection the app needs.

<Callout tone="warn">
**In production, prefer a real secrets manager.** The filled-and-applied `secret.yaml` pattern is fine for learning and low-scale deploys. For production use External Secrets Operator (syncs from AWS Secrets Manager / GCP Secret Manager), Sealed Secrets, or SOPS. All three give you secrets-as-code without committing plaintext.
</Callout>

## Deployment — health checks, resources, and hardened securityContext

Before reading the manifest, fix the mental model — a `Deployment` is not a command Kubernetes runs once, it is a target a controller chases forever:

<K8sReconcile />

The `Deployment` is where most of the operability decisions live:

```yaml
# infra/k8s/deployment.yaml (abridged)
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: app
          image: ghcr.io/cloudcodetree/dealfinder-app:latest
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8000
          envFrom:
            - configMapRef:
                name: dealfinder-config
            - secretRef:
                name: dealfinder-secrets
          readinessProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3
          resources:
            requests:
              cpu: "100m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL
```

Walk through the key decisions:

**Image.** `ghcr.io/cloudcodetree/dealfinder-app:latest` is the image built by the Part 28 CI pipeline and pushed to GitHub Container Registry. In your own cluster, replace the registry prefix with wherever you pushed it. Pin by digest (`@sha256:...`) for reproducibility in production.

**Two probes, different timings.** The readiness probe starts after 5 seconds and polls every 10 seconds — it controls whether traffic is routed to the pod. The liveness probe starts after 15 seconds (letting the app finish startup) and polls every 20 seconds — it controls whether the pod is restarted. Both call `/healthz`, the real health endpoint in `dealfinder/serve.py`. A pod that is live but not ready receives no traffic; a pod that fails liveness is restarted.

**Resource requests and limits.** `requests` are what the scheduler uses when placing pods — a node must have at least 100 m CPU and 256 Mi memory free. `limits` cap what the pod can consume. The HPA's utilisation percentage is measured against the *request*, not the limit: a pod using 70 m of CPU is at 70% utilisation (70 m ÷ the 100 m request) even though it is well under its 500 m limit. Set the request too high and the HPA never scales out; too low and it scales out constantly. Setting requests accurately is what makes the HPA's 70% target meaningful.

**securityContext.** `allowPrivilegeEscalation: false` prevents the process from gaining more privileges than it starts with (no `setuid` binaries). `capabilities.drop: [ALL]` drops every Linux capability — the FastAPI server does not need any. The Dockerfile runs as root, so `runAsNonRoot` is not set; adding a non-root `USER` to the Dockerfile is the next hardening step.

## Service and Ingress — TLS and SSE-safe buffering

The `Service` exposes the deployment inside the cluster:

```yaml
# infra/k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: dealfinder-app
  namespace: dealfinder
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: dealfinder
    app.kubernetes.io/component: api
  ports:
    - name: http
      port: 80
      targetPort: http
```

`ClusterIP` makes the service reachable only within the cluster, on port 80. External traffic arrives via the Ingress.

The `Ingress` has two decisions that matter for DealFinder specifically:

```yaml
# infra/k8s/ingress.yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
spec:
  ingressClassName: nginx
  rules:
    - host: api.dealfinder.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: dealfinder-app
                port:
                  name: http
  tls:
    - hosts:
        - api.dealfinder.example.com
      secretName: dealfinder-tls
```

**SSE annotations.** The Part 31 `/search/stream` endpoint returns an `EventSource` stream — Server-Sent Events. If the proxy buffers the response, the browser sees nothing until the buffer flushes, which defeats the point of streaming. `proxy-buffering: "off"` disables nginx buffering for all paths. `proxy-read-timeout: "3600"` prevents nginx from closing the connection mid-stream on a slow query (the default is 60 seconds). If you skip these two annotations, streaming search silently degrades to a buffered response — the browser receives results in one batch at the end, looking like a slow plain JSON call.

**TLS.** `tls[].secretName: dealfinder-tls` tells nginx-ingress where to find the certificate. Provision it with cert-manager (a `Certificate` resource pointing at Let's Encrypt) or your cloud's certificate controller. TLS termination happens at the ingress; traffic inside the cluster (ingress → service → pod) is plain HTTP.

<Callout tone="tip">
If you are on a cloud provider (EKS, GKE, AKS), swap `ingressClassName: nginx` for the platform's ingress class and translate the annotations to the platform's equivalents — for example, AWS ALB uses `alb.ingress.kubernetes.io/target-type: ip` and does not need `proxy-buffering` because ALBs do not buffer SSE.
</Callout>

## HPA — autoscale on CPU, guard scale-in with a stabilisation window

<K8sReplicaSpread />

```yaml
# infra/k8s/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: dealfinder-app
  namespace: dealfinder
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: dealfinder-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120
```

Each number is a deliberate choice:

**`minReplicas: 2`.** One replica is a single point of failure — a node drain, rolling update, or health-check restart takes the service down. Two replicas at minimum means a rolling update keeps at least one pod live.

**`maxReplicas: 10`.** A ceiling prevents runaway scaling from a traffic spike or a CPU-heavy bug (infinite loop in an extractor, for example) from consuming the whole cluster. Ten is a reasonable ceiling for a single-service API; raise it when load tests in Part 36 tell you the actual peak.

**`averageUtilization: 70`.** The HPA targets 70% of the CPU *request* (100 m) across all pods. At 70 m average, the HPA is satisfied. If the average climbs above 70 m, the HPA schedules more pods. Choosing 70% leaves 30% headroom — a sudden traffic spike can be absorbed by the existing pods while the new ones start up (readiness probe delays ~5 seconds).

**`stabilizationWindowSeconds: 120`.** Without this, the HPA would start scaling in as soon as CPU drops below 70%, potentially thrashing — spin up 5 pods, traffic dips, spin down to 2, traffic returns, spin up again. A 120-second window makes scale-in wait until the average has been below threshold for two continuous minutes. Scale-out has no window (the default is 0 seconds) so it responds immediately to spikes.

The Metrics Server must be installed in your cluster for the HPA to function. Most managed Kubernetes offerings (EKS, GKE, AKS) include it. If `kubectl top pods` returns an error, the Metrics Server is missing.

## Kustomization — apply everything, exclude the secret template

```yaml
# infra/k8s/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: dealfinder
resources:
  - namespace.yaml
  - configmap.yaml
  - deployment.yaml
  - service.yaml
  - ingress.yaml
  - hpa.yaml
commonLabels:
  app.kubernetes.io/name: dealfinder
  app.kubernetes.io/part-of: dealfinder
```

Two things to notice:

`secret.example.yaml` is **not** in the resources list. The template should never be applied — it holds placeholder strings, not real values. If you `kubectl apply -k .` with the template in the list, Kubernetes creates a Secret with the literal string `"REPLACE_WITH_SUPABASE_JWT_SECRET"`, and the auth middleware will fail immediately.

`commonLabels` stamps every resource with `app.kubernetes.io/name: dealfinder` and `app.kubernetes.io/part-of: dealfinder`. The HPA uses these labels to find the target Deployment. The Prometheus/Grafana stack in Part 30 uses them to scope metrics queries to this service.

## Apply the stack

With your cluster configured and `secret.yaml` filled in:

```bash
# 0. Build and push the image (Part 28 CI does this automatically on push to main)
docker build -t ghcr.io/<your-org>/dealfinder-app:latest .
docker push ghcr.io/<your-org>/dealfinder-app:latest

# 1. Apply the secret out-of-band (not via kustomize — it is gitignored)
kubectl apply -f infra/k8s/secret.yaml

# 2. Apply the rest of the stack
kubectl apply -k infra/k8s/

# 3. Watch the rollout
kubectl rollout status deployment/dealfinder-app -n dealfinder

# 4. Check that both pods are ready and passing health checks
kubectl get pods -n dealfinder
```

Expected output from step 4:

```
NAME                              READY   STATUS    RESTARTS   AGE
dealfinder-app-7f9d4b8c9-k2xzp   1/1     Running   0          45s
dealfinder-app-7f9d4b8c9-m9wqv   1/1     Running   0          45s
```

Both pods `1/1 Running`. If you see `0/1` in the READY column, check the readiness probe: `kubectl describe pod <name> -n dealfinder` will show the probe result and any error from `/healthz`.

Once the pods are running, verify the ingress:

```bash
# Smoke-test the health endpoint through the ingress
curl -s https://api.dealfinder.example.com/healthz
# {"status":"ok","products":<n>}

# Smoke-test the noise-cancelling headphones search (needs live-source keys in the Secret)
curl -s "https://api.dealfinder.example.com/search?q=noise+cancelling+headphones" \
  | python3 -m json.tool | head -30
```

<Callout tone="note">
**Live keys required for the search endpoint.** The `/healthz` check runs without any keys. The `/search` endpoint needs at least one live-source key (`RAPIDAPI_KEY`, `APIFY_TOKEN`, or similar) populated in the Secret, or it returns an empty result set. The hero cast — Sony WH-1000XM5 at $162.97, Anker Q20i at $44.99 — comes from those live sources; the snapshot does not back the API server.
</Callout>

Verify the HPA is tracking CPU:

```bash
kubectl get hpa -n dealfinder
# NAME              REFERENCE                    TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# dealfinder-app    Deployment/dealfinder-app    12%/70%   2         10        2          2m
```

`12%/70%` means 12% average CPU utilisation against the 70% target — comfortably idle. Send a load test (Part 36 uses k6 for this) and watch `REPLICAS` climb.

These are not niceties — they are the difference between a demo and a service.
