## Why a UI at this point

The agent (Part 11) and MCP server (Part 12) let programs call DealFinder. The pgvector store (Part 13) persists everything ever searched so results can be queried by meaning rather than exact keyword. But neither of those surfaces is something you hand to a user and say "run this."

A web UI closes the loop. It also reveals the shape of the backend from the outside: what a 2–4 second multi-source aggregation call feels like to a real user, and whether the two-signal deal score is legible in a card layout. Both observations will feed back into Parts 22–27.

The deliberate constraint — Vanilla JS, no build step, served from the same FastAPI origin — keeps the part focused on the backend SSE pattern. Part 27 (Front end for real) replaces the static HTML with React/Next.js, server components, and proper state management. That context is explicit here so learners know this is a simplification, not the final shape.

## What the server already gives you

`dealfinder/serve.py` already exists after Part 13. Reading it from the top:

```python
# dealfinder/serve.py
from fastapi import FastAPI, HTTPException
from fastapi.responses import HTMLResponse

from . import pgstore
from .aggregate import aggregate
from .deal import deal_score
from .dealmodel import LinearModel
from .features import feature_matrix
from .live_sources import LIVE_SOURCES
from .tools import load_catalog

app = FastAPI(title="DealFinder")

_DB = bool(os.getenv("DATABASE_URL"))
if _DB:
    try:
        pgstore.migrate()
    except Exception:
        _DB = False
```

At module import time the server checks whether `DATABASE_URL` is set. If it is, it calls `pgstore.migrate()` (which creates the `products` table and HNSW index if they don't already exist — see Part 13). If the env var is missing or the connection fails, `_DB` is set to `False` and the server degrades gracefully: live search still works, the `/semantic` endpoint returns a 503.

```python
_catalog = load_catalog()
_idx = {p.id: i for i, p in enumerate(_catalog)}
_X = feature_matrix(_catalog)
_model = LinearModel().fit(_X, [p.price for p in _catalog])
_fair = {p.id: float(fp) for p, fp in zip(_catalog, _model.predict(_X))}
```

The snapshot catalog, feature matrix, and linear model are all loaded once at startup. `_fair` is a dict mapping product id to the model's predicted fair price — used by the `/deal/{product_id}` endpoint and available to the SSE endpoint once you add it.

The existing endpoints are:

```python
@app.get("/healthz")           # status + item count
@app.get("/search")            # live aggregate → persist + embed if DB present
@app.get("/semantic")          # pgvector nearest-neighbour search (503 without DB)
@app.get("/sources")           # which live sources are currently configured
@app.get("/", response_class=HTMLResponse)   # serves static/index.html
@app.get("/deal/{product_id}") # per-item fair price + deal score
```

This part adds one new endpoint (`/search/stream`) and one `StaticFiles` mount. Everything else is wired already.

## Serving the static front end

The `home()` endpoint already reads `static/index.html` from the package directory and returns it as HTML:

```python
@app.get("/", response_class=HTMLResponse)
def home():
    return (Path(__file__).parent / "static" / "index.html").read_text()
```

That is sufficient for the root route. But the CSS and any future assets (a favicon, a loading spinner SVG) would each need their own explicit route. The cleaner approach is a `StaticFiles` mount on a sub-path, added after the explicit routes so it cannot shadow them:

```python
from fastapi.staticfiles import StaticFiles

# mount AFTER all explicit routes so /search, /semantic, /sources are not shadowed
app.mount(
    "/static",
    StaticFiles(directory=str(Path(__file__).parent / "static")),
    name="static",
)
```

After this mount, the browser can fetch `/static/icon.svg` or any file you drop in `dealfinder/static/` without adding a Python route. The `index.html` itself stays served from `GET /` via the `home()` handler — that explicit route wins over the mount for the root path.

Start the server:

```bash
uvicorn dealfinder.serve:app --reload
```

Open `http://localhost:8000`. The search form appears. Before wiring the SSE endpoint, every search uses a single `fetch()` call to `/search` — the result arrives all at once after the slowest source finishes.

## Request/response vs. SSE

The existing `/search` endpoint calls `aggregate(q)`, which fans out across all live sources, waits for all of them, deduplicates, and returns one JSON payload. If Google Shopping takes 340 ms and the Best Buy scraper takes 890 ms, the browser waits the full 890 ms before rendering anything.

<SSEStream />

Server-Sent Events (SSE) let the server push partial payloads over a single long-lived HTTP connection. The browser opens `EventSource("/search/stream?q=...")` and receives a `data:` event each time a source batch finishes. The first cards appear at ~340 ms — 550 ms before the slow source finishes. Total round-trip is unchanged; perceived latency drops by more than half.

The browser's `EventSource` API is the right tool here because the data flows in one direction (server → browser) and reconnects automatically on failure. WebSockets are bidirectional and heavier; there is no input from the browser during a search stream.

<Callout tone="warning">
**Safari and EventSource.** Safari 14+ supports `EventSource`, but its close-and-reconnect behaviour differs from Chrome and Firefox when the connection drops mid-stream. This part uses a single SSE connection per query (opened on submit, closed on the `done` event) rather than a persistent connection, which avoids the reconnect edge case. If your users include iOS 13 or earlier, add a polyfill.
</Callout>

## The SSE endpoint: async generator pattern

Add the `/search/stream` endpoint to `serve.py`. It wraps the existing synchronous `aggregate()` call in an async generator that yields progress events as each source responds:

```python
# dealfinder/serve.py  (step-30 addition)
import asyncio
import json
from fastapi.responses import StreamingResponse

async def _aggregate_stream(q: str):
    """Yield SSE-formatted lines from the tiered aggregator, source by source."""
    from .live_sources import LIVE_SOURCES
    from .aggregate import _tier, _benched, _bench
    from .ingest import dedup_key

    best: dict[str, object] = {}
    total = 0

    for tier in sorted({_tier(s) for s in LIVE_SOURCES}):
        for src in (s for s in LIVE_SOURCES if _tier(s) == tier and s.available() and not _benched(s.name)):
            try:
                found = await asyncio.get_event_loop().run_in_executor(
                    None, lambda s=src: s.search(q)
                )
                batch_new = 0
                for p in found:
                    k = dedup_key(p)
                    if k not in best or p.price < best[k].price:
                        best[k] = p
                        batch_new += 1
                total += batch_new
                payload = json.dumps({
                    "source": src.name,
                    "count": len(found),
                    "deduped_new": batch_new,
                    "results": [p.__dict__ for p in found],
                })
                yield f"data: {payload}\n\n"
            except Exception:
                _bench(src.name)

    yield f"data: {json.dumps({'done': True, 'total': total})}\n\n"


@app.get("/search/stream")
async def search_stream(q: str):
    return StreamingResponse(
        _aggregate_stream(q),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",   # disable nginx buffering if proxied
        },
    )
```

Key points:

- `run_in_executor` moves the blocking `src.search()` call off the event loop. The aggregator sources use `httpx` in synchronous mode (inherited from `aggregate.py`); making each call non-blocking without a full async rewrite is the pragmatic choice here.
- `X-Accel-Buffering: no` disables nginx response buffering if the app is behind a reverse proxy. Without it, the browser receives all events at once at the end — defeating the purpose.
- The `done` event is the terminal signal. The JavaScript client closes the `EventSource` connection when it receives it.

## The EventSource client

`dealfinder/static/index.html` already has the form, CSS, and a `run()` function that calls `/search` directly. The `step-30` change replaces that function with one that opens an `EventSource` connection and appends cards as events arrive:

```javascript
// dealfinder/static/index.html  (step-30, SSE path in run())
async function run(q) {
  const m = mode();
  if (m === "meaning") {
    // semantic path: single fetch, no SSE
    const r = await fetch("/semantic?q=" + encodeURIComponent(q));
    const d = await r.json();
    renderCards(d.results);
    return;
  }

  // live path: open SSE connection
  const url = "/search/stream?q=" + encodeURIComponent(q);
  const es  = new EventSource(url);

  es.addEventListener("message", (e) => {
    const data = JSON.parse(e.data);
    if (data.done) {
      es.close();
      return;
    }
    // append cards from this batch
    if (data.results) {
      data.results.forEach(p => {
        document.getElementById("grid").insertAdjacentHTML("beforeend", card(p));
      });
    }
  });

  es.addEventListener("error", () => es.close());
}
```

`EventSource` opens a `GET` request with `Accept: text/event-stream`. The browser parses the `data: <json>\n\n` framing automatically — you just get parsed strings in the `message` event. The `close()` call on the `done` event is important: without it, the browser would try to reconnect (the default `EventSource` retry behaviour) and issue a new search immediately.

## The live/semantic mode toggle

The form has two radio buttons: `live deals` and `by meaning (saved)`.

```html
<div style="display:flex;gap:16px;...">
  <label><input type="radio" name="mode" value="live" checked> live deals</label>
  <label><input type="radio" name="mode" value="meaning"> by meaning (saved)</label>
</div>
```

`mode()` reads the checked value. The `run()` function branches:

- `live` → SSE stream from `/search/stream` (tiered aggregator, real-time Google Shopping + Best Buy)
- `meaning` → single `fetch()` to `/semantic?q=...` (pgvector nearest-neighbour over the 384-dim bge-small-en-v1.5 embeddings stored in Part 13)

<HybridFusion />

The semantic path surface is different from the keyword path in a meaningful way. Type "active noise reduction over-ear" instead of "noise cancelling headphones" — the live aggregator returns nothing (no keyword match) but pgvector finds the Sony XM5 and XM6 because their title embeddings are geometrically close to "active noise reduction over-ear" in the bge-small-en-v1.5 space. That is the semantic advantage the toggle makes tangible.

If `DATABASE_URL` is not set, the `/semantic` endpoint returns a `503`. The JavaScript in `index.html` checks for `r.status === 503` and shows an inline message: "meaning search needs a database (set DATABASE_URL)" — no unhandled error.

## Badge logic: render_badge()

The deal cards need a human-readable verdict: **DEAL**, **FAIR**, **SUSPICIOUS**, or **OVERPRICED**. That logic lives in `dealfinder/dealscore.py`, which already has the `verdict()` function from Part 3. The `step-30` addition is a thin `render_badge()` wrapper that converts a `(deal_pct, residual_frac)` pair to the badge string:

```python
# dealfinder/dealscore.py  (step-30 addition)
SUSPICIOUS_RESIDUAL_FRAC = 0.70
DEAL_MEDIAN_FRAC         = 0.15

def render_badge(deal_pct: float, residual_frac: float) -> str:
    """Map the two-signal score to a single badge label.

    Parameters
    ----------
    deal_pct:       fraction below the same-query cross-source median
                    (positive = cheaper than median; from median_signal())
    residual_frac:  (fair_price - actual) / fair_price
                    (positive = actual is below model fair price)

    Returns
    -------
    One of: "DEAL" | "FAIR" | "SUSPICIOUS" | "OVERPRICED"
    """
    if deal_pct >= DEAL_MEDIAN_FRAC and residual_frac >= SUSPICIOUS_RESIDUAL_FRAC:
        return "SUSPICIOUS"
    if deal_pct >= DEAL_MEDIAN_FRAC:
        return "DEAL"
    if deal_pct < 0:
        return "OVERPRICED"
    return "FAIR"
```

The guard fires on `residual_frac >= 0.70` regardless of how large `deal_pct` is. The order matters: the suspicious check comes before the deal check because `SUSPICIOUS` is the condition where both signals would separately say "great deal" — it is the overriding guard, not a fallback.

The JavaScript `card()` function calls the equivalent of `render_badge()` on the client side, reading `deal_pct` and `residual_frac` directly from the API response JSON. The API adds them at `/deal/{product_id}`:

```python
@app.get("/deal/{product_id}")
def deal(product_id: str):
    if product_id not in _idx:
        raise HTTPException(status_code=404, detail="unknown product")
    p = _catalog[_idx[product_id]]
    fair = _fair[p.id]
    from .dealscore import median_signal, residual_fraction, render_badge
    m = median_signal(p.price, p.median_price_at_capture or 0.0)
    rf = residual_fraction(p.price, fair)
    return {
        "id": p.id, "title": p.title, "price": p.price,
        "fair": round(fair, 2),
        "deal_pct": round(m, 3),
        "residual_frac": round(rf, 3),
        "badge": render_badge(m, rf),
    }
```

The JavaScript `card()` template reads `p.badge` and applies a colour class.

## Worked example: "noise cancelling headphones"

Start the server with `DATABASE_URL` pointing at the pgvector instance from Part 13:

```bash
DATABASE_URL=postgresql://user:pass@localhost:5432/dealfinder \
  uvicorn dealfinder.serve:app --reload
```

Open `http://localhost:8000`, type **noise cancelling headphones**, and click Search (live mode, default).

The SSE connection opens. Three source events arrive in the browser console:

```
data: {"source": "google_shopping", "count": 12, "deduped_new": 12, "results": [...]}
data: {"source": "bestbuy_scraper",  "count": 8,  "deduped_new": 5,  "results": [...]}
data: {"done": true, "total": 17}
```

Deal cards render as each event arrives. Three hero-cast cards appear:

| Card | Price | deal_pct | residual_frac | Badge |
|---|---|---|---|---|
| Anker Soundcore Q20i | $44.99 | +0.724 (72% under $162.97 median) | +0.585 | **DEAL** |
| Sony WH-1000XM5 (Costco) | $162.97 | 0.000 (at median) | +0.428 | **FAIR** |
| Bose QuietComfort 45 | $46.00 | +0.718 (72% under median) | +0.839 | **SUSPICIOUS** |

The Anker and Bose cards have nearly identical `deal_pct` values — both sit about 72% below the $162.97 median. The `residual_frac` is what separates them: 0.585 for the Anker (model fair price $108.33, actual $44.99 — a genuine stretch below model but within range) versus 0.839 for the Bose (model fair price $285.15, actual $46.00 — a tier-4 flagship priced at 16% of its predicted value).

<DealResidual />

The Bose card renders with a warning note: "72% below median ($162.97) but $239.15 below model fair price $285.15 — verify condition before buying." That note is what `verdict().reason` from `dealscore.py` produces. The badge is SUSPICIOUS; the user is told to check the listing, not that it is definitely fake. That is the right calibration: the model knows something is off; it does not know what.

The Sony XM6 at $399.99 would appear as **OVERPRICED** — $114.84 above the $285.15 model fair price, `deal_pct = -1.454` (145% above median).

**Semantic toggle.** Click "by meaning (saved)" and resubmit. The UI fetches `/semantic?q=noise+cancelling+headphones`. pgvector queries the HNSW index over the 384-dim bge-small-en-v1.5 embeddings stored during previous live searches. The Sony XM5 and XM6 surface even if you rephrase the query as "active noise reduction over-ear wireless" — because the embeddings encode meaning, not keywords. The `similarity` score for the XM5 against that rephrased query is approximately 0.87 (cosine similarity in the bge-small-en-v1.5 space).

The SSE integration test is in `tests/test_api_sse.py`. It mocks `_aggregate_stream` with a two-source fixture and asserts that three `data:` events arrive (two source events plus the `done` event) using `httpx.AsyncClient` with `stream()`:

```python
# tests/test_api_sse.py
import json
import pytest
from httpx import AsyncClient, ASGITransport
from dealfinder.serve import app

@pytest.mark.asyncio
async def test_search_stream_events():
    events = []
    async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as client:
        async with client.stream("GET", "/search/stream?q=headphones") as r:
            assert r.headers["content-type"].startswith("text/event-stream")
            async for line in r.aiter_lines():
                if line.startswith("data: "):
                    events.append(json.loads(line[6:]))

    source_events = [e for e in events if "source" in e]
    done_events   = [e for e in events if e.get("done")]
    assert len(source_events) >= 1
    assert len(done_events) == 1
```

The snapshot median $162.97 is the stable reference for calibrating what you see in the browser.
