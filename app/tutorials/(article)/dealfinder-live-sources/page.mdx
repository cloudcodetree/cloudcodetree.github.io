## Why three sources

The snapshot contains 270 items across 18 queries. For the anchor query `"noise cancelling headphones"` the subset is 15 items — all sourced from Google Shopping via RapidAPI and Apify. eBay (zero rows) and BestBuy (zero rows) are missing from the snapshot by construction: the snapshot used only the sources available at capture time.

That gap matters for two reasons:

**Price diversity.** The 15-item headphones subset has a median of $162.97. eBay's resale market introduces used and refurbished listings (often $40–$100 below retail), and BestBuy's direct prices reflect the current in-store sale price — a different signal from the marketplace aggregation Google Shopping performs. One source is not a market.

**Source-trust calibration.** Part 9 will weight sources differently when computing the deal score. You cannot build that weighting without multiple live sources. This part provides them.

<MultiSourceFunnel />

Each source returns a differently-shaped raw JSON object. The `normalize()` step maps every shape onto the same flat schema so the aggregator receives identical `Product` objects regardless of origin. The `source` field preserves provenance; `deal_pct` is left `null` at ingestion and filled by the aggregator after cross-source merging.

## The Source protocol

Part 1 introduced the `DealSource` interface used by `ingest()`. This part formalizes it as an abstract base class and adds `available()` — a guard that lets the aggregator skip sources whose credentials are absent, instead of raising at runtime:

```python
# dealfinder/live_sources.py
class RapidApiSource:
    name = "RapidAPI"
    tier = 1  # fast, generous limits — try first

    def available(self) -> bool:
        return bool(os.getenv("RAPIDAPI_KEY"))

    def search(self, query: str, limit: int = 15) -> list[Product]:
        key = os.getenv("RAPIDAPI_KEY")
        if not key:
            return []
        r = httpx.get(
            f"https://{self._host}/search",
            params={"q": query, "country": "us", "limit": str(limit)},
            headers={"X-RapidAPI-Key": key, "X-RapidAPI-Host": self._host},
            timeout=20,
        )
        ...
```

The contract is intentionally minimal: `available()` returns a bool, `search()` returns a list of `Product`. The aggregator calls `available()` first and skips silently if credentials are absent. New sources drop in by implementing these two methods — nothing downstream changes.

The `tier` attribute is advisory metadata for Part 9's tiered aggregator: tier 1 sources are tried first, and their results short-circuit the tier-2 and tier-3 sources if enough results are found. Part 9 owns that logic; here you only need to set the `tier` correctly.

## eBay Browse: OAuth client-credentials

The eBay Browse API uses OAuth 2.0 client-credentials — the grant type designed for machine-to-machine access where no user is involved. Your app proves its identity with a client ID and secret, receives a short-lived access token, and uses that token as a Bearer credential on every Browse API call.

<OAuthFlow />

The flow has three moving parts: token acquisition, token caching, and proactive refresh.

**Token acquisition.** The `_get_token()` method in `EbaySource` Base64-encodes `client_id:client_secret`, POSTs to `/identity/v1/oauth2/token` with `grant_type=client_credentials`, and extracts `access_token` and `expires_in` from the response:

```python
# dealfinder/live_sources.py — EbaySource
def _get_token(self) -> str:
    if self._token and time.monotonic() < self._expires:
        return self._token
    creds = f"{os.getenv('EBAY_APP_ID')}:{os.getenv('EBAY_CERT_ID')}"
    b64 = base64.b64encode(creds.encode()).decode()
    r = httpx.post(
        self._base() + "/identity/v1/oauth2/token",
        headers={
            "Authorization": f"Basic {b64}",
            "Content-Type": "application/x-www-form-urlencoded",
        },
        data={
            "grant_type": "client_credentials",
            "scope": "https://api.ebay.com/oauth/api_scope",
        },
        timeout=30,
    )
    r.raise_for_status()
    j = r.json()
    self._token = j["access_token"]
    self._expires = time.monotonic() + j.get("expires_in", 7200) - 60
    return self._token
```

**Token caching.** The token is stored in `self._token` and `self._expires`. The guard `time.monotonic() < self._expires` short-circuits the HTTP call on every subsequent request within the TTL window. One re-authentication per ~two hours, not one per query.

**Proactive refresh.** The 60-second buffer (`expires_in - 60`) means the token is considered expired one minute before eBay actually invalidates it. That buffer absorbs clock skew and network jitter, so a call never fails mid-flight because the token expired between the check and the request.

**Sandbox vs. production.** The `_base()` method reads `EBAY_ENV` and the app ID suffix to choose the endpoint. If `EBAY_ENV=sandbox` or your app ID contains `SBX`, requests go to `api.sandbox.ebay.com`. For this tutorial, use the Production environment — sandbox data is sparse and does not reflect real prices.

```bash
# .env (never commit)
EBAY_APP_ID=YourApp-ProductionID-PRD-...
EBAY_CERT_ID=PRD-yourapp-cert-id...
# Optional affiliate commission attribution:
EBAY_CAMPAIGN_ID=123456789
```

With the env vars set, the `search()` method uses the cached token as a Bearer header:

```python
def search(self, query: str, limit: int = 15) -> list[Product]:
    if not self.available():
        return []
    headers = {"Authorization": f"Bearer {self._get_token()}"}
    campaign = os.getenv("EBAY_CAMPAIGN_ID")
    if campaign:
        headers["X-EBAY-C-ENDUSERCTX"] = f"affiliateCampaignId={campaign}"
    r = httpx.get(
        self._base() + "/buy/browse/v1/item_summary/search",
        headers=headers,
        params={"q": query, "limit": str(limit)},
        timeout=30,
    )
    if r.status_code != 200:
        return []
    out = []
    for it in (r.json().get("itemSummaries") or []):
        price = _f((it.get("price") or {}).get("value"))
        if not price:
            continue
        cond = it.get("condition") or "eBay"
        out.append(Product(
            id=f"ebay-{str(it.get('itemId', ''))[-40:]}",
            title=(it.get("title") or query)[:120],
            brand=None,
            category="product",
            price=price,
            currency=(it.get("price") or {}).get("currency", "USD"),
            url=it.get("itemAffiliateWebUrl") or it.get("itemWebUrl") or "",
            source=f"{self.name}:{cond}",
            image_url=(it.get("image") or {}).get("imageUrl"),
        ))
    return out
```

The `brand` field is set to `None` on eBay results because the Browse API does not reliably surface the manufacturer name in the `itemSummaries` response — only the listing title does. Part 6's `title_brand()` extractor fills the true manufacturer downstream. This is intentional: `brand=None` is honest; `brand="eBay"` would be misleading.

When `EBAY_CAMPAIGN_ID` is set, the API returns an `itemAffiliateWebUrl` with your campaign attribution embedded. Use that URL in preference to `itemWebUrl`; the product page is identical and you earn a commission on purchases.

A representative result for `"noise cancelling headphones"`:

```json
{
  "id": "ebay-v1|271843901234",
  "query": "noise cancelling headphones",
  "category": null,
  "title": "Sony WH-1000XM5 Wireless Noise Canceling Headphones - Black",
```

## BestBuy Affiliate: key-auth

BestBuy's open Developer API is simpler than eBay's OAuth: pass `apiKey` as a query parameter. Registration is free at `developer.bestbuy.com` — but be realistic about the timeline: Best Buy *advertises* 1–3 business days, and real-world approvals often take weeks (the program is lightly staffed; the key string isn't even revealed until a human approves your account). If you're stuck in "pending," the [contact form](https://developer.bestbuy.com/contact-us?topic=general) with your account email and app name is what historically shakes keys loose. In the meantime nothing is blocked: the respx-mocked test `test_bestbuy_search_maps_saleprice` in `tests/test_live_sources.py` exercises the normalization path with no key, and Best Buy's *prices* already reach the aggregator through Google Shopping (you'll see `RapidAPI:Best Buy` source tags in live results) — the official API's main addition is the structured `salePrice`/`regularPrice` split.

```python
# dealfinder/live_sources.py — BestBuySource
def search(self, query: str, limit: int = 15) -> list[Product]:
    key = os.getenv("BESTBUY_API_KEY")
    if not key:
        return []
    tokens = [t for t in re.findall(r"[a-z0-9]+", query.lower()) if len(t) > 1][:6]
    if not tokens:
        return []
    pred = "&".join(f"search={t}" for t in tokens)
    show = "sku,name,salePrice,regularPrice,url,image,manufacturer"
    url = (
        f"https://api.bestbuy.com/v1/products({pred})"
        f"?apiKey={key}&format=json&show={show}&pageSize={limit}&sort=salePrice.asc"
    )
    r = httpx.get(url, timeout=20)
    if r.status_code != 200:
        return []
    out = []
    for p in r.json().get("products", []):
        price = _f(p.get("salePrice"))
        if not price:
            continue
        reg = p.get("regularPrice")
        on_sale = bool(reg) and p.get("salePrice", reg) < reg
        out.append(Product(
            id=f"bestbuy-{p.get('sku')}",
            title=(p.get("name") or query)[:120],
            brand=p.get("manufacturer"),
            category="product",
            price=price,
            url=p.get("url") or "",
            source=self.name + (":sale" if on_sale else ""),
            image_url=p.get("image"),
        ))
    return out
```

Two things to note:

**Search predicate.** BestBuy's product search API uses a `(search=term&search=term)` filter syntax, not a single `q=` parameter. The code tokenizes the query into individual words and joins them with `&search=`. This is a quirk of the BestBuy API — the same approach works for any multi-word query.

**Sale detection.** The API returns both `salePrice` and `regularPrice`. When `salePrice < regularPrice`, the connector appends `:sale` to the `source` string (`"BestBuy:sale"` vs `"BestBuy"`). Part 9 can use this signal when computing source-trust weighting.

```bash
# .env
BESTBUY_API_KEY=your_key_here
```

## The Bose QC45 contrast: source trust matters

The snapshot contains a Bose QuietComfort 45 at $46.00, sourced from a third-party Google Shopping listing. The deal-score model flags it as suspicious: at a fair value of $285.15, the residual is $239.15, giving `residual_frac = 0.839`. The thresholds for suspicious are `median_signal >= 0.70` AND `residual_frac > 0.70` — both conditions are met. The product has no condition token in its title, so `condition = "new"` by default (the model residual catches the trap, not a condition flag).

Now look at what BestBuy returns for the same product. A direct BestBuy search for Bose QuietComfort 45 headphones returns `salePrice` values in the $199–$249 range — the legitimate current retail price for a flagship that carries a $329 MSRP.

Same product. Same query. Very different prices: $46 from a third-party Google Shopping listing vs. $199–$249 from BestBuy's direct API.

The $46 listing is not necessarily fraudulent — it could be a refurb, a bundle mislisting, or a marketplace error. But the gap between the two sources is information. Part 9's aggregator assigns a `source_trust_weight` to each source based on its historical signal quality. BestBuy's direct API carries higher trust than anonymous third-party Google Shopping listings — not because BestBuy is always cheaper, but because BestBuy's `source` tag is less likely to carry the kind of listing noise that produced the $46 anomaly.

This contrast — the same model, two sources, a 4x price difference — is the empirical motivation for source-trust weighting. You cannot see it from one source alone.

## Check it works

1. **The connector, in isolation.** One live RapidAPI query from Python:

   ```bash
       print(f'{p.brand[:20]:20s} | {p.title[:50]:50s} | \${p.price}')"
   ```

   ```bash
   uvicorn dealfinder.serve:app --port 8000   # restart after editing .env
   curl -s http://localhost:8000/sources
   ```
   **Expect:** `true` for every source whose key you set — with RapidAPI + eBay that reads `{"eBay":true,"RapidAPI":true,...}`. **If a source you configured shows `false`:** the env var name is misspelled or the server predates your `.env` edit.

3. **The product, end to end.** Open [http://localhost:8000](http://localhost:8000), keep **live deals** selected, search `noise cancelling headphones`. **Expect:** a result grid within ~5–20 s whose status line names your live sources. eBay items carry condition labels (`eBay:Open box`, `eBay:Certified - Refurbished`) — inventory Google Shopping doesn't have. **If the grid is empty:** check the terminal running uvicorn; a stack trace there is a connector bug, an empty-but-clean response means every source is keyless or benched.

The offline tests cover the same code paths with no keys at all: `pytest tests/test_live_sources.py -v` — 5 passed, including the mocked eBay OAuth-then-search flow.
