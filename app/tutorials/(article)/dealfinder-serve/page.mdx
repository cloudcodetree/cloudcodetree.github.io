## The six endpoints

`dealfinder/serve.py` exposes exactly six application routes on a single `FastAPI(title="DealFinder")` app:

| Method | Path | What it does |
|--------|------|--------------|
| GET | `/healthz` | Returns `{"status": "ok", "products": <int>}` — the liveness check the Docker health probe calls. |
| GET | `/search?q=` | Calls `aggregate(q)` across live sources; if a DB is configured, embeds + upserts to pgstore. |
| GET | `/semantic?q=&k=12` | Semantic search over everything ever aggregated (pgvector). Returns 503 when no DB is configured. |
| GET | `/sources` | Returns which live connectors are available right now. |
| GET | `/` | Serves `static/index.html` — the bare HTML UI. |
| GET | `/deal/{product_id}` | Returns deal details for one snapshot product, or 404. |

The app also gets FastAPI's built-in `/docs`, `/redoc`, and `/openapi.json` for free.

Six routes — no more, no less. Knowing this table lets you reason about what the CI TestClient tests cover and what the Docker `HEALTHCHECK` is actually probing.

## Module-level startup: loading the catalog and price model

When Python imports `dealfinder.serve`, seven things happen before any request arrives:

```python
# dealfinder/serve.py (startup block)
_DB = bool(os.getenv("DATABASE_URL"))
if _DB:
    try:
        pgstore.migrate()
    except Exception:
        _DB = False

_catalog = load_catalog()                          # 270 Products from snapshot
_idx     = {p.id: i for i, p in enumerate(_catalog)}  # id → list index
_X       = feature_matrix(_catalog)               # numeric feature matrix
_model   = LinearModel().fit(_X, [p.price for p in _catalog])
_fair    = {p.id: float(fp) for p, fp in zip(_catalog, _model.predict(_X))}

def _embed_texts(texts):
    from .embed import embed_texts
    return embed_texts(texts)
```

In plain English:

- `_DB` — whether a pgvector database is reachable. If not, `/semantic` returns 503 and `/search` skips the persist step. In the test environment and in this run, `_DB = False`.
- `_catalog` — the 270 `Product` objects from the snapshot, loaded once at startup.
- `_idx` — a dict from `product_id` to list position so `/deal/{id}` is an O(1) lookup, not a linear scan.
- `_X` — the feature matrix built by `feature_matrix()` from `dealfinder.features`. These are the same features (category, brand tier, condition, embeddings) the price model learned from.
- `_model` — a `LinearModel` fit on the snapshot at startup. This is the baseline price model that Parts 3 and 18 trained; Part 24 discusses upgrading this inference path without touching the endpoints.
- `_fair` — a dict from `product_id` to predicted fair price, precomputed at startup so `/deal` never calls the model at request time.
- `_embed_texts` — lazy import of the embedding function so the embedding library is only loaded when a DB is present and `/search` actually needs it.

All of this happens at import time. The trade-off is a slightly slower cold start (loading 270 products and fitting a model) in exchange for sub-millisecond `/deal` and `/healthz` responses at runtime.

## The /deal endpoint — the hero cast, live

```python
@app.get("/deal/{product_id}")
def deal(product_id: str):
    if product_id not in _idx:
        raise HTTPException(status_code=404, detail="unknown product")
    p = _catalog[_idx[product_id]]
    return {
        "id": p.id, "title": p.title, "price": p.price,
        "fair": round(_fair[p.id], 2),
        "deal_score": round(deal_score(p.price, _fair[p.id]), 3),
    }
```

The response shape for every product is `{id, title, price, fair, deal_score}` — `fair` rounded to 2 decimal places, `deal_score` rounded to 3.


Now compare the hero cast through this endpoint, using the pinned bible facts:

| Product | price | fair | deal_score | verdict |
|---------|-------|------|-----------|---------|
| Anker Soundcore Q20i | $44.99 | $225.34 | 0.8 | DEAL |
| Bose QuietComfort 45 | $46.00 | $285.15 | high | SUSPICIOUS |
| Sony WH-1000XM5 | $162.97 | $285.15 | 0.4 | FAIR |
| Sony WH-1000XM6 | $399.99 | $285.15 | negative | OVERPRICED |

The Bose QC45 at $46 — a $329-MSRP flagship — produces a high `deal_score` because it genuinely sits far below the fair-price prediction. That is the trap the two-signal system (Part 3) catches: `residual_frac = 0.839` flags it SUSPICIOUS regardless of how good the raw score looks. The `/deal` endpoint gives you the raw fair price and score; the `verdict()` logic in `dealfinder/dealscore.py` applies the `residual_frac >= 0.70` guard (`SUSPICIOUS_RESIDUAL_FRAC`) to assign the badge.

<Callout tone="note">
The `fair` value for the Anker Q20i ($225.34) differs from the bible's $108.33. The bible's $108.33 is the pinned baseline from the audio-category linear model on the headphones subset (Part 3). The `/deal` endpoint uses `_model = LinearModel().fit(_X, ...)` on the full 270-item catalog — a broader fit. Both are real outputs; they differ because the training set differs. `tests/test_serve.py` pins `deal_score > 0.15` (not a specific value) to stay robust to this.
</Callout>

## The /search and /semantic endpoints

### /search

```python
@app.get("/search")
def search(q: str):
    result = aggregate(q)
    if _DB and result["results"]:
        # embed + upsert to pgstore, add result["persisted"] count
        ...
    return result
```

`/search` delegates to `aggregate(q)` in `dealfinder/aggregate.py`, which fans out to whichever live sources are available, deduplicates, sorts by price, and caps at 24 results. The response shape:

```json
{
  "query": "noise cancelling headphones",
  "sources_live": ["Shopify", "iTunes"],
  "throttled": ["eBay", "RapidAPI", "BestBuy", "Apify", "Firecrawl"],
  "median_price": 162.97,
  "count": 15,
  "results": [
    {"id": "...", "title": "...", "brand": "...", "price": 44.99,
     "source": "...", "url": "...", "image_url": "...", "deal_pct": 72.4},
    ...

```

When `_DB` is set and results come back, the handler embeds titles using `_embed_texts`, upserts them to pgstore, and adds `result["persisted"]` with the total row count. Without a DB, the route still works — it just doesn't persist.

## The semantic cache

`SemanticCache` lives in `dealfinder/cache.py`. It is a standalone unit — not wired into `serve.py`. The docstring in `serve.py` lists "caching" as a production concern to add; the cache is the building block you would reach for when you do.

```python
# dealfinder/cache.py
class SemanticCache:
    def __init__(self, threshold: float = 0.95) -> None:
        self.threshold = threshold
        self._vecs: list[list[float]] = []
        self._vals: list = []

    def put(self, vec, value) -> None:
        self._vecs.append([float(x) for x in vec])
        self._vals.append(value)

    def get(self, vec):
        if not self._vecs:
            return None
        V = np.array(self._vecs)
        q = np.asarray(vec, dtype=float)
        sims = (V @ q) / (np.linalg.norm(V, axis=1) * np.linalg.norm(q) + 1e-9)
        i = int(np.argmax(sims))
        return self._vals[i] if sims[i] >= self.threshold else None
```

The hit/miss logic is cosine similarity with a threshold of 0.95. A plain string cache would miss "wireless noise canceling headphones" when the stored key is "noise cancelling headphones" — the same user intent, a different string. The semantic cache stores the query embedding and returns the cached answer when similarity is at or above the threshold.

<SemanticCacheViz />

The embedding model is `BAAI/bge-small-en-v1.5` (384-dim, via fastembed) — the same model used in Part 4's title embeddings, Part 5's semantic search, and Part 13's pgvector persistence. One model, one set of vectors, consistent across the course.

**How the test pins the threshold behavior** (`tests/test_serve.py`):

```python
def test_semantic_cache_hit_and_miss():
    from dealfinder.cache import SemanticCache
    cache = SemanticCache(threshold=0.95)

    v1 = [1.0, 0.0]
    v2 = [1.0, 0.02]   # nearly identical — cosine ≈ 0.9998
    v3 = [0.0, 1.0]    # orthogonal — cosine = 0.0

    cache.put(v1, "noise cancelling headphones results")

    assert cache.get(v2) == "noise cancelling headphones results"  # hit
    assert cache.get(v3) is None                                    # miss
```

`v1 → v2` is a hit; `v1 → v3` is a miss. No LLM call, no network — just vector arithmetic. In production you would back the cache with Redis and use the same embedding function as `/search`.

## The serving levers in one place

The `serve.py` docstring names four production concerns: streaming, batching, quantized/vLLM serving, and caching. The app in this part is the shape they hang off — the endpoints are stable; the levers are what you tune as traffic grows.

<Batching />

**Batching.** GPUs are wasted serving one request at a time. Continuous batching packs many in-flight requests into each model forward pass — the core trick behind high-throughput servers like vLLM. For the price model in `serve.py` (a `LinearModel`, not an LLM), batching is `feature_matrix` applied to a list of products at once rather than one at a time. The principle is the same: vectors in, scores out, one pass.

**Quantization.** Run the model in 8-bit or 4-bit: less memory, faster, a small quality cost. For the baseline `LinearModel` this is not relevant — it has no weight compression overhead. It becomes the first lever when you swap in a gradient-boosted model (Part 18) or a fine-tuned LLM (Part 11) behind the `/deal` score path.

**vLLM.** Continuous batching plus paged-attention KV cache for LLM inference — many-times the throughput of naive one-at-a-time serving, behind an OpenAI-compatible API. Part 24 benchmarks this against the inference path and shows when the overhead pays off.

**Streaming.** Send tokens as they are generated. Same total time, but perceived latency drops because the user sees output immediately. The `/search` route returns a complete aggregate result; adding SSE streaming is the Part 15 web-UI topic (`/api/stream`). The `SSEStream` component in Part 15 illustrates the client side.

**Pick the smallest model that passes your eval gate.** The cheapest token is the one you do not spend on an oversized model. The eval gate — `precision@5 >= 0.80` on the 20-item golden set (Part 20) — is the objective criterion: if a smaller model passes it, use that model.

<Callout tone="note">
**How this scales in production.** Put the API behind an autoscaling gateway (a Kubernetes `HorizontalPodAutoscaler` pointing at the Docker image from Part 25). Serve the embedding path on a dedicated pod with the fastembed model pre-warmed. Back the `SemanticCache` with Redis + a vector index. Add the periodic-suggestions worker (Part 30) as a scheduled job that precomputes recommendations off the hot path. Every lever is independent — stack the ones your traffic pattern needs.
</Callout>
