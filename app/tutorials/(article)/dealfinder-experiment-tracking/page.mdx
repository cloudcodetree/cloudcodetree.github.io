# Experiment Tracking & Model Registry

**TL;DR: Part 17 trained three price models. Now you log every run — params, MAE, R² — to a local MLflow SQLite store, select the winner on a fair, same-features basis, and register it. The discipline is what makes ML work you can actually trust and reproduce.**

This is **Part 18 of DealFinder**, and the lesson is about honesty. Training a model is easy; knowing which model you trained, under what conditions, and why it won is the hard part. MLflow gives you the infrastructure to answer those questions without ceremony — no tracking server, no cloud account, just a local SQLite file that records everything. By the end you will have a comparison table backed by real executed numbers, a registered model selected by rule, and four tests that pin it all.

## Why you need a ledger, not just a winner

After Part 17 you have three price models: a linear baseline, a gradient-boosted regressor, and a PyTorch MLP. You know the GBDT wins by MAE on the electronics snapshot. But how do you know that next month? Or next quarter, when a colleague retrain it with a different `random_state` and gets a slightly different number? How do you know the comparison was fair?

The problem with knowing the winner in your head is that heads forget. They also confuse runs — "was that the hand-features GBDT or the hand+embeddings one?" They don't record which snapshot was used, or what PCA dimension was set, or whether the train/test split was the same across all three models.

A tracking ledger fixes this. Every run writes a row: the model name, the params (feature set, random state, epochs), and the metrics (MAE, R²). The winning run is tagged and registered. The whole comparison is reproducible from the committed `tracking_uri`.

MLflow is the standard tool for this in Python ML. DealFinder uses it pointed at a local SQLite file — no tracking server, no extra process to manage, nothing that breaks in CI. You get the full experiment UI locally if you want it, and the programmatic API for CI.

## The local MLflow store: SQLite, no server

`dealfinder/tracking.py` exposes a context manager called `local_tracking()`. It creates a temporary directory, opens an SQLite database in it, and points MLflow at that URI for the duration of the block:

```python
# dealfinder/tracking.py
@contextmanager
def local_tracking(uri: str | None = None):
    """Point MLflow at a LOCAL store (a temp SQLite file by default) — no server."""
    mlflow = _require_mlflow()
    prev = mlflow.get_tracking_uri()
    tmp: tempfile.TemporaryDirectory | None = None
    if uri is None:
        tmp = tempfile.TemporaryDirectory(prefix="dealfinder-mlruns-")
        uri = f"sqlite:///{Path(tmp.name) / 'mlflow.db'}"
    try:
        mlflow.set_tracking_uri(uri)
        mlflow.set_experiment(_EXPERIMENT)
        yield mlflow
    finally:
        mlflow.set_tracking_uri(prev)
        if tmp is not None:
            tmp.cleanup()
```

On a real run, the observed `tracking_uri` is something like:

```
sqlite:////var/folders/.../T/dealfinder-mlruns-<rand>/mlflow.db
```

MLflow logs to the console when it initialises:

```
Creating initial MLflow database tables...
Experiment with name 'dealfinder-price-models' does not exist. Creating a new experiment.
Successfully registered model 'dealfinder-fair-price'.
```

The context manager restores the previous `tracking_uri` on exit and cleans up the temp directory. Nothing persists to your home directory. Nothing hits the network.

<Callout tone="note">
**MLflow 3 removed the bare filesystem `./mlruns` backend from the default registry path.** The bare file store works for logging runs but the model registry requires a database backend. `local_tracking()` uses SQLite so both runs and the registry work identically, offline. `mlflow_available()` returns `True` in the companion venv; `tests/test_tracking.py` uses `pytestmark = skipif(not mlflow_available())` so the suite skips cleanly on machines without MLflow rather than failing.
</Callout>

## The feature contract: what makes a comparison fair

Before logging anything, you need to settle a question that is easy to get wrong: are all three models being compared on the same features?

Part 17 trained models in different configurations. The `train_torch_pricehead()` function in `dealfinder/models.py` trains a PyTorch MLP on hand-only features (the §4 set: category, brand_tier, condition, and sparse numeric extractions). The `gbdt_vs_linear()` function trains both a linear model and a GBDT on hand features **plus** 16 PCA-compressed title embedding dimensions. Those are different feature representations, so the resulting MAEs are not directly comparable — a model trained on richer features has a systematic advantage.

The fair comparison is the one where every model sees the identical matrix. In `tracking.py`, `_contract_matrix()` builds exactly that shared representation:

```python
# dealfinder/tracking.py (abridged)
def _contract_matrix():
    """Return (Xtr, Xte, ytr, yte) on the fair-price feature contract.

    PCA is fit on TRAIN ONLY (no leakage), matching models.gbdt_vs_linear exactly,
    so the GBDT MAE here matches the pinned $138.11.
    """
    products = load_products()
    Xh = feature_matrix(products)          # §4 hand features
    y = np.asarray([p.price for p in products], dtype=float)
    tr, te = _split(len(products))

    ids, vectors = load_title_embeddings()
    emb = np.asarray([vectors[order[p.id]] for p in products], dtype=float)
    pca = PCA(n_components=16, random_state=0).fit(emb[tr])  # fit on train only
    Xtr = np.hstack([Xh[tr], pca.transform(emb[tr])])
    Xte = np.hstack([Xh[te], pca.transform(emb[te])])
    return Xtr, Xte, y[tr], y[te]
```

All three selectable runs — linear, gbdt, and torch — receive this same `Xtr` / `Xte`. The PyTorch model runs its own training loop (gradient descent, log-price target, seeded) on the contract matrix via `_torch_on_contract()`, giving a comparable MAE.

<FeatureContractGate />

The two documented baselines from Part 17 — `linear_baseline` ($227.89, hand-only) and `torch_baseline` ($117.11, hand-only) — are logged separately with `contract="documented-baseline"` and `selectable=False`. They are in the ledger so the Part 17 prose numbers reproduce here verbatim, but they are excluded from the winner selection. A lower MAE on a different (cheaper) feature set is not evidence of a better model.

## Logging the three selectable runs

Inside `run_tracking()`, each model is trained and logged in a `mlflow.start_run()` block. Here is the linear and GBDT portion:

```python
# dealfinder/tracking.py (run_tracking, abridged)
Xtr, Xte, ytr, yte = _contract_matrix()

lin = LinearModel().fit(Xtr, ytr)
lin_pred = lin.predict(Xte)
runs = [
    RunRecord(
        "linear", "fair-price",
        round(mae(yte, lin_pred), 2), round(r2(yte, lin_pred), 3),
        params={"model": "LinearModel", "features": "hand+emb16", "solver": "normal-eq"},
    ),
]

gbdt = GradientBoostingRegressor(random_state=0).fit(Xtr, ytr)
gbdt_pred = gbdt.predict(Xte)
runs.append(
    RunRecord(
        "gbdt", "fair-price",
        round(mae(yte, gbdt_pred), 2), round(r2(yte, gbdt_pred), 3),
        params={"model": "GradientBoostingRegressor", "features": "hand+emb16", "random_state": 0},
    )
)
```

Notice `GradientBoostingRegressor` — that is `sklearn.ensemble.GradientBoostingRegressor`, not xgboost. DealFinder's boosting is pure scikit-learn throughout.

The logging step happens inside `local_tracking()`:

```python
with local_tracking() as mlflow:
    for r in runs:
        with mlflow.start_run(run_name=r.name) as run:
            mlflow.log_params(r.params)
            mlflow.set_tag("contract", r.contract)
            mlflow.set_tag("selectable", str(r.selectable))
            mlflow.log_metric("mae", r.mae)
            if r.r2 is not None:
                mlflow.log_metric("r2", r.r2)
```

`r.contract` and `r.selectable` are MLflow tags — they survive in the database and let you filter runs programmatically. When you open the MLflow UI against the same SQLite file, you see exactly five runs tagged with those values.

## The documented baselines: logging without competing

Part 17 trained `gbdt_vs_linear()` on hand-only features and got `linear_baseline` at $227.89. It also trained `train_torch_pricehead()` on hand-only features and got `torch_baseline` at $117.11. Those are the numbers the Part 17 prose quotes. They need to live in the tracking store so that anyone who opens the MLflow UI sees them alongside the fair-price runs and understands the full picture.

But they must not win. Winning means being selected for the registry — and registering a model trained on a cheaper feature set would mean DealFinder's deployed `dealfinder-fair-price` produces different predictions depending on which branch of your experiment history happened to look better.

The `RunRecord` type has a `selectable: bool` field for exactly this:

```python
@dataclass
class RunRecord:
    name: str
    contract: str       # "fair-price" | "documented-baseline"
    mae: float
    r2: float | None
    params: dict = field(default_factory=dict)
    selectable: bool = True

# documented-baseline runs
runs.append(
    RunRecord(
        "linear_baseline", "documented-baseline", doc.linear_mae, None,
        params={"model": "LinearModel", "features": "hand-only", "source": "Part 17"},
        selectable=False,
    )
)
runs.append(
    RunRecord(
        "torch_baseline", "documented-baseline", tb.mae, None,
        params={"model": "MLP", "features": "hand-only", "epochs": tb.epochs},
        selectable=False,
    )
)
```

Both are logged to MLflow with `selectable=False`. The winner selection explicitly filters:

```python
selectable = [r for r in runs if r.selectable]
winner = min(selectable, key=lambda r: r.mae)
```

`torch_baseline` at $117.11 never enters that list. The registered winner is `gbdt` at $138.11.

## Selecting and registering the winner

The winner selection is a single line: `min(selectable, key=lambda r: r.mae)`. What follows is the registry write:

```python
client = mlflow.tracking.MlflowClient()
client.create_registered_model("dealfinder-fair-price")
client.set_registered_model_tag("dealfinder-fair-price", "winner", winner.name)
client.set_registered_model_tag("dealfinder-fair-price", "winner_mae", str(winner.mae))
```

The registered model is named `dealfinder-fair-price` — the same name you will reference in Part 20 when the MLOps loop promotes a challenger after drift is detected.

Call `run_tracking()` and inspect the result:

```python
from dealfinder.tracking import run_tracking

result = run_tracking()
print(f"experiment:        {result.experiment}")
print(f"registered_model:  {result.registered_model}")
print(f"winner:            {result.winner}        winner_mae: {result.winner_mae}")
print(f"torch_available:   {result.torch_available}")
```

Real output:

```
experiment:        dealfinder-price-models
registered_model:  dealfinder-fair-price
winner:            gbdt        winner_mae: 138.11
torch_available:   True
```

The `TrackingResult` dataclass also carries the full run list (`result.runs`) and a `comparison_table()` method that formats it.

## The full comparison table

`result.comparison_table()` produces this output verbatim:

```
model                metric  MAE ($)     R²     contract
linear                  257.85   0.010   fair-price
gbdt               *    138.11   0.727   fair-price
torch                   149.21     n/a   fair-price
linear_baseline         227.89     n/a   documented-baseline
torch_baseline          117.11     n/a   documented-baseline
```

The `*` marks the winner. The documented baselines appear at the bottom with their contract tag — visible, honest, and excluded from competition.

Some things this table makes plain that are easy to miss:

**The GBDT genuinely wins the fair comparison.** On identical hand+emb16 features, `gbdt` at $138.11 beats `linear` at $257.85 and `torch` at $149.21. The embeddings are why: Part 17 showed that GBDT without embeddings reaches $257.99 — adding the PCA-compressed title embeddings cuts 46% of that error.

**The GBDT does not beat torch overall.** `torch_baseline` at $117.11 is lower, but on hand-only features. That is a different experiment. Claiming GBDT beats torch overall would require running both on the same features — which is exactly what the fair-price contract does, where torch gets $149.21.

**R² is missing for torch and the baselines.** The PyTorch training loop in `_torch_on_contract()` does not compute R² — it returns only MAE. The comparison is still fair because MAE is the selection metric, and it is computed identically for all three selectable models on the same held-out test set.

**Linear is worse than the baseline.** The `linear` fair-price run ($257.85) is higher MAE than `linear_baseline` ($227.89). That seems backwards — more features made it worse? Yes: linear models can degrade when you add high-dimensional features that are not linearly predictive. PCA compression helps GBDT (which can learn non-linear interactions across the compressed dims) more than it helps linear regression. The ledger lets you see this clearly.

## Tests that pin it

`tests/test_tracking.py` contains four tests. Each is pinned to real output and would catch any regression in the selection logic, the MAE numbers, or the contract tagging:

```python
# tests/test_tracking.py
pytestmark = pytest.mark.skipif(
    not mlflow_available(), reason="mlflow not installed"
)

def test_gbdt_is_the_selected_winner_by_mae():
    result = run_tracking()
    assert result.winner == "gbdt"
    assert abs(result.winner_mae - 138.11) < 0.05

def test_selectable_runs_share_the_fair_price_contract_and_gbdt_beats_them():
    result = run_tracking()
    selectable = [r for r in result.runs if r.selectable]
    assert all(r.contract == "fair-price" for r in selectable)
    winner = min(selectable, key=lambda r: r.mae)
    assert winner.name == "gbdt"
    assert winner.mae < 149.21   # beats torch
    assert winner.mae < 257.85   # beats linear

def test_documented_baselines_reproduce_and_are_not_selectable():
    result = run_tracking()
    baselines = {r.name: r for r in result.runs if not r.selectable}
    assert "linear_baseline" in baselines
    assert "torch_baseline" in baselines
    assert abs(baselines["linear_baseline"].mae - 227.89) < 0.05
    assert abs(baselines["torch_baseline"].mae - 117.11) < 0.05

def test_comparison_table_marks_the_winner():
    result = run_tracking()
    table = result.comparison_table()
    assert "* " in table          # winner marked
    assert "gbdt" in table
    assert "138.11" in table
    assert "documented-baseline" in table
```

Run them with:

```bash
pip install ".[mlflow]"
pytest tests/test_tracking.py -v
```

All four pass against the committed snapshot. The `skipif` on `mlflow_available()` means the suite is safe to run on machines without MLflow — the tests simply show as skipped rather than failing.

<Callout tone="note">
**The companion module also runs deterministically.** `run_tracking()` is seeded (`random_state=0`, `torch.manual_seed(0)`) and uses the same `_split()` function as `models.gbdt_vs_linear()` — so the GBDT MAE here ($138.11) matches the number pinned in `tests/test_features.py` from Part 17. The two test files are testing the same underlying numbers from different angles.
</Callout>
