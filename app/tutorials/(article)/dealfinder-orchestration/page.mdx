# Pipelines & Orchestration

**TL;DR: Wrap the five dataset-engineering stages in a real Prefect 3.7.7 flow, enforce a Pydantic data contract that hard-fails on bad rows, and materialize a dbt-style SQL view that filters the 270-item snapshot down to 111 honest good deals. Every number here comes from running the companion code against the committed snapshot.**

This is **Part 20 of DealFinder**. Part 19 built the labeled dataset. Now you orchestrate it — connecting the stages into a pipeline that retries on transient failures, caches expensive pure steps, stops loud on a data-quality violation, and emits a reproducible training table. The tooling is Prefect 3.7.7 (a real, installed dependency, not a mock), but the stage functions are plain Python with a Prefect-free fallback path, so the whole flow runs whether Prefect is installed or not.

<Callout tone="note">
**How this maps to Airflow, Astronomer, and Dagster.** Orchestrators are more alike than their marketing suggests, and every concept in this part translates directly. A Prefect **flow** is an Airflow **DAG**; a Prefect **task** with its retry policy is an Airflow **task/operator** with `retries`; Prefect's run history is Airflow's scheduler metadata database; **Astronomer** is managed Airflow as a service (hosted scheduler, deploys, observability — you write the same DAGs). **Dagster** reframes the same graph around data *assets* rather than tasks — closest in spirit to how this part treats `good_deals` as a materialized output. The course uses Prefect for one honest reason: it runs in-process from `pip install`, offline, in CI. Airflow needs a scheduler, webserver, and metadata database standing up — which fights this course's "every lesson runs on your laptop" rule. Learn the concepts here; the vocabulary swap to any of the three is an afternoon.
</Callout>

## The problem: five loose stages need a spine

Part 19 gave you `build_labeled_dataset()` — a function that ingests the snapshot, applies the two-signal deal score, and hands back a labeled `LabeledDataset`. That works fine as a one-shot call. It does not give you:

- **Retry semantics** when the ingest step hits a transient I/O error.
- **Caching** so a pure normalize step doesn't recompute on re-run.
- **A hard stop** when a bad row slips through before it poisons the model.
- **A materialized output table** the training step can read by path instead of rerunning the whole pipeline.
- **Observability** — a run ID, a duration, a success/failure signal visible in a UI.

Orchestration is how you get those properties without rewriting your stage logic. The design principle in `flows.py` is worth stating explicitly before you see the code: **the stage functions are plain Python; Prefect wraps them**. `ingest_snapshot`, `normalize_rows`, `quality_gate`, `label_rows`, and `run_good_deals_model` each do exactly one job and are independently testable. Prefect supplies the task graph, the retry engine, and the run history. If Prefect is absent, the same stages run as a plain function call chain — `snapshot_pipeline()` — and produce the same output.

## The DAG: five stages, one direction

The pipeline is a strict left-to-right DAG with no branching and no joins:

```
ingest → normalize → quality-gate → label → good_deals model → [persist]
```

Each arrow is a data dependency: the output of one task is the input of the next. There are no cycles. There is no parallelism in this pipeline — the stages are deliberately sequential because the contract gate must see the normalized rows before it admits them, and the label step depends on the full snapshot path rather than the in-memory normalized list (it calls `build_labeled_dataset`, which re-reads the snapshot for the grouped split). That is the real shape; do not paper over it with a diagram that implies parallelism.

The persist step is optional — it only runs if you pass `persist_dir`. When it runs, it writes `good_deals.csv` to disk so downstream consumers (the Part 21 training script, a scheduler, a data warehouse loader) can pick it up by path without re-running the pipeline.

## Prefect tasks: retries, caching, and the no-op fallback

Here is the Prefect wiring from `dealfinder/flows.py`:

```python
# dealfinder/flows.py (abridged — Prefect path)
from prefect import flow, task
from prefect.cache_policies import NO_CACHE

# ingest: retries=2 because the real connector hits a remote API.
# The snapshot reader never fails, but the decorator is there for
# the day you swap in a live connector.
_ingest_task = task(retries=2, retry_delay_seconds=1, cache_policy=NO_CACHE)(ingest_snapshot)

# normalize: pure function — caching is safe and useful.
_normalize_task = task(name="normalize")(normalize_rows)

# gate: always re-check — never cache a quality gate.
_gate_task = task(name="quality-gate", cache_policy=NO_CACHE)(quality_gate)

# label: re-reads the snapshot; NO_CACHE keeps the run honest.
_label_task = task(name="label", cache_policy=NO_CACHE)(label_rows)

# good_deals model: SQLite in-memory; cheap enough to re-run, but
# caching is fine because the model SQL is committed and deterministic.
_model_task = task(name="good-deals-model")(run_good_deals_model)
```

Two cache policies to keep straight:

- **Default (LRU cache)** — Prefect caches the task output keyed by input hash. Correct for `normalize` and `good-deals-model`: pure functions on a fixed snapshot.
- **NO_CACHE** — the task always re-executes. Required for `quality-gate` (so you always see the real contract state) and `label` (so a snapshot update is reflected immediately).

The fallback path is a plain function call that bypasses Prefect entirely:

```python
def snapshot_pipeline(path=None, persist_dir=None) -> FlowResult:
    """Run the DAG as plain functions — Prefect-free fallback."""
    return _run_pipeline(path, persist_dir)

# When Prefect is absent, snapshot_flow is assigned snapshot_pipeline:
if not HAS_PREFECT:
    snapshot_flow = snapshot_pipeline
```

In this environment, `HAS_PREFECT` is `True` — Prefect 3.7.7 is installed, and `snapshot_flow` is the genuine `@flow`-decorated function running on a real Prefect engine. `snapshot_flow is snapshot_pipeline` evaluates to `False` (they are distinct objects). Both paths produce identical `FlowResult` values; `tests/test_flows.py` pins both.

<Callout tone="note">
**Which path is the reader on?** Install Prefect with `pip install ".[prefect]"` to get the orchestrated path. Skip it and `snapshot_pipeline` runs automatically. The tutorial shows you the Prefect path; the tests cover both. The prose will say which path a given run is on.
</Callout>

## The data contract: SnapshotRow and ContractReport

A data contract is a formal assertion about the shape of your data. In production, it lives at the boundary between a data source and a downstream consumer — the same role a typed API schema plays at a service boundary. Here it lives at the boundary between the ingest/normalize stages and the label/model stages.

`SnapshotRow` is the contract:

```python
# dealfinder/flows.py
class SnapshotRow(BaseModel):
    id: str
    query: str
    category: str
    title: str
    price: float
    median_price_at_capture: float

    @field_validator("price")
    @classmethod
    def _price_positive(cls, v: float) -> float:
        if v <= 0:
            raise ValueError("price must be > 0")
        return v

    @field_validator("category")
    @classmethod
    def _category_known(cls, v: str) -> str:
        if v not in KNOWN_CATEGORIES:
            raise ValueError(f"category {v!r} not in known set")
        return v
```

Two rules: `price > 0`, and `category` in the 11 known categories (`audio`, `computers`, `displays`, `peripherals`, `storage`, `accessories`, `mobile`, `wearables`, `smart-home`, `components`, `misc`). Six required columns must be present before Pydantic even gets to validate the values — missing columns are caught by a pre-check loop in `validate_contract`.

`validate_contract` returns a `ContractReport` — the outcome of running every row through `SnapshotRow.model_validate`:

```python
@dataclass
class ContractReport:
    total: int
    valid: int
    violations: list[dict] = field(default_factory=list)

    @property
    def passed(self) -> bool:
        return self.total > 0 and self.valid == self.total
```

Against the real snapshot: `total=270`, `valid=270`, `violations=[]`, `passed=True`. The Anker Soundcore Q20i row — `price=44.99`, `category="audio"` — passes both validators on the first check.

## The quality gate: stopping the flow on violation

`quality_gate` wraps `validate_contract` with a single decision: if the contract did not pass, raise `DataContractError` and stop the flow.

```python
def quality_gate(rows: list[dict]) -> ContractReport:
    report = validate_contract(rows)
    if not report.passed:
        raise DataContractError(
            f"contract failed: {report.valid}/{report.total} rows valid; "
            f"first violation: {report.violations[0] if report.violations else None}"
        )
    return report
```

The design choice is deliberate: the gate does not log and continue, it does not drop invalid rows silently, and it does not produce a "partial success." It raises. When a Prefect task raises, the flow run transitions to `Failed`, the error is recorded in the run history, and no downstream task executes. The message carries the first violation so you know what to fix without parsing logs.

<DataContractGauge />

The three scenarios in the animation are:

1. **Real snapshot (anchored)** — 270/270 valid, `gate_passed=True`, flow continues.
2. **One bad row (illustrative)** — inject `price=-1`; `validate_contract` produces `valid=269`, `violations=[{"id": ..., "error": "price must be > 0"}]`; `quality_gate` raises `DataContractError`; the flow fails after the gate task.
3. **Missing required column (illustrative)** — a row without `"category"` fails the pre-check before Pydantic sees it; `valid=0`; same `DataContractError`.

The gate is cheap to run (one Pydantic model validation per row, no I/O). That is the point: a fast, hard stop before any expensive downstream work.

## The dbt-style model: good_deals.sql

The final stage materializes a SQL view over the normalized rows. The model lives at `dealfinder/models/good_deals.sql` and runs via SQLite in `run_good_deals_model`:

```sql
-- dealfinder/models/good_deals.sql
SELECT
    id,
    query,
    category,
    title,
    brand,
    price,
    median_price_at_capture,
    (median_price_at_capture - price) / median_price_at_capture AS median_deal_pct
FROM products
WHERE
    price > 0
    AND median_price_at_capture > 0
    AND (median_price_at_capture - price) / median_price_at_capture BETWEEN 0.10 AND 0.90
ORDER BY median_deal_pct DESC
```

The `BETWEEN 0.10 AND 0.90` band is the key design decision. It keeps listings that are genuinely discounted — at least 10% below the same-query median — while excluding two noise classes:

- **Below 10%** — essentially at the median price; not a deal signal worth acting on.
- **Above 90%** — the mislisting region. A 91.7%-under-median listing in the snapshot is an accessory mislisted under a headphones query; the naive median signal reads it as a screaming deal, but the $10.75 price for a Kindle Paperwhite accessory has nothing to do with headphone value.

Against the committed snapshot, the view returns **111 rows**. That is not a tuned number — it is the count that falls inside the band when you run the SQL against 270 rows. `tests/test_flows.py` pins it:

```python
def test_good_deals_model_row_count_is_pinned():
    rows = load_snapshot()
    deals = run_good_deals_model(rows)
    assert len(deals) == 111
```

The Anker Soundcore Q20i appears in the view: `price=44.99`, `median_price_at_capture=162.97`, `median_deal_pct ≈ 0.724`. The Bose QuietComfort 45 at $46 also appears, with `median_deal_pct ≈ 0.718` — the SQL view does not know it is a trap. That is why Part 21 adds the gradient-boosted residual that separates them.

<Callout tone="warn">
**The good_deals view is not the final deal signal.** It uses the same naive median that Part 3 showed is fooled by mislistings. The Bose QC45 at $46 — median says 71.8% off — passes the SQL filter because the filter is median-only. Part 21's gradient-boosted model adds the residual that catches it. The view is the right output for a batch training table (it gives you 111 labeled "candidate deal" rows); it is not the production classifier.
</Callout>

## Running the real flow: what snapshot_flow() returns

Running `snapshot_flow()` with Prefect 3.7.7 installed produces this output (real, captured from the companion):

```python
from dealfinder.flows import snapshot_flow, HAS_PREFECT

print("HAS_PREFECT:", HAS_PREFECT)           # True
result = snapshot_flow()
print("ingested:", result.ingested)           # 270
print("normalized:", result.normalized)       # 270
print("contract passed:", result.gate_passed) # True
print("violations:", result.contract.violations)  # []
print("labeled:", result.labeled)             # 270
print("label_distribution:", result.label_distribution)
# {'deal': 71, 'fair': 40, 'suspicious': 32, 'overpriced': 127}
print("good_deals:", result.good_deals)       # 111
```

The label distribution deserves a moment. Of 270 items: 71 are deals, 40 are fair, 32 are suspicious, and 127 are overpriced. Overpriced is the plurality class. That is the class imbalance Part 19 documented — the same training set the Part 21 classifier will confront. The pipeline preserves the real distribution; it does not resample or balance here.

The noise-cancelling headphones subset drives that distribution: 15 items at the $162.97 median. The Anker Soundcore Q20i at $44.99 is labeled `deal`. The Bose QuietComfort 45 at $46 is labeled `suspicious` — the two-signal score (median signal ≈ 0.718, residual fraction ≈ 0.839) crosses both thresholds.

## The FlowResult: everything the caller needs

`FlowResult` is what `snapshot_flow` and `snapshot_pipeline` both return:

```python
@dataclass
class FlowResult:
    ingested: int
    normalized: int
    contract: ContractReport
    labeled: int
    label_distribution: dict[str, int]
    good_deals: int
    persisted_to: str | None = None

    @property
    def gate_passed(self) -> bool:
        return self.contract.passed
```

`persisted_to` is `None` unless you pass `persist_dir` — then it is the path to the written `good_deals.csv`. Every field is a plain Python value: no Prefect-specific types, no futures, no handles. A downstream scheduler, a CI script, or a notebook can use `FlowResult` without importing Prefect at all.

The `gate_passed` property is the single "did the pipeline succeed?" boolean. A monitoring hook, a Slack alert, or an eval gate in Part 24 can check `result.gate_passed` without reading the `ContractReport` internals.

## Tests that pin the contract

All seven tests in `tests/test_flows.py` pass against the committed snapshot:

```python
# tests/test_flows.py — real test names (anchored to the committed snapshot)

def test_contract_passes_on_the_real_snapshot():
    # 270/270 valid; no violations; passed=True
    rows = load_snapshot()
    report = validate_contract(rows)
    assert report.passed
    assert report.valid == 270
    assert report.violations == []

def test_contract_flags_bad_rows_and_gate_raises():
    # inject one bad row (price=-1) → DataContractError
    rows = load_snapshot()
    rows[0] = {**rows[0], "price": -1.0}
    with pytest.raises(DataContractError):
        quality_gate(rows)

def test_good_deals_model_row_count_is_pinned():
    rows = load_snapshot()
    deals = run_good_deals_model(rows)
    assert len(deals) == 111

def test_plain_pipeline_end_to_end_pins_real_output():
    result = snapshot_pipeline()
    assert result.ingested == 270
    assert result.contract.passed
    assert result.labeled == 270
    assert result.label_distribution == {
        "deal": 71, "fair": 40, "suspicious": 32, "overpriced": 127
    }
    assert result.good_deals == 111

def test_normalize_attaches_title_extracted_brand():
    # Anker Soundcore Q20i: true_brand extracted from title, not the retailer field
    rows = load_snapshot()
    normalized = normalize_rows(rows)
    anker = next(r for r in normalized if "Q20i" in r["title"])
    assert anker["true_brand"] == "Soundcore"

def test_persist_writes_good_deals_csv():
    # FlowResult.persisted_to points to a real file
    with tempfile.TemporaryDirectory() as d:
        result = snapshot_pipeline(persist_dir=d)
        assert result.persisted_to is not None
        assert Path(result.persisted_to).exists()

def test_prefect_flow_runs_end_to_end():
    # Only runs when HAS_PREFECT; ran here — Prefect 3.7.7 present
    pytest.importorskip("prefect")
    result = snapshot_flow()
    assert result.gate_passed
    assert result.good_deals == 111
```

Run them with:

```bash
pytest tests/test_flows.py -v
```

All seven pass. Prefect emits shutdown logging after the run (`Stopping temporary server…`) — cosmetic, not a failure. The key test is `test_prefect_flow_runs_end_to_end`: it uses `pytest.importorskip` so it skips gracefully when Prefect is absent, and in this environment it ran on the real engine.

<Callout tone="note">
**The normalize assertion.** `test_normalize_attaches_title_extracted_brand` checks that the Anker Soundcore Q20i row — where the raw `brand` field holds the retailer, not the manufacturer — emerges from `normalize_rows` with `true_brand == "Soundcore"`. That is the `title_brand()` function from Part 1 applied at pipeline scale: 270 rows, one pass, no API calls.
