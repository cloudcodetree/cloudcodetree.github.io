# What You'll Like Next

**TL;DR: Part 3 told you whether a deal is real. This part makes DealFinder proactive — it exposes the two recommenders every recsys starts with, over the real snapshot. `content_recommend` ranks items by cosine over the cached `BAAI/bge-small-en-v1.5` title embeddings ("more like this"); `collaborative_recommend` ranks by item–item co-occurrence in the real interaction log ("people who liked this also liked…"). The two signals return genuinely different neighborhoods for the same Sony WH-1000XM5 anchor — and that contrast is the whole lesson.**

You'll see why each signal alone is incomplete: content similarity surfaces near-duplicate listings of the same product, while collaborative filtering needs interaction history it may not have. The primitives are representation-agnostic — the same two functions power the feature-vector demo, the title-embedding recommender, and the CF log.

## The recommendation problem

Part 3 answered a binary question: is this price a deal? This part answers a different one: given one product a user is looking at, which five should you show them next?

Two independent signals exist. **Content-based** asks "what is this product like?" using the item's own title embedding — it works on day one, even for a brand-new user. **Collaborative filtering** ignores features entirely and asks "what did users who looked at this also look at?" — it captures taste that specs can't, but needs interaction data.

Neither signal alone is safe to serve over heterogeneous electronics data. You need both.

## Two strategies, two blind spots

Content-based on a broad electronics catalog has a specific failure: it finds items that are *textually* similar, not items that are *useful* alternatives. The reference "Sony WH-1000XM5 Wireless Headphones" is textually closest to another Sony WH-1000XM5 listing — the "SONY WH-1000XM5 Wireless Noise-Canceling Headphones" at $248.00 — so a near-duplicate of the same product grabs rank 1 before you've offered a single genuine alternative.

Collaborative filtering ignores item features entirely and asks who-liked-what, so it captures taste that specs can't — but it needs an interaction log, which for a one-day-old catalog you may not have. Neither signal alone is complete. Seeing the two side by side is the point.

## Content-based: embed titles, rank by cosine

`dealfinder/embed.py` handles both the one-time embed run and loading the committed cache. `recommend.py` imports the cache and exposes `similar_products`:

```python
# dealfinder/recommend.py
def load_catalog_embeddings(
    products: list[Product] | None = None,
) -> tuple[list[Product], np.ndarray]:
    """Align the frozen snapshot's products to their cached title embeddings.

    Reuses the Part-4 committed embedding cache (no model run), returning the
    products and an (n, 384) matrix in the same order.
    """
    products = products if products is not None else load_products()
    ids, vectors = load_title_embeddings()
    pos = {pid: i for i, pid in enumerate(ids)}
    rows = np.array([vectors[pos[p.id]] for p in products], dtype=float)
    return products, rows


def similar_products(title_substring: str, k: int = 5) -> list[dict]:
    """"More like this" over real items — e.g. similar_products("WH-1000XM5").

    Content-based on the cached title embeddings, so neighbors are semantically
    close real listings (other Sony/premium audio), with their price attached.
    """
    products, emb = load_catalog_embeddings()
    idx = next(i for i, p in enumerate(products) if title_substring.lower() in p.title.lower())
    recs = content_recommend(idx, emb, k, standardize=False)
    return [
        {"id": products[j].id, "title": products[j].title,
         "price": products[j].price, "category": products[j].category}
        for j in recs
    ]
```

`content_recommend` z-scores columns by default (right for small hand-built feature vectors of differing scale), but `similar_products` passes `standardize=False`: the bge-small embeddings are already dense and normalized, so per-column z-scoring would distort their geometry. The reference item is always excluded from its own results (the `j != idx` filter).

The cache lives at `data/embeddings/electronics-2026-07.title-bge-small.npz` — committed, so CI never runs the model. It loads in milliseconds and returns a `(270, 384)` matrix.

Now call it for the hero-cast anchor:

```python
from dealfinder.recommend import similar_products

for r in similar_products("WH-1000XM5", k=5):
    print(f"  ${r['price']:>7.2f}  [{r['category']}] {r['title']}")
```

```
  $ 248.00  [audio] SONY WH-1000XM5 Wireless Noise-Canceling Headphones
  $ 399.99  [audio] Sony WH-1000XM6 Wireless Noise Canceling Headphones
  $ 129.99  [audio] Sony WH-CH720N/P Wireless Noise Canceling Headphones
  $ 129.99  [audio] Sony WH-CH720N Noise Canceling Wireless Headphones
  $  68.00  [audio] Sony WF-C510 Truly Wireless Earbuds
```

Every neighbor is a real Sony/premium audio listing — content similarity keeps you inside the right category. But rank 1 is telling: it is a *different listing of the same product*, the "SONY WH-1000XM5 Wireless Noise-Canceling Headphones" at $248.00, not a genuine alternative.

## The near-duplicate neighbor

The #1 neighbor is another WH-1000XM5 listing — same product, different retailer entry, at $248.00. Its title is almost identical to the reference item's, so its embedding sits right next to it and it takes rank 1 before a single genuine alternative appears.

This is not a model deficiency; it is a data property. The snapshot contains multiple XM5 listings because the live connectors return every offer for a query. Content similarity is doing its job — ranking by title-embedding cosine — it just has no notion of "this is the same product I'm already looking at" or of deal quality. That second gap is exactly what a taste signal covers: collaborative filtering ranks by who-liked-what, not by how the titles read.

<Callout tone="note">
**Content similarity is representation-agnostic.** `content_recommend` and `collaborative_recommend` take *any* matrix. Here `similar_products` feeds them the cached 384-dim title embeddings, but the same two functions would rank hand-built feature vectors or the CF co-like matrix — the geometry is the only thing that changes.
</Callout>

<Callout tone="tip">
**Going further: the embedder itself is fine-tunable.** This part (and Parts 5 and 13) all lean on a *general-purpose* `bge-small` — a model that has never seen a consumer-electronics catalog. Part 10 fine-tunes the extractor LLM; the embedder is the other model in the stack you can specialize, and it's often the higher-leverage one for retrieval quality. The recipe is small: collect `(anchor, positive)` pairs — for DealFinder, two listings of the same product, or a query paired with the listing a user clicked — and train with sentence-transformers' `MultipleNegativesRankingLoss`, which mines negatives *in-batch* (so a bigger batch = more negatives = a sharper model; batch 32, lr 2e-5, one epoch over ~500+ pairs is a typical starting point). Reported domain gains run **+15–40% NDCG@10**; always confirm with `InformationRetrievalEvaluator` before-and-after on a held-out set rather than trusting the headline number. The payoff is a drop-in swap: re-embed the catalog with the tuned model and the `.npz` cache format, the cosine math, and the pgvector index (Part 13) are all unchanged — a "retailer-vocabulary embedder" that knows `WH-1000XM5` and `Q20i` are model numbers, not noise.
</Callout>

## Collaborative filtering from the real interaction log

`data/sample/interactions.json` is the real interaction log: a users × items matrix of 0/1 signals (view/like) keyed to snapshot `id` values. Load it with `load_interactions`:

```python
# dealfinder/recommend.py
def load_interactions(path: Path | str | None = None) -> tuple[list[str], np.ndarray]:
    """Load the real interaction log: (item_ids, users×items 0/1 matrix)."""
    data = json.loads(Path(path or _INTERACTIONS).read_text())
    return data["item_ids"], np.array(data["matrix"], dtype=float)
```

Before running it, see what "item–item co-occurrence" actually computes — the entire mechanism fits in a toy matrix:

<ItemItemCF />

Then call `collaborative_recommend` with a single-item preference vector — a user who has only liked the XM5. `collaborative_recommend` builds an item–item co-occurrence matrix from `R.T`, sums similarity to the liked items, and sets already-liked items to `-inf` so it never recommends something you already have:

```python
from dealfinder.recommend import collaborative_recommend, load_interactions
from dealfinder.snapshot import load_products
import numpy as np

item_ids, R = load_interactions()          # (72 users, 24 items)
products = {p.id: p for p in load_products()}

ref = "Sony WH-1000XM5 Wireless Headphones"
xm5_id = next(p.id for p in products.values() if p.title == ref)
xm5_idx = item_ids.index(xm5_id)

user = np.zeros(len(item_ids))
user[xm5_idx] = 1                           # liked only the XM5

for j in collaborative_recommend(user, R, k=5):
    p = products[item_ids[j]]
    print(f"  {p.title}  ${p.price}")
```

```
  Sony WH-1000XM6 Wireless Noise Canceling Headphones  $399.99
  Beats Studio Pro Wireless Headphones  $249.99
  Bose QuietComfort Ultra Headphones  $415.98
  Sony WH-CH720N Noise Canceling Wireless Headphones  $129.99
  Bose QuietComfort Noise Cancelling Wireless Headphones  $359.99
```

The collaborative signal surfaces a different, taste-driven neighborhood — co-likes across users, not embedding geometry. Notice it leans toward *premium/expensive* headphones (Beats Studio Pro, Bose QuietComfort Ultra) that the content list never surfaced: that is real purchase co-occurrence, not title similarity. The interaction log is small (72 users, 24 items) so the matrix is sparse; the part notes where you'd upgrade to ALS or a two-tower retriever once you have ≥10k items. At this scale a direct dot-product is fine.

`run_recs.py` demonstrates the canonical invocation (`k=3`) and also runs a leave-one-out offline eval comparing CF `precision@5`/`ndcg@5` against a popularity baseline. (`precision@5` = of the 5 items recommended, what fraction the held-out user actually liked; `ndcg@5` measures the same thing but rewards putting the liked items *nearer the top* of the five.)

<Callout tone="note">
**The interaction log is hand-authored for this tutorial.** It is not presented as real user data — the lesson is the mechanics of co-occurrence, not the validity of the log. Every `item_id` in `data/sample/interactions.json` is a real `id` from the committed snapshot. In production you would replace this with live clickstream; Part 33 (Saved searches and suggestions worker) wires that signal.
</Callout>

## Same anchor, two different neighborhoods

Put the two lists side by side for the same Sony WH-1000XM5 anchor. This is the entire lesson of the part — one anchor, two signals, two different answers:

| Rank | `similar_products` (content) | `collaborative_recommend` (co-likes) |
|------|------------------------------|--------------------------------------|
| 1 | SONY WH-1000XM5 (Noise-Canceling) — $248.00 | Sony WH-1000XM6 — $399.99 |
| 2 | Sony WH-1000XM6 — $399.99 | Beats Studio Pro — $249.99 |
| 3 | Sony WH-CH720N/P — $129.99 | Bose QuietComfort Ultra — $415.98 |
| 4 | Sony WH-CH720N — $129.99 | Sony WH-CH720N — $129.99 |
| 5 | Sony WF-C510 Earbuds — $68.00 | Bose QuietComfort — $359.99 |

Content stays tightly inside Sony (it is reading the title text), and its #1 result is a near-duplicate of the anchor. Collaborative filtering crosses brands to Beats and Bose because *people who liked the XM5 also liked those* — a signal no title embedding can see. Only one item (Sony WH-CH720N) appears in both lists. That divergence is why a real system keeps both signals: content for cold-start and category coherence, collaborative for taste.

<Callout tone="note">
**Neither list knows about deal quality.** Both recommenders rank by similarity alone — the Part 3 deal score (median + model residual) is a separate signal. Fusing similarity *and* value into one ranking is the job of Part 5's `search_catalog`, which layers keyword + semantic retrieval and then re-ranks by deal score. Here in Part 4 the two recommenders stay pure: "more like this" and "people who liked this."
</Callout>

## Reproducibility checks

The recommender assertions run against the committed snapshot and interaction log. They live in `tests/test_recommend.py`:

```python
# tests/test_recommend.py
from dealfinder.recommend import (
    collaborative_recommend, content_recommend,
    load_catalog_embeddings, load_interactions, similar_products,
)
```

The five pinned tests:

- `test_content_recommends_nearest_by_features` — `content_recommend` returns the nearest item by feature cosine on a small hand-built matrix.
- `test_collaborative_recommends_co_liked_item` — `collaborative_recommend` surfaces a co-liked item and never re-recommends something already liked.
- `test_collaborative_excludes_already_liked` — already-liked items (set to `-inf`) never appear in the results.
- `test_similar_products_to_xm5_are_real_audio_items` — every neighbor of `similar_products("WH-1000XM5", 5)` is a real `audio` listing.
- `test_collaborative_over_real_interaction_log` — CF over the committed `data/sample/interactions.json` returns real snapshot ids for the XM5 anchor.

Run them with:

```bash
pytest tests/test_recommend.py -v
```

All pass against the committed snapshot. The embedding cache means no model is downloaded in CI.
