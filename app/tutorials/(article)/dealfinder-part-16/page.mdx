# Context Engineering: The Window Is RAM

**TL;DR: Agentic RAG (Part 15) can retrieve fifteen candidate listings across three hops. Every one of them competes with the system prompt, the tool schemas, and the conversation for one finite token budget. Retrieval decides *what is relevant*; context engineering decides *what actually goes in the window, in what order, and what to evict*. This part does all three over the real DealFinder context with exact bge token counts: a k=20 retrieved block is 1101 tokens, so packing it into a 256-token slice keeps 4 items and evicts 16; the strongest picks move to the edges to beat "lost in the middle"; and a six-turn deal chat compacts from 78 tokens to 49.**

You have spent five parts getting retrieval right. But retrieval hands you *candidates*, not a *prompt*. The window is the model's working memory — RAM, not storage — and it is small. Stuff too much in and you pay for tokens the model can't use, push important evidence into the dead zone where attention is weakest, or blow the limit entirely. "Context engineering" is the 2026 name for the discipline that RAG grew into: treating the assembly of that window as a first-class engineering problem, not an afterthought.

## Counting tokens for real

You cannot budget what you cannot measure. `context.py` counts with the exact bge-small WordPiece tokenizer the course already caches — no estimate, no download:

```python
from dealfinder import context as ctx

ctx.count_tokens("Sony WH-1000XM5 Wireless Noise Cancelling Headphones")  # -> 16
ctx.count_tokens("noise cancelling headphones under $150")                # -> 10
```

Sixteen tokens for a six-word title — because `WH-1000XM5` explodes into pieces, exactly the tokenization lesson from Part 2. That gap between word count and token count is *why* you have to measure: a catalog of "cheap" titles can cost far more context than it looks.

<Callout tone="note">
**Which tokenizer?** In production you count with the *generator's* tokenizer (tiktoken for GPT, for instance), because that is whose window you're filling. The course uses the cached bge tokenizer so the numbers are reproducible offline; the budgeting logic is identical whichever tokenizer you swap in.
</Callout>

## Budgeting: pack what fits, evict the rest

Here is the squeeze. The DealFinder system prompt is **62 tokens**. A k=20 retrieved block — the kind agentic RAG can accumulate — is **1101 tokens**. Add tool schemas and conversation history and you are well past a tight budget. So you don't send all 20; you pack the highest-ranked deals until the budget is spent, and evict the rest:

<ContextBudget />

```python
def pack_deals(items: list[rag.RetrievedItem], budget_tokens: int) -> Packed:
    """Greedily include retrieved deal lines (as build_context formats them) in
    rank order until the token budget is exhausted; drop the rest."""
    included, dropped, used = [], [], 0
    for it in items:
        line = rag.build_context([it])       # one numbered line, exactly as the LLM sees it
        cost = count_tokens(line)
        if used + cost <= budget_tokens:
            included.append(it); used += cost
        else:
            dropped.append(it)
    return Packed(included=included, dropped=dropped, tokens=used, budget=budget_tokens)
```

Run it against a 256-token slice. Real output:

```python
items = rag.retrieve("noise cancelling headphones under $150", k=20)   # 1101 tokens total
packed = ctx.pack_deals(items, budget_tokens=256)
print(len(packed.included), "included /", len(packed.dropped), "dropped /", packed.tokens, "tokens")
# 4 included / 16 dropped / 244 tokens
```

Four listings fit; sixteen are evicted before they ever reach the model. That is the "context as RAM" move in one function: you retrieved twenty candidates, but the window only has room for the best four alongside everything else it must hold. Evicting is not failure — it is the whole point. The tail was the least relevant anyway.

## Ordering: beating "lost in the middle"

Which four you keep matters; so does the order you place them in. Transformers recover information at the **start and end** of a long context far better than in the middle — the "lost in the middle" effect that still degrades RAG quality in 2026:

<LostInMiddle />

So after packing, reorder so the strongest picks bracket the block:

```python
def lost_in_the_middle(items: list[rag.RetrievedItem]) -> list[rag.RetrievedItem]:
    """Reorder a rank-sorted list so the strongest picks sit at the START and END.
    The top pick leads, the 2nd sits last, the 3rd is second, and so on — burying
    only the weakest in the middle."""
    head, tail = [], []
    for i, it in enumerate(items):
        (head if i % 2 == 0 else tail).append(it)
    return head + tail[::-1]
```

On the ranked top-5, the transformation is:

```text
ranked  :  [#1 Anker DEAL] [#2 Soundcore DEAL] [#3 JBL DEAL] [#4 Bose OVER] [#5 Bose SUSP]
reordered:  [#1 Anker DEAL] [#3 JBL DEAL] [#5 Bose SUSP] [#4 Bose OVER] [#2 Soundcore DEAL]
```

The best pick still leads; the second-best now *closes* the block; the weakest is buried in the middle where the model is least likely to over-weight it. Same evidence, placed where the model can actually use it.

## Compaction: fold the conversation, keep the intent

A multi-turn deal chat grows without bound, and old assistant prose is the bulk of the tokens and the least useful to carry forward. Compaction folds the old turns into a compact **intent trail** — the evolving queries — and keeps only the most recent turns verbatim:

```python
def compact_history(turns: list[str], keep_recent: int = 2) -> Compacted:
    """Compact a multi-turn deal chat: summarize old turns into one intent-trail
    line, keep the most recent `keep_recent` verbatim."""
    if len(turns) <= keep_recent:
        n = count_tokens("\n".join(turns))
        return Compacted("\n".join(turns), len(turns), len(turns), n, n)
    old, recent = turns[:-keep_recent], turns[-keep_recent:]
    intents = [_user_intent(t) for t in old if _user_intent(t)]
    summary = "[earlier queries: " + " → ".join(intents) + "]"
    after = "\n".join([summary, *recent])
    return Compacted(after, len(turns), keep_recent, count_tokens("\n".join(turns)), count_tokens(after))
```

Run it on a six-turn conversation. Real output:

```python
c = ctx.compact_history(turns, keep_recent=2)
print(c.tokens_before, "->", c.tokens_after)   # 78 -> 49
print(c.text)
```

```text
[earlier queries: noise cancelling headphones under $150 → what about wireless earbuds instead]
user: only ones with a mic
assistant: The Anker Q20i and JBL 770NC both have mics.
```

From 78 tokens to 49 — a 37% cut — and the thread survives: the summary preserves *where the conversation has been* (the query trail), and the two recent turns stay verbatim because that is where the live intent lives. The verbose assistant recommendations from earlier turns are gone, and they weren't worth their tokens.

<Callout tone="warning">
**Compaction is lossy — on purpose.** You are trading fidelity for budget. Keep the recent turns verbatim (intent lives there), summarize the old ones, and never compact away a constraint the user still cares about ("only ones with a mic" stays because it is recent). Compact too aggressively and the agent forgets what it's doing; not at all and you run out of window.
</Callout>

## Seeing it in the product

Budgeting, ordering, and eviction are normally invisible — they happen inside the pipeline, and all you see is the answer. So the app exposes them. A new **`/context`** endpoint (`serve.py`) runs the exact three levers from this part over a query and returns the token math; the static UI adds a **"window (context)"** mode that renders it:

```python
@app.get("/context")
def context_window(q: str, budget: int = 256, k: int = 20):
    # Pin to the reproducible snapshot path so the token math never depends on
    # how much has been seeded into pgvector (that is Part 13's concern, not this).
    items = rag.retrieve(q, k=k, use_db=False)
    block_tokens = sum(ctx.count_tokens(rag.build_context([it])) for it in items)
    packed  = ctx.pack_deals(items, budget_tokens=budget)   # budget + evict
    ordered = ctx.lost_in_the_middle(packed.included)        # edges beat the middle
    return {"retrieved": len(items), "block_tokens": block_tokens,
            "packed_tokens": packed.tokens, "kept": len(packed.included),
            "evicted": len(packed.dropped), "included": ordered, ...}
```

Note the `use_db=False`: `retrieve` normally follows `DATABASE_URL` (pgvector when set), but a teaching surface for token budgeting must be **reproducible**, so this route pins the deterministic in-memory snapshot path regardless of how the server is run. Same query ⇒ same 20 candidates ⇒ same 1101 tokens, every time.

The five assertions in `tests/test_context.py` pin the token math, packing, ordering, and compaction — offline, with exact counts:

```python
# tests/test_context.py  (step-16 tag)
from dealfinder import context as ctx
from dealfinder import rag

def test_count_tokens_matches_the_model_number_explosion():
    assert ctx.count_tokens("Sony WH-1000XM5 Wireless Noise Cancelling Headphones") == 16

def test_pack_deals_drops_the_tail_to_fit_a_budget():
    items = rag.retrieve("noise cancelling headphones under $150", k=20)
    packed = ctx.pack_deals(items, budget_tokens=256)
    assert packed.tokens <= 256
    assert len(packed.dropped) > 0                # k=20 does NOT fit in 256 tokens
    assert packed.included[0].title == items[0].title   # keeps the top-ranked prefix

def test_lost_in_the_middle_puts_the_best_at_the_edges():
    items = rag.retrieve("noise cancelling headphones under $150", k=5)
    reordered = ctx.lost_in_the_middle(items)
    assert reordered[0] is items[0]              # best leads
    assert reordered[-1] is items[1]             # 2nd best closes
    assert items[-1] not in (reordered[0], reordered[-1])   # weakest buried

def test_compact_history_preserves_intent_and_shrinks_tokens():
    c = ctx.compact_history(turns, keep_recent=2)
    assert c.tokens_after < c.tokens_before
    assert "noise cancelling headphones under $150" in c.text   # intent kept
    assert "Best value" not in c.text                           # old prose dropped
```

# 5 passed
